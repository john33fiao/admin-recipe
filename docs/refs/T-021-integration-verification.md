# T-021 통합 검증 기록

2026-10-25. T-019 뒤 현재 Mac release의 정상 HTTP API로 가상 전체 업무를 검증하고 T-031~T-033 이후 최종 통합·성능을 확인했다. 이 기록은 개발 장비에서 실행한 근거이며 T-001의 필수 실환경 기준을 대신하지 않는다. 실행 가능한 검증과 남은 외부 조건을 구분한다.

이 문서의 Mac 결과와 후속 [Windows 재개 검증](T-021-windows-resume-verification.md)은 서로 다른 실행 근거다. Windows에서는 새 x64 빌드를 사용하고 사용자 요청으로 종료·재시작 단계를 분리해 생략한다. 기존 Mac 통과 수·성능·시연 결과를 Windows의 새 통과 수로 복사하지 않는다.

## RTD Before

[Step 1] 변경 계획 - PASS: 초기 전체 업무·지정 시연 뒤 일괄 입력을 구현하고 최종 통합·성능을 확인한다. T-001 외부 검증·OS 왕복·운영 원자료 전체 이관은 분리한다.

[Step 2] 계획 검토 - PASS: 새 격리 DB·정상 UI/API만 사용하고 개인 자료와 가상 회귀를 분리한다. 입력 파일·비교 전용 기대값·과거 검증과 새 실행 근거를 구분한다.

[Step 3] 검토 재검토 - PASS: 원실사와 현재 정정, 초기 재고 대체 입고의 단일 반영, 레시피 배합 기준 개수·빈 값과0의 계약을 대조한다. 실제 외부 환경 없이 실환경 완료를 추정하지 않는다.

[Step 4] 계획 단순화 - PASS: 기존 release·Playwright·정상 writer·복원과 잠금 파일을 사용한다. 별도 프레임워크·직접 DB 적재·전역 설정·원자료 전체 이관을 추가하지 않는다.

## 환경과 재현

macOS 27.0.1(26A434) arm64, Rust/Cargo 1.98.0, Node 24.20.0, npm 11.19.0, Apple clang 21.0.0·macOS SDK 27.0, Playwright 1.64.1·Chromium 156.0.8078.4다. 개발 의존성을 설치하고 `node scripts/build.mjs`로 만든 `target/release/sunchang-hansang`을 사용했다.

가상 통합은 저장소 루트에서 `node scripts/verify-integration.mjs`로 재현한다. `scripts/verification/app.mjs`가 기존 Playwright를 사용해 새 격리 폴더에 release를 복사하고 실제 세션·Origin·정상 API로만 입력한다. DB 직접 쓰기·기대값 적재·기록 삭제를 하지 않는다. 앱과 DB·원요청/응답·검증 결과는 Git 제외 경로에 보존한다. Mac의 SIGINT 처리·종료 코드0·안전 종료 문구·재시작을 검증하며 Windows 정상 종료의 근거로 확대하지 않는다.

최초 검증 release SHA-256은 `a931caaefcf4227b1e38c3d56afc5397653466b7fc65264d14210d0da45e72a4`다. 앱 사본을 실행 중인 빌드 결과와 분리했으므로 다른 시험의 재빌드가 해당 사본을 바꾸지 않는다.

일괄 입력의 후속 수정까지 반영한 최종 후보 SHA-256은 `3ca214f35218d3c175465d2e9430c96a5335a38499687fc37430d58e1925da53`다. 이 후보에서 가상 전체 업무48개와 지정 시연의 보존된 DB 복사본 읽기10개를 각각 다시 확인했다. 앞선 후보의 반복48·10과 합산하지 않는다. 아래 성능·전체 회귀도 사용한 후보와 실제 완료 여부를 따로 기록한다.

초기 전체 Rust 실행은 sandbox의 포트 확보 실패1개와 실제 loopback bind의 `PermissionDenied`4개를 기록했다. 이후 장시간 실사 저장 시험 도중 실행 환경이 종료되어 전체 완료 결과가 없다. 초기 Chromium 전체122개 실행도25개 통과 뒤 환경 종료로 중단됐다. 이 두 중단 실행을 전체 통과로 표시하거나 최종 재실행 결과에 합산하지 않는다. 이후 UI를 다시 빌드하고 loopback 실행이 허용되는 환경에서 아래 회귀를 별도로 확인했다.

## 가상 전체 업무

1. 사전 가격과 주문은 보유 수량을 만들지 않는다. 주문 입고와 직접 입고를 실제 수량·금액으로 각각 확정하고 평균을 대조한다.
2. 원재료 100g·200원 중 40g·80원을 실제 생산에 투입하여 손질품 20g·80원으로 연결한다. 원재료는 60g·120원이 남는다.
3. 손질품을 시작 실사한 뒤 메뉴 3개·1개를 판매한다. 판매 전후의 마지막 확인·보유·가격 근거는 동일하며 판매 당시 레시피 원가를 보존한다.
4. 원재료 10g을 명시 폐기하여 50g·120원이 남는 손실 배분을 확인한다. 손질품 마지막 실사 16g·64원은 소모 4g·16원을 확정하고 두 판매에 3:1로 배분한다.
5. 첫 판매를 1개로 정정한다. 총소모·현재 보유를 유지하며 현재 배분은 2g·8원씩 바뀐다. 원실사 상세는 당시 배분을 보존하고 정정 영향·현재 판매 조회가 새 배분을 보여주는 경계를 각각 확인한다.
6. 첫 원입고의 5g 반품은 원구입 단가 대신 현재 평균으로 12원을 차감하여 원재료 45g·108원을 남긴다. 원입고 참고 금액을 보존한다.
7. 레시피 변경 뒤 기존 판매의 당시 원가는 그대로이고 새 판매에만 새 버전을 적용한다. 0개·판매가 0원의 알려진 금액0과 무상 입고·실사 수량0을 확인한다. 실입고 수량0은 기존 양수 계약대로 확정하지 않는다.
8. 전체 상태 복원 후 수량·가치·판매 버전·정정·배분·반품을 대조하고 복원 UUID 재시도의 동일 응답을 확인한다. 복원 전 업무 요청은 `409 stale_generation`·`already_processed`로 처리 사실을 알리고 새 변경을 만들지 않는다. 세션 없는 API와 다른 Origin의 변경은 각각401·403이다.

첫 실행은21개 단언을 확인한 뒤 원실사 상세에 현재 배분을 기대한 시험 관측 오류로 실패했다. 원기록과 현재 유효 정정을 구분한 뒤 다음 실행은42개 단언을 확인하고 복원 전 업무 요청에201을 기대한 시험 관측 오류로 실패했다. ADR-009의 세대 계약에 맞춰 처리 사실과 무변경을 확인하도록 보완했다. 제품 코드를 바꾸지 않았으며 최초 로그·격리 DB를 보존했다. 최종 실행은 **48개 스크립트 단언 PASS·종료0**이다. 앞선 실행에서 이미 통과한 단언이나 기존 Rust/브라우저 시험 수를 합산하지 않는다.

T-031~T-033 추가 뒤 최종 후보에서 같은48개 흐름을 새 격리 DB로 재실행하여 **48 PASS·종료0**을 확인했다. 최초 단계의48개와 겹치므로96개로 합산하지 않는다. 두 앱 프로세스는 모두 SIGINT 정상종료 후 회수됐고 실패 정리 경로를 성공 종료 증거로 사용하지 않았다.

## 지정 비공개 자료 시연

입력 자료와 전달 해시·보존 검증 기록을 대조했다. 입력 CSV·시나리오·비교용 기대값은 이전본과 바이트가 같았다. 기존 로컬 검증기 세 파일은 출력 함수의 개행 인자만 조정되어 있었으며, 두 보고서의 차이는 파일 열거 검사 순서였다. 해당 변경을 보존하고 새 비공개 복사본에서 검증기3개를 다시 실행해 모두 종료0·원본 해시 불변을 확인했다. 이는 앱 실행 성공과 별개다.

지정 시나리오는 새 격리 DB의 정상 UI/API에서 초기 재고의 각 행을 한 번씩 직접 입고로 대체 → 시작 실사 → 두 판매 → 마지막 실사 순서로 실행한다. 레시피는 배합 기준 개수를 사용해 순환 소수를 자르지 않고 입력한다. 기대값은 앱의 모든 변경이 끝난 뒤 비교 전용으로 읽는다. 상위 운영 원자료·별도 초기 잔액을 중복 가산하지 않는다.

최초 시연은6개 단언과 모든 입력·마지막 실사 API를 확인한 뒤 여러 실사 행을 단일 요소로 조회한 화면 대기 오류로 실패했다. 다중 행의 첫 요소 가시성으로 관측을 보완했다. 후속 실행은 **90개 스크립트 단언 PASS·종료0**이며 단계별 수량·가치·판매 전후 보유 불변·미확정/확정 소모·각 배분과 합계를 비교용 기대값에 대조했다. 모든 화면 연결을 끊은 뒤 기본120초 유예로 종료 코드0·signal 없음·안전 종료 문구를 확인하고 재시작 후 상태·보유 근거가 같았다. 최초 입력 성공이나 자료 검증만으로 시연 성공을 판정하지 않는다. 자료·DB·화면·수치·원로그는 공개 파일에 넣지 않는다.

최종 후보의 영향 확인은 정상종료된 같은 시연 DB를 새 제외 폴더로 복사하여 수행했다. 기존 재시작 응답과 state·보유 조회5개가 동일하고 마지막 실사5행·메뉴 화면을 읽을 수 있으며 조회 전후 state가 같았다. 원시연 폴더의 DB·바이너리·화면·결과를 포함한 전체 파일 해시도 동일했다. 이 **읽기 검증10개 PASS·종료0**은90개 시연 입력을 다시 수행한 결과나 새로운 재고 적재가 아니다. 최종 두 화면도 직접 검토했으며 개인 자료를 포함하므로 공개에 넣지 않는다.

## 성능과 최종 통합 상태

`node scripts/verify-performance.mjs`를 최종 release에서 프로젝트의 다른 빌드·검증 부하가 종료된 뒤 **1회 실행하여 PASS·종료0,146.569초**를 확인했다. Apple M4 Pro·위 macOS/도구 환경이며 시작/끝의 실행파일과 스크립트 SHA-256이 같았다. 가상 판매 0·1·10·50·100건과100건 실사 배분 후의 저장·시작·판매 목록/필터·통계/그래프·JSON 누적 크기를 기록했다. 이 dataset의 재료는 원재료1개·메뉴1개로 고정한다. 별도 새 catalog DB에는 가상 재료0·1·10·50·100개를 정상 API로 순차 등록하여 시작·전체 목록·일부 이름 검색·JSON 크기와 실제 목록/검색 화면을 측정했다. 두 dataset을 같은 release로 실행했으며 보존·의미 검증 경로를 바꾸거나 JSON을 삭제하지 않았다. 단일 실행의 자료 규모별 관측이며 과거 Windows debug 시험과 엄밀한 배율이나 운영 성능 보장을 만들지 않는다.

## 남은 환경과 재개 절차

T-021-01~04·06의 로컬 근거는 확보했으며05는 미검증이다. 다음 작업은 [T-001](../tickets/T-001-portable-local-app.md)의 필수 잔여 기준을 실제 환경에서 확인하는 것이다.
