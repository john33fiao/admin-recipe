# 수량·원가와 소모 보정 계산 계약

- 상태: T-002 설계 완료 — 독립 검토 통과, 제품 코드·앱 검증 결과 아님
- 작성일: 2026-10-24
- 범위: [T-002](tickets/T-002-domain-contract.md)의 T-002-01~08
- 운영 기준: [요구사항](REQUIREMENTS.md), [ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)
- 기존 저장 계약: [ADR-006](decisions/ADR-006-local-runtime-and-journal.md)

이 문서는 확정된 운영 정책을 구현할 숫자 표현·입출력·순서·보존 조건을 정의한다. 신규 운영 정책, 제품 구현, 실제 데이터 이관을 완료한 문서가 아니다. 예시는 모두 이 계약 검토용 가상 수치다. T-001의 별도 장비·실제 절전 등 미완료 기준은 그대로 유지한다.

## 1. 불변 조건과 용어

1. 품목 UUID는 이름·표시 단위·버전 변경과 무관하게 유지한다. 판매는 당시 메뉴/레시피/판매가 버전을 참조하며 재고 변동을 만들지 않는다.
2. 확정 업무의 수량·가치·참조와 요청 ID는 한 트랜잭션에서 기록한다. 임시 기록은 확정 수량/가치·실사 배분에 영향을 주지 않는다.
3. 품목의 마지막 실사 수량과 그 뒤의 확정 입고/생산/반품/명시 폐기를 구분한다. 아래 `Q`는 소모 정산용 계산 상태이고 실사 사이의 실제 현재고나 별도 예상 재고로 표시하지 않는다.
4. 실사 소모·생산 투입·반품은 보유 가치를 차감한다. 잔량이 있는 명시 폐기는 가치를 유지하고 전량 명시 폐기는 남은 가치를 손실로 끝낸다.
5. 한 사건의 수량/가치와 그 정정은 한 번만 반영한다. 소모 배분량 합계는 총소모, 배분 원가 합계는 총소모 원가와 일치한다. 생산 결과물 가치 합계는 투입 가치와 일치한다.
6. 원기록·원본 JSON·과거 버전은 바꾸지 않는다. 보정은 새 기록과 변경 전후 근거로 남기며 전체 복원도 새 기록이다.

| 기호 | 의미 |
| --- | --- |
| `Q`, `V` | 확정 사건으로 계산한 소모 정산 기준 수량, 보유 가치 |
| `B` | 해당 품목의 마지막 유효 실사 또는 확인한 시작 기준 |
| `M` | 이번 실사에서 입력한 실제 수량 |
| `C` | 실사에서 확정한 미기록 소모 수량 |
| `K` | 그 소모에 대응하는 가치 |
| `seq` | DB가 확정하는 전역 기록 순번. UTC 시각이 같은 사건도 구별 |
| `revision` | 미리보기의 전제가 되는 현재 상태의 개정 번호 |
| `epoch` | 전체 복원 뒤 오래된 화면의 쓰기를 구별하는 상태 세대 |

## 2. 수치 표현·범위·반올림

### 저장과 전송

업무 수량은 기준 단위의 백만분의 일, 금액은 원의 백만분의 일을 정수로 저장한다. 금액의 소수는 평균 원가와 배분에 필요한 계산 정밀도이며 세금·결제 정책을 추가하지 않는다. SQLite에는 `INTEGER`, Rust에는 `i64`, 곱셈·합계의 중간 계산에는 검사된 `i128`을 사용한다. `float`/`REAL`로 수량·가치를 누적하지 않는다.

| 값 | 허용 범위와 표현 |
| --- | --- |
| 수량 | `0`~`9,000,000,000` 기준 단위, 소수 최대 6자리. 내부 최대 `9,000,000,000,000,000` |
| 금액/보유 가치 | `0`~`9,000,000,000,000`원, 소수 최대 6자리. 내부 최대 `9,000,000,000,000,000,000` |
| 판매 개수 | `0`~`1,000,000,000` 정수. 레시피 구성 수량 0 및 판매 개수 0을 저장 가능. 0개 판매는 배분 가중치 0 |
| 원가 배분율 | 0~100%, 소수 최대 6자리. 확정 시 합계 100% |
| 보정 차액 | 위 금액 범위 안의 부호 있는 정수. 결과 보유 가치는 음수가 될 수 없음 |
| 순번 | 양의 `i64`. JSON에서는 정수 문자열 |
| 개정 번호 | 0 이상의 `i64`. 아직 변경이 없는 초기 상태는 0이며 JSON에서는 정수 문자열 |

API·JSON의 수량·금액·단가 비율 항·순번은 십진 문자열이다. 예를 들어 기준 수량은 `"1500.125"`, 금액은 `"1800.5"`, 순번은 `"42"`다. 일반 십진 표기만 수신하고 공백 제거 후 부호·소수 자릿수·상한을 검사한다. 지수·천 단위 구분자·`NaN`·`Infinity`·음수 업무 수량을 거절한다. 출력은 불필요한 소수 0을 제거하고 음의 0을 만들지 않는다. 내부 부호 있는 보정 필드만 음수를 허용한다.

입력의 6자리 초과는 조용히 반올림하지 않고 입력 오류로 반환한다. 환산한 기준 수량도 같은 정밀도·범위 검사를 거친다. 브라우저는 표시·검증 때 문자열 또는 `BigInt`를 사용하며 JavaScript `Number`의 정수 범위로 저장값을 제한하거나 변환하지 않는다. 일괄 입력의 합계·계산 중간값·생산 결과물·정정 후 상태가 해당 범위를 넘으면 전체 요청을 거절하고 입력을 유지한다.

위 표는 표현 범위다. 각 업무의 입력 조건은 다음과 같으며 0 수량에 양의 입고금액을 붙여 수량 0·가치 양수인 재고를 만들지 않는다.

| 업무 | 수량/금액 조건 |
| --- | --- |
| 레시피 직접 구성 | 수량 0 허용. 배치 기준 개수/분모는 양의 정수 |
| 판매 | 개수 0 허용. 판매가/금액 0 또는 없음 구분 |
| 실사/시작 기준 | 수량 0 허용. 확정한 수량 0이면 보유 가치도 0. 빈칸은 미확인 |
| 사전 가격 | 기준 수량 양수, 금액 0 이상 |
| 발주/실제 입고 | 수량 양수. 입고금액 0 이상, 발주 예상금액은 없음 가능 |
| 생산 투입/결과·반품·명시 폐기 | 선택한 각 행의 수량 양수. 투입/결과 원가 0 허용 |
| 지연 입고 | 총입고 R 양수, 포함 I는 0~R, 미포함 U는 R-I. U가 0이면 신규 수량 행을 생략 |

빈 업무 행은 확정 대상에 넣지 않는다. 임시 기록은 미완성 값을 보관할 수 있지만 확정 시 위 조건을 다시 검증한다.

### 계산과 잔여

- 단가는 `금액 정수 / 수량 정수`의 정확한 비율로 취급한다. 현재 평균의 분자/분모와 적용 원기록을 보존한다. 화면에 반올림한 단가를 다시 원가 계산에 사용하지 않는다.
- 단일 비례 원가 `V × q / Q`는 최종 금액 최소 단위에서 가장 가까운 정수로 반올림한다. 정확한 절반은 0에서 먼 쪽으로 처리한다. 보유 가치 차감에 적용할 때 결과는 원금액의 범위 안이어야 한다.
- `q == Q`인 전량 사용·반품·소모는 나눗셈 대신 남은 `V` 전부를 가져간다. 마지막 금액 잔여를 유령 재고나 다음 입고로 넘기지 않는다.
- 여러 대상에 하나의 총량을 나눌 때 각 몫의 내림값을 구한 뒤 가장 큰 분수 잔여 순으로 최소 단위 하나씩 준다. 동률은 대상의 원본 `seq`, 행 순번, UUID 사전순으로 해소한다. 총량과 합계는 정수로 정확히 일치한다.
- 소모 수량과 소모 원가는 각각 같은 판매 개수 가중치로 분배한다. 아주 작은 총량에서는 어떤 행의 표시 수량이 0이고 금액이 1 최소 단위일 수 있다. 배분 근거·정밀도를 보존하며 그 행을 임의 삭제하지 않는다.
- 여러 재료의 레시피 원가는 각 직접 참조 행의 정확한 단가 비율×수량을 금액 최소 단위로 한 번 반올림한 뒤 합한다. 최종 원가는 저장된 행 원가의 합과 일치한다. 화면에서 원 단위 등으로 줄여 보여준 행 값을 다시 합산하지 않는다.
- 합계 가중치가 0이면 나누지 않는다. 실사 소모는 미배분, 판매가가 0/없음인 원가율은 계산 불가다. 가격 `null`은 없음, 금액 `"0"`은 유효한 0원이다.

가격이 없는 직접 참조 행의 구성 수량이 0이면 행 원가는 0이며 가격 없음 표시는 유지한다. 구성 수량이 양수면 원가를 `null`로 두고 알려진 원가 소계와 미계산 재료를 표시한다. 이를 0원 총원가나 0% 원가율로 제시하지 않는다. 판매 저장 자체는 가격 없음으로 막지 않는다.

## 3. 단위·품목·버전 계약

| 차원 | 기준 단위 | 입력/표시 환산 |
| --- | --- | --- |
| 질량 | g | g = 1, kg = 1000 |
| 부피 | mL | mL = 1, L = 1000 |
| 자유 단위 | 등록한 문자 그대로 | 같은 자유 단위 안에서만 1:1 |

`g`↔`mL`는 밀도 추정 없이 거절한다. `개`↔`장`, 서로 다른 자유 단위도 환산하지 않는다. 정해진 네 기호만 자동 분류하며 대소문자·띄어쓰기·비슷한 철자를 임의 통합하지 않는다. 기존 단위 문자열은 보존하고, 인식되지 않는 단위는 자유 단위로 유지한다.

`item`은 기존 재료 UUID를 품목 ID로 사용한다. `item_version`에는 이름, 상태(원물/손질재료/비축품/판매메뉴), 설명, 단위 차원/기준 단위, 표시 단위, 아카이브 여부, 생성 기록을 둔다. 같은 차원의 표시 변경은 새 버전을 만들고 기준 수량은 바꾸지 않는다. 과거 행에는 당시 입력 수량·단위와 버전 ID도 보존한다. 다른 차원으로의 변경은 새 품목 등록으로 처리한다.

이름은 현재처럼 중복을 허용하며 검색 결과에는 상태·단위·ID 구별 정보를 제공한다. UUID로 참조하고 이름으로 외래 키를 만들지 않는다. 메뉴 복제는 새 UUID와 독립 레시피 버전을 만든다. 이름은 `원메뉴명 (2)`, 충돌하면 다음 번호다.

`recipe_version`은 메뉴 UUID, 버전 UUID, 기준 메뉴 개수 `basis_count`, 직접 구성 행(품목 UUID/품목 버전, 기준 수량의 분자, 메모), 조리 설명/공정/시간, 판매가의 값 또는 `null`을 보존한다. `basis_count`는 1~1,000,000,000의 정수이며 직접 1개분 입력은 1이다. 배치 레시피는 구성 수량을 먼저 나누어 잘라 저장하지 않는다. 가상 3개분에 100g이면 분자 `"100"`, 분모/기준 개수 `"3"`을 저장하고 메뉴 1개분은 정확히 `100/3g`이다. 화면의 근삿값은 이 분수를 대체하지 않는다. API/JSON에는 분자 수량과 정수 분모를 십진 문자열로 전달한다.

각 행 원가는 `단가 금액 정수 × 구성 분자 수량 정수 / (단가 기준 수량 정수 × basis_count)`를 한 번 계산해 micro원으로 반올림한다. 두 곱의 중간값은 위 범위에서 `i128` 안에 있으며 합계도 검사한다. 서로 다른 단가 분모를 연쇄 곱하지 않는다. 예를 들어 10원/g과 3개분100g은 1개 행 원가333.333333원이다. 실제 생산 투입·입고·실사에는 이 분수를 자동 차감하지 않고 별도로 입력한 6자리 고정소수의 실측 수량을 쓴다. 당시 판매는 이 `basis_count`와 구성 분자까지 포함한 레시피 버전을 고정 참조한다.

같은 품목을 여러 행으로 참조해도 소모 대상 메뉴 판정은 한 번만 한다. 구성은 원물·손질분·비축품을 직접 선택하며 순환 참조는 오류로 반환한다. 비축품을 참조한 메뉴의 원가에는 그 비축품 단가만 적용하고 하위 재료를 다시 합산하지 않는다.

판매는 등록 시점의 메뉴/레시피/판매가 버전, 개수, 원가 계산 출처와 결과, 판매금액, 서버 입력 시각을 저장한다. 판매가가 있으면 판매금액은 그 값×개수이며 0원도 유효하다. 판매가가 없으면 판매금액은 `null`로 저장하고 금액 합계에서 알려진 소계와 미계산 판매 건수를 구분한다. 이를 확정된 전체 판매금액 0원으로 처리하지 않는다. 일반적인 레시피 수정으로 이미 등록된 판매의 참조를 바꾸지 않는다. 아카이브는 신규 선택 목록의 기본 노출을 바꾸지만 과거 참조·복원 가능성은 유지한다.

## 4. 가격·보유 가치

계산에 사용할 가격은 다음 순서로 선택하고 `source_kind`, 원기록/버전 ID, 분자/분모를 반환한다.

1. `Q > 0`이고 가치가 확인되었으면 현재 보유 평균 `V/Q`. `V == 0`도 유효하다.
2. `Q == 0`이면 가장 최근에 유효했던 보유 평균 단가. 전량 소모/반품/폐기 직전의 유효 비율을 마지막 단가로 남긴다.
3. 유효한 입출고/보유 단가 이력이 없으면 최근 사전 등록 가격의 `금액/기준 수량`.
4. 모두 없으면 가격 없음. 0원은 없음을 의미하지 않는다.

사전 가격은 품목·금액·양의 기준 수량·등록 시각을 가진 독립 버전이다. 가격 등록은 `Q`, `V`를 바꾸지 않는다. 보유량이 양수인데 가치가 미확인이라면 사전 가격으로 몰래 대체하지 않고 가치 확인이 필요한 상태를 반환한다. 실제 입고금액·확인한 시작 가치·확인한 초과 조정이 보유 가치를 만든다.

일반 입고 `q`, 금액 `a`는 `Q' = Q + q`, `V' = V + a`다. 입고일은 별도 업무 정보이며 정산 순서는 입력 확정 `seq`다. 발주·발주 취소는 수량/가치를 바꾸지 않고, 한 번의 실제 입고로 원주문량·실입고량·차이를 보존하고 주문을 종료한다.

## 5. 실사 구간과 확정 순서

### 관측 기준과 정산

품목별 실사는 독립된 경계를 가진다. 직전 해당 품목 경계 `B.seq` 뒤부터 이번 실사 확정 직전까지의 유효 사건으로 다음을 계산한다.

`Q = B.수량 + 확정 입고 + 생산 유입 - 생산 투입 - 반품 - 명시 폐기`

`C = Q - M`

판매·발주·임시 저장·레시피 편집·이미 확정한 이전 구간 소모는 이 식에서 다시 빼지 않는다. `C > 0`이면 정상 소모를 확정하고 `K = V × C/Q`를 차감하여 새 기준은 `M`, 새 가치는 `V-K`다. `C == 0`이면 소모 0인 실사를 보존한다. `M > Q`이면 소모를 음수로 만들지 않고 누락 입고/생산/오입력을 확인한 뒤 초과 조정으로 처리한다.

초과 `E=M-Q`는 사용 가능한 기존 단가×`E`로 가치를 더한다. 적용 가능한 단가가 없으면 초과분 금액을 사용자에게 확인한다. 기존 단가의 출처, 확인한 금액 및 이유를 실사에 남긴다. 실사 소모를 자동 폐기로 만들지 않는다.

### 첫 실사와 미확인

- `observation_id == null`과 수량 0은 다르다. 빈 실사 입력은 미확인으로 제외하며, `"0"`은 확인한 0이다.
- 이전 실사가 없어도 알려진 시작 수량/가치 또는 확정 입고/생산으로 만든 시작 기준이 있으면 그 기준부터 정산한다. 시작 근거 `baseline_id/seq`를 기록한다.
- 시작 수량을 알 수 없으면 이번 `M`과 가치를 확인해 시작 기준을 만든다. 기존 단가를 적용했다면 출처와 확인을 남긴다. 그 이전 판매로 소모를 역산하지 않고 소모 미확정 상태를 보존한다.
- 알려진 시작 기준이 없는 품목에서 단가 등록이나 재료 등록만으로 초기 수량 0을 확정하지 않는다.
- 여러 품목을 한 화면에서 실사해도 행별 직전 기준·소모 구간을 사용한다. 입력하지 않은 품목의 경계는 움직이지 않는다.

### 입력 중 상태 변경

미리보기 응답은 `epoch`, `revision`, 참조 버전, 품목별 직전 실사, 정산 기준, 소모/초과, 배분, 가치 전후를 포함한다. 확정 요청은 같은 값과 요청 UUID를 보낸다. 저장 mutex/트랜잭션 안에서 세대·개정 번호를 다시 비교하고 달라졌으면 409로 새 미리보기를 요구한다. 사용자가 확인한 숫자와 다른 결과를 조용히 저장하지 않는다.

전역 개정 번호는 단일 사용자·복수 탭에서 보수적으로 모든 영속 변경마다 증가한다. 같은 밀리초라도 `seq`가 순서를 정한다. 실사 판매 대상은 `(직전 해당 품목 기준 seq, 이번 실사 seq)`의 열린 구간이다. 실사보다 먼저 확정된 판매는 포함되고 뒤에 확정된 판매는 다음 구간이다. 미리보기 이후 새로운 판매가 있으면 재확인을 요구한다. 날짜별 마감 잠금·영업일 재개방은 도입하지 않는다.

## 6. 판매 소모 배분

대상은 해당 실사 구간에 등록된 유효 판매 중 당시 레시피가 그 품목을 **직접 참조**한 판매다. 레시피 구성 수량 0도 대상이다. 비축품의 하위 원물은 메뉴가 직접 참조하지 않았다면 대상이 아니다. 이미 생산 투입으로 처리한 원물을 메뉴 판매에 다시 배분하지 않는다.

각 판매 행의 가중치 `w`는 판매 개수이며 총합 `W`로 `C×w/W`, `K×w/W`를 배분한다. 레시피 사용량·판매가·판매금액을 가중치로 쓰지 않는다. 원본 판매 ID, 당시 버전, 실사 ID, 구간 경계, 가중치, 배분 순서를 저장한다. 메뉴별 화면은 이 행을 합산한다.

대상이 없거나 `W==0`이면 `C`, `K` 전부를 미배분 소모로 보존한다. 배분 결과는 메뉴별 실제 계량값이 아니며, 당시 레시피 기준 원가와 실사 배분 원가를 별도 필드·표시로 유지한다. 판매 직접 선택은 T-030 백로그다.

## 7. 생산·명시 폐기·반품

| 확정 사건 | 수량과 가치 변화 |
| --- | --- |
| 생산 투입 | 투입 품목별 `q` 차감, 평균에 따른 `a` 차감. 전량이면 남은 `V` 전부 |
| 생산 결과물 | 실제 결과 수량 추가. 투입 가치 합계를 결과물 배분율로 나누어 추가 |
| 명시 폐기 `0 < q < Q` | `Q-q`, `V` 유지. 남은 수량의 평균 단가 상승 |
| 명시 폐기 `q == Q` | 수량·가치 0, 이전 `V`는 별도 전량 폐기 손실 |
| 반품 | `Q-q`, `V-현재 평균 원가(q)`. 원구입금액은 참고금액으로 보존 |

생산의 주 결과물 배분율은 100%, 나머지는 0%로 시작하고 사용자가 수정할 수 있다. 결과 수량은 양수, 배분율 합계는 100%다. 투입 차감·결과 추가·배분·JSON은 하나의 확정 요청이다. 모든 결과의 원가가 0이어도 유효하며 기준 수율은 계산하지 않는다.

판매에 근거한 예상 부족으로 생산/판매를 차단하지 않는다. 다만 실제 투입·반품·폐기 수량이 현재 정산 기준을 넘으면 음수 가치·임의 축소를 만들 수 없다. 요청은 입력을 유지한 채 `needs_reconciliation`로 안내하고 실제 누락 입고·시작 기준·실사 또는 원기록 정정으로 기준을 확인한다. 보정 참조와 새로운 `revision`에서 다시 미리보기한 뒤 확정한다. 가상 재고를 몰래 만들거나 기존 부족 금지 정책을 일반 판매에 재도입하지 않는다. T-008은 가상 보정 결과로 계약을 검증하고 실제 실사/정정 연결은 T-010·T-012에서 완성한다.

## 8. 지연 입고의 수량·금액 보정

### 포함 수량과 중복 방지

사용자가 실사/시작 기준, 그 기준에 이미 포함된 입고 수량 `I`를 선택·확인한다. 실제 입고 `R` 중 `0 <= I <= R`, 현재 새로 추가할 수량은 `U=R-I`다. 이 확인은 입고일에서 자동 추정하지 않는다.

선택한 관측에서 포함분에 이미 계상한 가치 `Bv`와 출처를 연결한다. 초과 조정에서 생긴 수량이면 해당 조정의 미연결 수량/가치에서 배분하고, 확인한 시작 기준에 포함되었다면 그 기준의 확인 가치에서 배분한다. **초과가 없는 정상 실사도 선택할 수 있다.** 이 경우 사용자가 그 관측의 기존 잔량 중 포함 수량을 확인하고 관측 당시 보유 가치/수량 비율로 해당 몫 `Bv`를 계산한다. 초과 조정이나 시작 기준에서 특정한 몫과 정상 실사의 같은 몫을 동시에 중복 선택하지 않는다.

관측마다 새 연결 가능 수량을 만드는 대신, 선택된 수량 몫에 영구 연결 ID와 원래 관측/잔량의 근거 ID를 준다. 후속 관측은 이전 근거의 살아 있는 몫을 이어받으며 이미 연결한 몫을 새 미연결 수량으로 초기화하지 않는다. 수량 감소/생산 이전은 같은 평균 비율로 연결 몫을 분할해 이어가고 최소 단위 잔여는 §2 순서를 따른다. 새 확정 유입/초과분만 새 근거를 만든다. 원래 관측에서 사용한 연결 한도는 이후 소모되어도 반환하지 않는다. 이는 중복 연결을 막는 계산용 근거이며 실물 로트·선입선출 정책이 아니다.

T-011의 내부 출처 지분은 정확 유리수로 유지한다. 생산의 권리 분할은 같은 기준 단위군 안에서 실제 수량 비례, 서로 다른 단위군 사이에서 균등한 무차원 비율을 사용한다. 원가 배분율과 별개이므로0%·0원 결과물의 출처도 보존한다. 이는 서로 다른 단위의 물리 배합을 추정한 값이 아니며 실제 생산 수량·원가 계산을 바꾸지 않는다. 선택 관측의 미연결 몫 전체 또는 특정 원천을 명시할 수 있고, 최소 수량보다 작은 여러 원천 몫은 묶음 선택한 뒤 서버가 원천별 영구 연결로 나눈다. 후속 고정 예약까지 확인한 가능량을 사용하며 이전 연결을 자동 재분배하지 않는다. 구체적 타입·반례는 [T-011 계획](tickets/T-011-plan.md)에 둔다.

여러 근거를 잇는 경우 행을 나누어 선택하고 원본 근거의 예약 수량 합계와 현재 선택 관측의 살아 있는 몫을 모두 검사한다. 하나의 출처 수량을 두 입고에서 중복 점유할 수 없다. 수량/가치가 없는 관측, 유효 버전이 달라진 근거, 이미 전부 연결된 몫은 입력을 보존하고 다시 확인한다. 사용자가 확인하지 않은 실물 사용·입고 내역을 역산해서 새 소모/판매 배분을 만들지 않는다.

입고금액 `A`를 `I:U`로 나눈 금액 `Ai`, `Au`는 합계 `A`를 보존한다. 포함분의 가격 차액은 `D=Ai-Bv`다. `U`와 `Au`는 현재 시점 일반 입고로 한 번 추가하고, 포함분에는 수량을 추가하지 않는다. 관련 기준·입고·이미 연결한 수량/가치·정정 버전과 요청 UUID를 영구 연결한다.

같은 관측의 포함분을 여러 행이나 여러 확정으로 나누어도 Bv를 행마다 독립 반올림해 중복 계상하지 않는다. 각 선택의 고정 가치 근거를 정확히 합한 누적 Bv를 한 번 반올림하고 이전 확정 Bv를 뺀 잔여를 이번 선택에 최대 잔여 배분한다. 직접 초과·일반 잔량을 섞어 선택한 경우도 같은 관측의 가치 잔여를 보존한다. 기존 확정 Bv와 근거 비율을 수정하지 않는다.

### 현재 보유 가치와 별도 보정

이미 포함된 기준 이후에 소모·생산·폐기가 있으면 차액 전부를 현재 원재료에 얹을 수 없다. 현재 확정 원장을 복사해 **가치 계산만** 비교한다.

1. 선택한 기준의 해당 포함분 잠정 가치 `Bv`를 실제 금액 `Ai`로 치환하는 계산용 가정을 만든다.
2. 이후 확정 사건의 수량·순서·생산 배분율·실사 확정 소모를 그대로 두고 이 문서의 평균·잔여·폐기 규칙으로 가치 흐름을 다시 계산한다. 생산이 있으면 그 결과물과 후속 생산까지 따라간다. 판매는 가치 흐름을 바꾸지 않는다.
3. 현재 남아 있는 품목별 가치와 계산용 가치의 차이 `dV`를 산출한다. `D - ΣdV`는 이미 소모·반품·전량 폐기 등으로 남아 있지 않은 부분의 별도 금액 보정이다. 해당 원기록을 참조하되 과거 판매/소모 원가를 덮어쓰지 않는다.
4. 현재 입고의 순증 가치는 `Au + ΣdV`, 별도 보정은 `D-ΣdV`이며 합계는 `A-Bv`다. 모든 현재 수량은 `U`만 증가하고 생산 결과물 수량은 바뀌지 않는다. 미리보기로 품목별 가치와 별도 보정 전후를 확인받아 현재 시점에 한 번 확정한다.

이는 실제 입고일로 과거 판매·원가를 소급 수정하는 기능이 아니다. 기존 원가·배분은 유지하고 현재 보정 내역에만 계산용 전후와 출처를 보관한다. 과거 소모 원가와 현재 보정을 화면에서 합쳐 과거가 수정된 것처럼 표시하지 않는다.

계산에는 이미 적용한 지연 입고/정정의 유효 버전만 한 번 포함한다. 같은 포함분을 다시 처리하거나 수정된 실사 버전을 참조한 미리보기는 충돌로 반환한다. 0원 입고는 음의 차액이 가능하지만 보정 후 각 보유 가치가 음수가 되면 확정하지 않고 근거/이전 정정을 확인한다. 마지막 수량 0인 품목에는 가치를 남기지 않고 별도 보정으로 보존한다. 지연 입고 자체로 과거 판매 대상·총소모를 다시 배분하지 않는다.

## 9. 정정·재실사·임시 기록

모든 확정 사건에는 원본 ID와 현재 유효 개정 ID가 있다. 정정은 원본·직전 개정·이유·변경 전후·영향 미리보기·대상 기준을 참조하는 새 사건이다. 같은 정정 요청 UUID는 한 번만 실행한다. 원본 행을 삭제하거나 역변동만 무조건 현재에 더하지 않는다.

- **판매 개수 정정:** 실사 전이면 해당 구간의 배분 가중치를 바꾼다. 실사 후이면 그 실사의 확정 `C`, `K`, 현재 `Q`, `V`를 유지한 채 메뉴별 배분/미배분의 새 버전만 만든다. 전부 취소되어 대상이 없어지면 미배분으로 이동한다. 고객 환불·실물 반환을 만들지 않는다.
- **일반 레시피 수정:** 이후 등록하는 판매부터 새 버전을 사용한다. 판매 오입력 정정에서도 당시 참조 버전을 기본으로 유지하며 최신 레시피로 전체 과거 판매를 재계산하지 않는다.
- **입고/생산/폐기/반품 정정:** 원본 입력 위치에서 유효 개정만 바꾼 계산용 원장을 만들고 후속 실사·생산·지연 입고의 영향 경로를 비교한다. 이미 실사한 실제 수량은 그대로 유지한다. 후속 관측이 없는 마지막 구간은 정정 수량 차이를 현재 정산 기준에 반영하고, 관측이 있는 구간은 소모/초과와 가치 보정을 새 개정으로 연결한다.
- **실사 정정:** 해당 품목의 그 관측 수량을 고친 계산용 원장에서 해당 구간과 다음 관측까지 영향을 계산한다. 다음 실사가 확인한 수량은 바꾸지 않는다. 그 뒤의 가치 영향은 필요한 만큼 후속 생산·실사 경로로 전파한다. 이전 소모·배분과 새 소모·배분을 모두 보존한다.
- **지연 입고와 정정의 결합:** 같은 원본/포함 수량 연결의 유효 개정을 대체하여 계산한다. 원래 지연 입고 차액과 새 정정 차액을 모두 누적하지 않는다. 포함 수량 한도가 줄거나 연결이 사라지면 영향받는 입고 연결을 함께 해소해야 하며 조용히 잘라내지 않는다.

정정 미리보기에는 영향받는 원기록, 품목별 수량·가치, 실사별 소모·배분, 별도 보정 전후와 경고를 담는다. 새로 음수 수량/가치·잘못된 참조·범위 초과가 생기면 입력과 기존 상태를 보존하고 관련 누락 기록/관측을 먼저 확인한다. 정정은 현재 확정 기록으로 남지만 원본의 계산 위치와 실제 새 입력 시각을 함께 보존한다. 통계는 원본 기준·현재 유효 정정 결과를 구별한다.

재실사는 직전 **유효 관측**과 그 뒤의 사건부터 시작한다. 이전 구간의 소모/정정/지연 입고 수량을 새 구간 입고나 소모로 다시 더하지 않는다. 임시 기록은 독립 ID/버전으로 저장하고 JSON에 포함한다. 임시 저장·수정·폐기에는 원가 영향이 없고 확정 전환만 업무 효과를 한 번 만든다. 저장이 불확실하면 같은 요청으로 재시도한다.

참조는 UUID와 버전/개정 ID로 검증한다. API 입력의 이름·상태 문자열을 그대로 신뢰하여 참조를 만들지 않는다. 미리보기는 저장 효과가 없고 확정 시 같은 계산 함수를 다시 호출한다. 계산 함수는 단위/정수·가격·배분·원장 비교를 다루고 파일/HTTP에 의존하지 않는다. 저장 계층은 기존 단일 작성자 잠금·트랜잭션·마이그레이션·outbox를 재사용한다. HTTP의 세션·Host/Origin·종료 처리는 유지한다.

### DB v2 → 확장 스키마

1. 기존 v2의 `materials`, `creation_requests`, `snapshot_outbox`를 그대로 읽는 fixture를 보존한다. 기존 `id`, 이름, 단위, 생성 시각, 요청 UUID와 원본 JSON 바이트를 유지한다.
2. 다음 스키마부터 순차 마이그레이션으로 품목 버전/가격, 업무/정산, 자산/복원 관계를 추가한다. 기존 재료는 같은 UUID의 초기 품목 버전으로 연결한다. 기존 자료에는 수량·가격 이력이 없으므로 시작 기준과 가격은 미확인/없음으로 두고 재고 0·0원으로 추정하지 않는다.
3. g/kg·mL/L은 기준/표시 단위를 분리하고 나머지는 원래 자유 단위를 유지한다. 과거 단위 문자열·이름 중복은 보존한다. 스키마 마이그레이션만으로 입고·실사·판매를 만들지 않는다.
4. 기존 요청의 재시도는 기존 재료 ID를 반환한다. 새 공통 요청 기록으로 옮기더라도 기존 입력 비교 의미를 보존한다. 동일 UUID·다른 명령/입력은 409다.
5. 현재처럼 변경 전 SQLite 백업, 한 트랜잭션의 순차 변환·참조/무결성 검사, 실패 시 원본 유지, 미래 버전 쓰기 전 거절을 적용한다. 각 스키마 변경 티켓에서 직전 버전 fixture와 실패 사례를 추가한다.

### JSON v1 → 확장 형식과 복원

기존 v1은 재료 전체 상태만 담는다. 새 형식 v2는 `format_version`, `schema_version`, `sequence`, `request_id`, `recorded_at`와 숫자 문자열 계약을 포함하고, `state`에 품목/모든 버전·가격·레시피·업무/정정·관측/배분·임시 기록·사진 참조·구입처를 담는다. 형식 버전과 DB 스키마 버전을 구분한다.

읽기는 v1/v2를 명시적으로 분기한다. v1의 재료는 위와 같이 확장 상태로 변환하되 없던 업무·가격·사진은 빈 상태, 재고 기준은 미확인이다. 과거 원문은 바꾸지 않고, 변환 결과를 복원할 때 새 형식의 새 기록을 만든다. 미래 형식·중복 ID·깨진 참조·잘못된 숫자·자산 경로 이탈·불일치한 수량/가치는 쓰기 전에 거절한다. 알 수 없는 업무 종류를 무시해서 부분 복원하지 않는다.

모든 영속 변경은 상태+요청+전체 스냅샷 원문을 한 DB 트랜잭션에 보존하고 JSON 발행 성공 후에 성공 응답한다. 미해결 발행은 후속 변경 전에 해결하며 기존 파일 불일치는 덮어쓰지 않는다. 전체 상태 스냅샷으로 저장량과 검사 시간이 늘어나는 비용은 T-021에서 가상 누적 자료로 측정한다. 검증 없이 기존 모든 기록 검사나 무기한 보존을 생략하지 않는다.

복원은 선택 지점의 전체 업무 상태를 대상으로 하며 이전/이후 원본 JSON·불변 자산·요청 재실행 방지 기록은 보존 기록으로 남는다. 현재 활성 상태에서 빠진 이력이 보존 기록까지 삭제된다는 뜻이 아니다. 복원 직전 상태 보존과 복원 자체를 새 seq로 기록하고 `epoch`를 바꾼다. 옛 epoch의 새 확정 요청은 거절한다. 옛 요청 재시도는 과거 처리 결과와 현재 상태에서의 유효 여부를 반환하거나 상태 갱신을 요구하며 업무를 재적용하지 않는다. 요청/스냅샷의 순번을 선택 시점으로 되감지 않는다. 사진은 해시 등 상대 키로 찾고 과거 복원 지점이 참조하는 자산을 삭제하지 않는다.

수계산의 핵심 등식은 `시작 가치 + 새로 반영한 입고 가치 + 확인한 초과 가치 + 가치 보정 = 현재 보유 가치 + 소모 가치 + 반품 가치 + 전량 폐기 손실 + 별도 보정`이다. 지연 입고는 이미 계상한 Bv를 다시 유입으로 더하지 않고 미포함 금액 Au와 차액 D만 왼쪽에 반영한다. 실제 구입금액 A와 정산에 새로 반영한 가치를 구별한다. 특히 S21의 알 수 없던 과거 사용은 이 보정으로 새 소모 기록을 추정하지 않는다. 생산은 품목 간 이동이므로 전체 합계에서 상쇄한다. 사전 가격·판매·발주는 어느 항에도 보유 가치로 더하지 않는다. 부분 폐기는 수량만 줄이고 가치 차감 항을 만들지 않는다.

T-020은 공통 탐색·테마·반응형·입력/오류/재시도 표현을 제공한다. T-014는 기존 확정 명령을 모아 입력하는 화면이며 별도 마감 원장을 만들지 않는다. T-015는 사진·구입처, T-016·T-017은 위의 구분을 유지하는 조회·통계·개요다. T-018은 실제 전체 복원, T-019는 이전 자료·같은 OS 이동, T-021은 업무 통합·복구·누적 기록 비용과 배포 준비를 검증한다.

후속 구현에서는 계산 모듈(단위/정수·배분·가격·원장 비교), 저장 모듈(마이그레이션·업무 트랜잭션·snapshot), 얇은 API, 기존 Nuxt 화면/입력 composable의 경계를 활용한다. 현재 `store.rs`와 `server.rs`에 모든 업무 계산을 몰아넣거나 새로운 서버·다중 사용자 프레임워크를 추가하지 않는다. 대용량 사진/일괄 업무는 기존 API 16KiB 제한을 검토하고 용도별 제한·검증을 구현한다.

## 13. 검토 상태

T-002의 8개 기준을 §12와 가상 사례 S01~S22에 대조해 설계 검토를 완료했다. 독립 검토에서 발견한 0 수량 입고, 정상 실사의 지연 입고 연결, 여러 단가 분모의 중간 계산 문제를 보완하고 재검토했다. 수계산은 정수/정확한 분수로 별도 대조했다. 실행 근거와 RTD 결과는 [T-002](tickets/T-002-domain-contract.md)에 기록한다.

이 완료 판단은 설계 범위다. 실제 앱 계산·DB 변환·JSON 복원·사진·브라우저 시연은 각 후속 티켓에서 검증한다. 연결 기획 노트에는 같은 날짜와 C-/D- 식별자로 설계 결과를 추가했으며 기존 내용과 변경을 보존했다. T-001의 실환경 미검증과 T-021의 통합·실제 시연은 남아 있다.
