# ADR-009: 전체 상태 복원과 보존 요청 원장

- 상태: 채택 — T-018 구현·검증 완료
- 결정일: 2026-10-25
- 관련: D-11~D-13, [T-018](../tickets/T-018-full-state-restore.md)
- 근거: 기존 전체 복원·무기한 기록·사진 보존 요구와 위임받은 구현 설계. ADR-007의 운영·원가 정책은 유지한다.

## 문제와 제약

선택 JSON에는 전체 업무 상태가 있지만 각 과거 순번의 JSON 원문이 재귀적으로 들어 있지는 않다. 기존 업무 FK가 원문 outbox를 직접 참조하는 상태에서 과거 JSON 하나를 수입하면, 존재하지 않는 과거 원문을 만들거나 활성 업무와 보존 이력을 섞게 된다. 복원 후 현재 품목에서 빠진 요청도 다시 실행하면 안 된다.

마지막 outbox만 직전 상태로 지정하는 방식은 기록이 없는 초기 상태와 DB 마이그레이션으로 구조가 확장된 직후 상태를 완전히 보존하지 못한다. 사진도 현재 연결과 과거 등록 사실을 구분해야 한다.

## 검토한 선택지

- 여러 DB 파일·세대 manifest를 교체하는 방법은 파일 전환과 열린 연결·재시작 복구 경계를 추가한다.
- 선택 자료를 기존 활성 업무와 병합하거나 과거 명령을 재실행하면 전체 상태 복원과 원본 보존 요구를 어긴다.
- 단일 SQLite에서 활성 관계와 순번·원문·요청·자산 보존 관계를 나누면 기존 원자 저장과 발행 복구를 유지할 수 있다.

## 결정

스키마15는 세 번째 방법을 사용한다. 기존 outbox를 순번 anchor로 이동하고 실제 원문을 별도 outbox에 원 bytes 그대로 보존한다. 원 FK는 순번 anchor를 참조한다. 가져온 과거 순번에는 가짜 원문을 만들지 않으며 새 변경 순번은 모든 보존/선택 순번보다 크다.

활성57관계는 선택 자료로 전건 교체한다. 전역 요청 원장·복원 결과·등록 사진과 JSON 대상은 별도로 보존한다. JSON v2/schema15도 활성 상태와 이 구조화 보존 metadata를 나누어 담되 원문을 재귀적으로 포함하지 않는다. 모든 사진·구입처·초안·버전·정정·배분을 포함하고 일부 품목만 병합하지 않는다.

직전 실제 전체 상태를 `before_restore` 목적의 불변 JSON으로 먼저 보존한다. 원 revision0도 허용하며 과거 변경 원문으로 위장하지 않는다. 이후 복원 자체는 새 순번·새 epoch의 변경 기록이다. 원 요청, 복원 결과, 활성 상태, 새 JSON을 한 SQLite 트랜잭션에 넣고 JSON 발행 뒤 성공을 알린다. commit 후 발행 실패는 같은 요청으로 복구한다.

원 JSON은 스키마별 닫힌 reader로 검증한다. v1에서 없던 업무·가격·요청을 추정하지 않는다. 필요한 초기 버전/기술 epoch는 원문 hash와 품목 UUID로 결정적으로 파생한 UUIDv8이며 원래 사건의 ID라고 설명하지 않는다. 실제 복원 epoch는 새 UUID다. 수입 사전 검증은 writer 잠금 아래 SAVEPOINT에서 전체 역변환·FK·readback을 확인한 뒤 항상 rollback하며, 이 단계의 상태를 commit하거나 파일로 발행하지 않는다.

동일 UUID의 다른 명령·입력·원응답은 충돌이다. 같은 세대의 revision 충돌과 복원에 따른 세대 변경을 구분한다. 세대 변경은 이미 처리된 원요청인지 미처리인지 알리고 과거 업무를 재적용하지 않는다. 새 metadata가 없는 legacy 등록은 첫 복원 이후 새 요청을 거절하고 현재 상태 확인을 요구한다. 기존 응답과 원입력은 보존한다.

JSON 대상은 서버의 순번/해시 ID로 선택하고 임의 경로·URL·ZIP을 받지 않는다. 수입은 원 bytes64MiB·60초·동시1개로 제한한다. 중복 JSON key·미래 형식·깨진 참조·수량/가치 불일치를 거절한다. 앱 소유 열린 디렉터리와 no-follow 접근, hash·길이 검증·덮어쓰기 없는 발행을 사용한다. 전체 등록 사진의 누락·손상·실제 decode를 확인하고 빠진 참조를 제거한 부분 복원을 하지 않는다.

## 영향과 되돌리는 조건

새 스키마는 이전 실행 파일에서 열 수 없다. 마이그레이션 전 일관된 백업을 만들며 실패 시 원 DB를 보존한다. 이전 앱으로 돌아갈 때는 정상 종료한 호환 DB 사본이 필요하다. 활성 상태를 되돌리는 일은 보존된 직전 지점을 정상 복원 경로로 선택한다.

보존 원장과 직전 상태 파일 때문에 저장량이 증가한다. 자동 삭제를 추가하지 않으며 누적 자료 비용은 T-021에서 측정한다. 브라우저는 원입력·미확인 요청을 보존하고 새 기준을 자동 대입해 재전송하지 않는다. 다른 장비·절전·실제 전원 차단 검증은 로컬 합성 시험과 구분한다.

정확한 API·화면·검증 범위는 [T-018 설계](../tickets/T-018-plan.md), 실행 근거와 남은 항목은 [검증 기록](../tickets/T-018-verification.md)을 따른다. 이 결정의 채택은 구현 또는 배포 검증 완료를 뜻하지 않는다.
