# ADR-002: 개발 단계와 로컬 저장·배포 방향

- 상태: 일부 대체 — 손질 수율 선택·날짜별 마감·파일 위치와 후속 운영 정책은 [ADR-003](ADR-003-inventory-events-and-portable-data.md)을 따른다. 아래는 당시 결정 이력이다.
- 결정일: 2026-10-24
- 관련 요구사항: C-01~C-03, D-01~D-03, D-06~D-09, D-11~D-13

2026-10-24 후속 결정으로 DB·JSON·사진을 모두 바이너리 옆 `db/` 폴더에 두고 입력 시점별 운영을 채택했다. 아래의 직접 인접 저장·수율 선택·날짜별 마감 내용을 현행 구현 기준으로 적용하지 않는다. 개발 단계와 SQLite·서버 이관 방향은 유지한다.

## 배경과 선택지

요구사항과 화면 초안을 검토한 뒤 사용자가 개발 우선순위, 주방 재고 범위, 하루 마감과 초기 운영 방식을 정했다. 이전에는 파일 중심 운영, 외부 웹 호스팅, NAS 구성 등이 후보였으나 초기 제품은 로컬 설치형으로 진행한다.

## 결정

1. 1차는 레시피·식재료 원가·발주·입고·판매·재고다. 내일 메뉴 계획·작업시간은 2차, 시설 점검은 백로그다.
2. 원물 → 손질 → 비축메뉴 → 판매메뉴로 업무를 구분한다. 판매 전 주방의 식재료·음식을 재고로 관리하며 미리 만든 음식의 생산량과 잔량을 포함한다.
3. 손질은 실측 투입량·완성량 입력과 기준 수율 계산을 사용자가 선택할 수 있게 한다. 메뉴 등록 시 원물·손질분을 확인해 선택한다.
4. 하루 마감에 메뉴별 판매 합계를 입력하고 재고를 맞춘다. 메뉴 이외 임의소진을 지원하며 직원식은 현재 폐기로 취급한다.
5. 웹 UI 기반 설치형 앱을 단일 바이너리로 배포한다. 기본 데이터는 로컬 SQLite에 저장하고 JSON 파일로 백업한다. DB 파일과 JSON 백업 파일은 실행 바이너리와 같은 폴더에 보관한다.
6. 안정화 후 별도 서버를 마련해 데이터와 서비스를 이관한다.
7. 기존 Figma는 레이아웃 참고안이다. 현재 기획은 대체로 적절하다는 평가지만 최종 GUI가 아니며, 기능 요구사항 정리 후 전체 재설계할 수 있다.
8. 중대한 요구사항 변경은 레포 문서와 연결된 기획 노트에 함께 반영한다. 공개 문서에는 운영 자료·비공개 링크·개인 경로를 포함하지 않는다.

## 2026-10-24 추가 결정: 파일 보관 위치

사용자가 SQLite DB 파일과 JSON 백업 파일을 바이너리 옆에 함께 보관하도록 정했다(D-11, D-13). 기준 경로는 실행 바이너리가 있는 디렉터리이며, 실행 당시 작업 디렉터리에 따라 저장 위치가 달라지지 않도록 한다. 파일명·백업 주기·보존 기간·사진 저장 방식은 이번 결정에 포함하지 않는다.

## 영향과 남은 판단

생산·판매·임의소진·실사 조정을 연결할 때 같은 재고를 두 번 차감하지 않아야 한다. 단계별 품목 ID, 차감 시점, 정정·마감 정책과 수율 입력 세부 규칙은 아직 정하지 않았다.

언어·프레임워크, 대상 OS·아키텍처, UI 실행 방식, 사진 저장, 기기 간 공유, 로컬 인증·잠금, 백업 주기·형식 세부·복원 검증은 미정이다. 단일 바이너리가 여러 OS 공통 실행 파일이나 자동 동기화를 의미하지 않는다.

서버 전환 시점과 환경도 미정이다. 앱·DB·백업 구현이 완료된 것으로 해석하지 않는다.

## 재검토 조건

실제 주방 입력 부담, 기기 간 공유 필요, 설치 제약 또는 서버 전환 필요성이 구체화되면 별도 결정으로 수정한다. 기존 결정을 삭제하지 않고 대체 관계를 남긴다.
