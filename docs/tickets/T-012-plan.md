# T-012 구현 계획과 RTD Before

- 작성일: 2026-10-25
- 상태: 설계·구현·수용 검증과 RTD 완료. 최종 근거는 [검증 기록](T-012-verification.md)에 보존
- 기준: [티켓](T-012-corrections-and-versions.md), [계산 계약 §9](../DOMAIN-CONTRACT.md#9-정정재실사임시-기록), [요구사항](../REQUIREMENTS.md), [ADR-007](../decisions/ADR-007-consumption-and-ticket-scope.md)
- 선행: T-009 판매·T-010 실사/폐기·T-011 포함 입고 구현·검증. T-010의 실제 반품 연결은 T-013에서 확인한다.

## 목적과 범위

입고·생산·판매·폐기·실사의 오입력을 원본 삭제 없이 취소하거나 대체하고 영향을 미리 보여준다. 일반 레시피 수정은 이후 판매에만 적용한다. 판매 개수 정정은 실물 반환을 만들지 않고 확정 소모의 메뉴별 배분만 바꾼다. 물리 수량 사건의 정정은 원래 계산 위치에서 유효 입력을 바꾸되 후속 실제 관측 수량을 유지한다.

기존 가격·판매 정정의 요청/응답, 아카이브된 품목의 과거 참조와 전체 JSON 원문을 보존한다. T-013 반품 writer, 고객 환불, 과거 레시피의 자동 일괄 적용, 기록 삭제, 전체 자료 이관은 추가하지 않는다. 새 운영정책 질문을 선행 조건으로 만들지 않으며 기술 선택은 위임된 범위에서 결정한다.

## 입력·화면 계약

기존 business 초안→수정→미리보기→확정 경로에 닫힌 `correction`/version1을 추가한다. 바깥 `corrects_confirmation_id`는 원사건의 최초 확정 ID를 가리키며 대상 권위는 하나다. 입력의 `expected_target_version_id`는 편집 시작 당시 유효 개정의 비교 기준이며 대상 ID를 중복 정의하지 않는다. 한 정정 확정이 원사건과 연계 입고를 함께 바꿔도 사건마다 별도 유효 개정 ID를 유지한다. 기존 가격·판매 V1의 정정 연결은 그대로 보존한다.

입력은 이유, 취소 또는 종류별 대체 입력, 필요한 후속 관측 확인과 포함 입고 연결의 명시 개정이다. 임의 JSON patch나 중첩 정정 업무를 입력하지 않는다. 판매 대체는 개수이며 당시 품목·레시피·판매가·단가는 서버가 보존한다. 실사 대체는 stable 관측 ID와 현재 버전을 지정한 행별 대체/취소이며 생략한 행은 유지한다. 비어 있는 수량을 취소나 0으로 해석하지 않는다. 연계 입고는 실제 영향받은 입고 ID와 현재 유효 개정 ID를 확인하여 기존 입고 입력 전체를 대체하거나 취소한다.

전체 실사를 취소한 뒤 다시 대체할 수 있도록 조회 응답에 편집용 `replacement_template`을 원본/현재 입력과 별도로 둔다. 원입력 값은 유지하고 stable 관측별 현재 실제 개정 또는 취소 효과 ID만 편집 기준으로 연결한다. 원본 증거나 저장된 전송 본문을 이 템플릿으로 덮지 않는다. 통합 정정 이력이 있는 판매의 새 구형 개수 정정은 통합 정정 경로로 안내하되 이미 저장한 같은 UUID는 당시 원응답을 계속 재생한다.

정정 초안을 위한 조회는 대상의 원본·현재 유효 개정·편집 시작값·관련 기록과 상태를 구분해 반환한다. `/api/business/confirmations/{id}/correction-seed`와 `/api/corrections/{id}` 상세를 제공한다. 큰 생산/실사 대체 입력은 `/api/corrections/drafts` 및 `/api/corrections/{id}/draft-revisions`의256KiB 한도로 처리하고 기존 공통16KiB·세션/Host/Origin 규칙은 유지한다. 검토 목록에 임의의 전체 행 수 제한을 추가하거나 영향 이력을 잘라내지 않으며, 각 기존 업무 입력의 행/문자 한도와 전체 본문 한도를 적용한다.

가치 확인이나 포함 연결 해소가 남으면 `can_confirm=false`와 함께 typed 부분 계획·안정된 원사건 참조·해결할 입력을 반환한다. 아직 존재하지 않는 개정은 `Proposed` 계획 참조로 표시하고 확정 결과에서 실제 UUID를 연결한다. 처음 기준·마지막 관측·현재 투영의 순번을 별도 필드로 구분한다.

원본 상세에서 정정 초안을 열어 입력·이유를 보존하고, 영향받는 품목의 수량/가치·실사 소모/배분·포함 연결·별도 보정·주문 관계를 확인한 뒤 확정한다. 원본 당시와 현재 유효 결과를 구분한다. 알려지지 않은 상태와 확인한0을 다르게 표시하고 실제 ID가 있는 관계만 링크한다. 미리보기에는 미래 UUID를 만들지 않는다.

대상 head가 바뀌면 원초안을 유지하고 현재 유효 기록을 안내한다. 다른 대상으로 자동 재지정하지 않는다. 이미 전송한 요청의 결과가 불확실하면 원 UUID/본문으로 재시도한다. 공통 요약은 새 `reason`을 명시적으로 읽으며 기존 `note`를 가짜로 복제하지 않는다. 중첩 대체·확인 행도 baseline/pending과 깊은 복사하며, 키보드 오류·행 추가/삭제·미리보기 포커스와 세 너비/두 테마를 검증한다.

## 계산과 유효 이력

원사건의 논리 순번/원행 위치와 정정의 실제 기록 순번/시각을 분리한다. 조회 시점까지 확정한 유효 개정만 선택한다. 정정 당시 새 품목 버전 참조의 유효성도 실제 정정 시점으로 검사하며 원본 계산 위치와 혼동하지 않는다.

1. 현재 유효 사실에서 Base를 구성하고 실제 보유/관측/배분/포함 head와 일치하는지 검증한다. 불일치를 자동 보정으로 흡수하지 않는다.
2. 대상의 원래 위치에서 대체/취소를 적용해 Proposed 수량 경로를 만든다. 후속 실측 M은 고정하고 소모 C/초과 E를 다시 도출한다. 생산은 입력 전 합계를 평가하며 자기 결과물로 부족을 숨기지 않는다.
3. C/E 전환·시작/정산 전환·초과량 변경으로 기존 확인의 의미가 바뀌면 기존 실사 정책의 이유/금액 확인을 요구한다. 원래 확인 금액을 자동0이나 새 평균으로 바꾸지 않는다.
4. 평균·전량 잔여·부분/전량 폐기·생산 배분으로 가치를 전파하고 지연 입고는 유효 포함 개정만 한 번 적용한다. T-011의 고정 C/E 가치 재생을 그대로 수량 정정 엔진으로 사용하지 않는다.
5. 판매 정정만이면 C/K·현재 Q/V를 유지하고 판매 개수로 새 배분/미배분 버전을 만든다. 물리 사건 정정으로 C/K가 달라지면 해당 구간의 배분 개정도 연결한다. 원본과 이전 개정은 모두 보존한다.
6. 품목별 현재 결과와 원장/관측/배분/포함 연결/별도 보정 전후를 한 계획으로 반환한다. 같은 revision에서 다시 계산한 계획만 원자 확정한다.

첫 수량 근거만 취소돼 유효 근거가 없어지면 `NotEstablished`로 돌아간다. Q0/V0이나 취소된 유입의 마지막 단가로 대신하지 않는다. 뒤에 실제 관측이 남으면 그 관측의 시작 가치 확인이 필요하다. 알려진 현재 보유 결과는 실제 정정 효과를 근거로 저장하고 과거 보유/판매 단가 FK를 남긴다. 미확인 결과를 표현하는 head와 정정 효과 참조를 분리해 원행 삭제를 피한다. 알려진 현재 수량이0인 상태에서 정정된 마지막 유효 단가가 달라지면 별도 가격 근거 행을 만든다. 옛 보유 ID에 새 금액을 붙이거나 단가 보관을 위해 양수 재고를 만들지 않는다.

현재 보유를 새 정정 순번으로 저장하더라도 판매 구간 경계는 마지막 유효 관측의 원래 순번이다. 예를 들어 마지막 관측10, 판매15/20, 정정30, 다음 관측40이면 판매15/20은 다음 배분 후보에 포함한다. 과거 변동을30 이후의 새 유입으로 중복 합산하지 않는다.

## 포함 입고와 정정의 결합

포함 연결의 원본·이전 버전·예약은 삭제하지 않고 현재 유효 head만 한 번 집계한다. 원천/선택 관측이 취소되거나 한도가 줄면 영향을 받는 연결을 정확히 안내하고 명시적인 연결 개정을 같은 계획에 포함한다. 자동 비례 축소·다른 원천 재선택·실사마다 새 권리 부여는 하지 않는다.

변경하지 않은 연결은 당시 Bv·Ai를 보존한다. 관측/포함 입력 자체를 바꾸는 경우에는 그 개정의 치환 전 가치 근거와 새 Bv/Ai를 저장한다. 기존 D를 가산한 현재 평균으로 자기 Bv를 다시 계산하지 않는다. 같은 관측의 정확 누적 잔여에는 유효 개정만 포함한다. old/new 예약이나 가치 차액을 둘 다 누적하지 않는다.

지연 입고가 기록되기 전에 확정한 실사 K·생산 금액과, 지연 입고 뒤의 사건이 사용한 보정 후 단가를 구별한다. 모든 D를 과거 관측부터 주입한 비교 원장의 원가를 그대로 확정 소모로 바꾸지 않는다. S14에서 원래 K와 별도 보정을 유지한 뒤 새 실사는 보정된 현재 가치로 정산한다. 이 상태에서 판매 개수 정정은 그 K를 유지하며 배분만 바꾸고, 물리 사건 정정은 기존 별도 보정과 새 소모 원가를 중복 계상하지 않는다. 포함 Bv의 관측 근거도 원래 관측 시점까지 알려진 가치를 사용하며, 그 관측보다 나중에 기록한 자기 보정 D를 포함하지 않는다.

미리보기의 새 관측/효과 참조는 원본 ID·행 위치·계획 내 참조로 표현하고, 실제 새 UUID는 확정 트랜잭션에서만 만든다. 입고 취소/대체가 주문 종료에 미치는 영향도 보존된 원종료와 현재 유효 상태를 구분한다. 부분 입고 추적을 새로 도입하지 않는다.

## 저장·호환과 구현 분담

schema12/JSON2를 계획한다. 정정 원본/버전/head·입력/영향 결과와 필요한 관측·소모·포함 연결·현재 보유 head 확장을 기존 mutation/outbox 트랜잭션에 연결한다. `consumption_versions`의 관측당 단일 버전 제약을 개정 모델로 바꾸되 소모 원본과 모든 배분 행을 남긴다. 실제 기록 seq와 관측/판매 구간의 논리 seq는 다른 필드로 검증한다.

schema11의 정상 release API로 가상 fixture·원요청/응답·전체 JSON을 확보한다. frozen11은 당시 DTO를 닫고 새 필드/태그가 옛 형식에 들어오면 거절한다. 원문을 재직렬화하지 않으며 mutation canonical 요청도 바꾸지 않는다. 기존 기록의 당시 검증과 현재 유효 결과 검증을 구분하여 정상 정정 뒤 원본을 부패로 오판하지 않는다. 실패 시 DB/heads/outbox 전체 rollback과 원본 보존을 확인한다.

## 수용 검증과 순서

먼저 기존 release의 새 입력/조회 미지원과 이미 배분된 판매 정정 차단을 실제 행동으로 확인한다. UI 중첩 입력의 복사/복원/dirty/pending을 RED로 관찰한 뒤 구현한다. 판매 재배분 S17부터 확인하되 판매만 구현하고 T-012를 완료하지 않는다.

## RTD Before4

[Step 1] 변경 계획 - PASS: 다섯 업무의 원본 보존 취소/대체·영향 미리보기·유효 이력 범위와 여섯 수용 검증을 정했다. 다음 단계는 행동 RED와 공유 DTO/계산 인터페이스 고정이다.

[Step 2] 계획 검토 - PASS: 원문/UUID·보유 FK·아카이브·개인 자료를 보존하고 실제 정정 쓰기와 순수 계산을 따로 검증한다. 기존 저장/화면을 사용하며 반품은 T-013에 둔다.

[Step 3] 검토 재검토 - PASS: 실제/논리 순번 혼동, 취소된 첫 근거의 가짜0 표현, 자기 보정 가치로 Bv를 재산정하는 세 가정을 반례로 고정했다. 저장·도메인·UI 독립 사전 검토에서 새 운영 질문은 발견하지 못했다.

[Step 4] 계획 단순화 - PASS: 닫힌 정정 입력과 기존 업무 파이프라인을 재사용하고 범용 이벤트 프레임워크·전체 과거 레시피 재계산·환불을 추가하지 않는다. 분담한 구현을 합친 뒤 모든 수용 기준을 판정한다.

되돌릴 때는 검토 가능한 코드 diff와 migration 전 DB 백업을 사용한다. 원본 삭제·SQLite 직접 수치 수정·기대값 적재로 검증을 통과시키지 않는다. RTD After13과 요구사항 노트 동기화, 공개 경계/링크/UTF-8/LF/ignore 검증 뒤 최종 실제 diff에 근거해 커밋한다. T-001 실환경·T-021 실제 시연은 별도 미완료다.
