## 구현 전 실제 실패

T-013 release를 새 격리 디렉터리에 복사하고 SHA256 일치를 확인한 뒤 정상 세션으로 실행했다. 기존 `/`·`/business`는200이지만 새 `/workspace`의 GET·HEAD는 기대200에 실제404였다. 명령은2실패·8통과, 종료1이었다. 기존 unknown404·POST405·외부Origin403·무세션API401 보호도 확인했다. 이 결과는 새 화면 미지원의 행동 실패이며 컴파일 실패를 대체 근거로 사용하지 않았다.

UI 통합 상태 시험3건도 최초0통과/3실패·종료1이었다. 부모 화면에 상태가 전달되지 않음, 다른 기록 저장 뒤 오래된 미리보기의 확정 전송, 선행 불확실 요청 중 실사 미리보기 전송을 실제 assertion으로 확인했다. 선택적 부모 통지와 미리보기/선행 요청 검사를 추가한 뒤 같은3건이 종료0으로 통과했다.

일반 상세에서 보낸 요청이 작업 화면 진입 뒤 완료되는 경합은 추가 실제 시험에서1통과/1실패·종료1로 재현했다. 원요청 저장소는 해제됐지만 비활성 항목의 이전 상태가 남던 문제다. 목록을 다시 확인할 때 비활성 항목만 보존된 요청/입력과 실제 서버 상태로 맞추었고 관련9건이 통과했다. 응답 유실로 아직 남은 원요청은 DB 상태만으로 삭제하지 않는다.

첫 전체 UI 단위 실행은99/99·종료0, 타입 검사도 종료0이다. 최종 독립 검토와 표준 빌드·Cargo·실제 브라우저/키보드/화면 검증은 아직 전이다.

추가 검토에서 응답 유실된 새 초안의 원요청 재생이 이미 편집 중인 실제 기록의 부모 상태를 덮는 경우를2통과/1실패·종료1로 재현했다. 같은 실제 기록에 수정 요청이 불확실한 상태에서 원생성 응답이 도착하면 pending 표시를 지우던 원인이다. 이미 존재하는 실제 기록은 수정 입력·원요청·저장 head를 보존하고 새 로컬 항목과의 연결만 바꾼 뒤 조회하도록 수정했다. 관련 workspace10건은 종료0으로 통과했으며 전체 회귀는 다시 확인한다.

독립 실행에서 재진입 중 create 성공 후 상세가 비어 있던 경합과 브라우저 임시 보관 실패 후 메모리의 미저장 입력을 저장됨으로 표시하던 경합도0통과/2실패로 재현했다. 공유 선택 ID 변경을 관찰해 필요한 상세를 읽고 기존 편집기가 발행한 읽기용 상태를 복원 때 우선 사용하도록 수정했다. 기존 pending 초기화·요청 본문·DB 저장 동작은 유지했다. 수정 뒤 원래 독립 시험2/2와 workspace12건이 통과했다.

최종 UI 단위는102/102·종료0, 타입 검사도 종료0이다. 프런트엔드와 새 E2E7건을 동결하고 표준 빌드를 시작했으며 Cargo·브라우저·키보드/화면 검증은 아직 대기 중이다.

## 통합 검증 실행

위 단락들은 구현 중 각 단계의 기록이다. 최종 UI102건과 타입 검사 뒤 표준 `node scripts/build.mjs`가 `/workspace`를 포함한16개 경로를 생성했고 Rust release 빌드 완료·실행 파일 경로 검사1통과/0실패를 기록했다. 완료된 프로세스의 종료코드 값은 세션 전환 후 회수하지 못했으므로 별도의 종료0 근거로 사용하지 않는다. 후속 `node scripts/ui-manifest.mjs --check`는 종료0으로 입력·산출물 일치를 확인했다.

`cargo test --locked --test closing_workspace_storage --test closing_workspace_http --test http --test business_http --no-fail-fast`는21/21·종료0이다. 새 Store4·작업 화면 HTTP3·기존 HTTP8·공통 업무 HTTP6을 실행했다. `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`도 각각 종료0이다. DB 계산·스키마를 바꾸지 않아 바로 선행 T-013의 전체488건을 반복하지 않고 이번 화면과 HTTP 영향 경계를 검증했다.

키보드 보조의 첫 실행은 미완성 판매의 첫 오류를 메뉴 선택으로 예상해 실패했다. 실제 서버는 빈 판매 개수를 첫 오류로 반환하고 편집기도 개수 입력에 초점을 이동한다. 제품 코드와 공개 시험은 바꾸지 않고 보조의 기대만 고쳤다. 이후 Tab·Enter·Space로 탐색·작업 추가·임시 저장·오류 초점·0개 입력·미리보기·확정·목록 복귀·원결과 이동의 모든 검사가 PASS였다. 종료코드는 회수하지 못했으며 최종 PASS 로그와 실제 화면을 확인했다. 환경은 Windows·Node24.19.0·Chromium156.0.8078.4다.
