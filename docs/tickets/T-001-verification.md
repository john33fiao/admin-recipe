# T-001 검증 기록

이 문서는 실행 순서대로 결과를 보존한다. 현재 범위와 결과는 마지막의 **macOS 실제 Chrome 장시간 검증**까지 함께 읽으며, 최신 부분 관측과 완료된 과거 결과를 구분한다. 이전 절의 미검증 상태는 당시 환경의 기록이다.

현재 판정은 **T-001 진행 중 / 배포 준비 미완료**다. 검증 대상은 Windows x64·macOS ARM64다. 초기 macOS 결과, Windows 개발 PC의 후속 검증과 [보안 검토](T-001-security.md), 현재 Mac의 후속 검증을 각각 구분한다. 과거 결과만으로 이후 변경의 통과를 주장하지 않는다.

## 의존성 보안 경고

`npm ci`와 `npm audit`에서 high 7개 경고를 확인했다. 이는 서로 다른 7개 결함이 아니라 Nuxt→Nitro→listhen→node-forge 1.4.0 경로의 같은 RSA 서명 검증 권고가 상위 패키지로 전파된 결과다. 2026-10-24 확인한 [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv)는 수정 버전을 제시하지 않는다.

설치된 listhen 소스의 node-forge 사용은 개발 서버의 인증서 처리 경로다. 현재 앱은 정적 UI 생성 후 Rust HTTP 서버로 실행하며 Node/Nitro 서버·HTTPS 인증서 검증 기능을 배포하지 않는다. 현재 구현에서 해당 RSA 검증을 호출하는 경로는 찾지 못했다. 의존성 경고 자체는 해결되지 않았으며 개발 서버 HTTPS나 Node 서버 배포를 추가하기 전에 다시 검토해야 한다. npm이 제안한 Nuxt 4.1.3 강제 다운그레이드는 검증한 구성과 다르므로 적용하지 않았다. 감사 통과로 보고하지 않는다.

## 해결한 문제

- 새 입력 디렉터리를 Cargo가 감시하지 않아 오래된 UI를 그대로 빌드할 수 있었다. 실제 새 `public/` 파일 추가로 재현하고 루트 감시와 해시 검사를 결합했다.
- 세션 발급 전에 fragment를 제거하면 연결 중 새로고침 시 실행 토큰을 잃었다. 발급 성공 후 제거하고 요청 실패·새로고침 회귀를 검증했다.
- hot rollback journal이 남은 DB는 읽기 전용 버전 조회만으로 열 수 없었다. 실제 프로세스를 트랜잭션 도중 종료해 재현했다. 복사본 복구 후 버전을 확인해 지원 DB만 원본 복구하며 미래 DB/저널은 바이트 그대로 보존한다.
- 브라우저 테스트에서 SPA 전환 직후 주소를 너무 일찍 읽었다. URL 전환을 기다린 뒤 데이터 ID와 비교하도록 검증 코드를 고쳤다.

## 변경 후 검토

[Step 1] 목적 적합성 - PASS: 재료 등록·저장·조회와 휴대 실행 기반을 구현했다. 미충족 OS 기준은 완료로 표시하지 않았다.

[Step 2] 오류·중요 문제·보안 - PASS: SQL 매개변수·입력 제한·Host/Origin/세션·정적 경로 분리·잠금·hot journal을 검증했다. 공개 후보에는 가상 데이터만 있다.

[Step 3] 회귀 - PASS: 사용자 운영 결정·O-01~O-04·후속 범위를 유지했다. 시작 시 기존 Git 변경은 없었다.

[Step 4] 파일·함수 크기 - PASS: 수명/서버/저장/UI/빌드 책임을 분리했다. 저장 테스트와 실제 네트워크 테스트를 구분했다.

[Step 5] 재사용·통합 - PASS: 동일 Store를 실제 API와 테스트에서 사용한다. 기존 문서 색인과 ADR을 연결했다.

[Step 6] 부작용 - PASS: 개발 의존성·생성물·db/는 제외했다. 로컬 서버만 열며 JSON 기록은 무기한 증가한다. 전역 서비스·자동 동기화는 설치하지 않았다.

[Step 7] 전체 변경 재검토 - PASS: 독립 리뷰가 찾은 3개 문제를 수정하고 전체 테스트를 다시 실행했다. 최종 소스와 공개 diff를 재검토했다.

[Step 8] 불필요한 잔여물 - PASS: 테스트 자료는 임시 폴더 사용, 생성물·로그·운영 데이터·지침·스킬은 커밋에서 제외했다.

[Step 9] 품질 검증 - PASS: 위 빌드/테스트/형식/링크 검사 결과를 확인했다. 로컬 RTD 스킬 2개 검증기와 호환 심볼릭 링크도 확인했다.

[Step 10] 사용자·개발자 흐름 - PASS: 등록→상세→새로고침→재시작/이동, 응답 유실과 JSON 실패 재시도, 데스크톱 1280px·390px 다크 화면을 확인했다. README 명령으로 재현한다.

[Step 11] 발견 문제의 원인 - PASS: 실패를 실제로 재현한 뒤 원인을 수정했다. 저장·수명·UI 전체 회귀를 통과했다.

[Step 12] READY 판단 - PASS: 구현 변경은 검증 범위에서 READY. **T-001 전체는 NOT READY**이며 위 미검증 항목이 남는다. 연결 노트와 요구/구조 기록을 함께 갱신했다.

[Step 13] 요청된 커밋 준비 - PASS: 명시적 로컬 커밋 승인 범위에서 status·unstaged/staged diff와 후보별 ignore 검사를 수행한다. 비공개 자료·로컬 지침·운영 데이터는 제외한다. 푸시·PR·병합·배포는 하지 않는다.

## Windows 후속 검증 · 2026-10-24

- 시작: master `8f6a43e`, 깨끗한 작업 트리/스테이징. 실제 원격 master `ccfee58`보다 두 커밋 앞섰다. 기존 변경과 두 커밋을 보존했다.
- 환경: Windows 11 Home 10.0.26300 x64, Node 24.19.0, npm 11.19.0, rustc/cargo 1.99.0 (`x86_64-pc-windows-msvc`), MSVC 14.41.34120 / dumpbin 14.41.34123. rustfmt·clippy를 추가 설치했다. npm·cargo-audit·Gitleaks·브라우저 도구는 제외된 작업용 경로에 준비했다.
- 브라우저: Playwright 1.64.1 / Chromium 156.0.8078.4 headless, 설치된 Chrome 156.0.8078.47·Edge 156.0.4314.42. Firefox 143.0은 설치만 확인했고 실행하지 않았다.
- 모든 자료는 가상이다. 원시 명령 로그·감사 JSON·브라우저 trace·스크린샷·프로필은 제외된 `tmp/verification/`와 테스트 결과 경로에 보관한다. 공개 문서에 토큰·개인 절대경로를 복사하지 않는다.
- 마지막 정상 빌드 B: PE x64, 4,678,656 bytes, SHA-256 `e15486b79cbaa90341914327324d15c28f28dae920d869e76f0fb23c1c894b1b`. 서명 상태 `NotSigned`. 동적 의존성은 shlwapi, bcryptprimitives, kernel32, api-ms-win-core-synch-l1-2-0, ws2_32, ntdll의 Windows DLL이며 별도 VC/SQLite DLL은 없다. 최소 OS 지원 여부는 별도 장비에서 확인해야 한다.
- 장시간 시험·설치 브라우저 화면에 사용한 빌드 A: 4,680,704 bytes, SHA-256 `61025b77786d5f502f941aae870797d225901758f59d429995aaa86b59e30952`. 이후 E2E의 조기 종료 판정만 보완하고 정상 재빌드해 B를 만들었다. 제품 Rust/UI 소스는 같고, 실제 A 서버의 자산과 B의 생성 자산을 대조해 JS/CSS 바이트 일치와 HTML 3개·빌드 JSON의 생성 ID/시각 외 일치를 확인했다. B의 전체 E2E는 별도로 수행하며 A의 30분 관찰을 B 바이너리의 30분 실행으로 표시하지 않는다.

처음 npm 설치와 Rust 테스트는 샌드박스의 디렉터리/임시 파일 이동 권한 제한으로 실패했다. 승인된 실제 Windows 실행에서 다시 수행해 통과했다. 도구 미설치·샌드박스 실패를 제품 결함이나 통과로 기록하지 않았다. 정상 종료 E2E의 기존 Windows SIGINT 사용은 실제 실패를 재현하고 수정했다. 브라우저 장시간 검증은 자동화의 포커스/가시성 개입과 숨겨진 페이지 대기 실패 때문에 여러 차례 준비 단계에서 실패했다. 최종 스크립트는 격리 프로필의 기본 창을 원시 CDP로 관찰하고 실제 최소화·`hidden`을 확인한다. 모의 시계·가시성 덮어쓰기·운영 시간값 변경은 사용하지 않는다.

빌드 A의 첫 E2E 재실행은 이전 실행과 결과 디렉터리를 공유해 첫 사례 정리 시 `browserContext.close`의 trace 파일 `ENOENT`로 1개 실패/5개 통과였다. 이를 정상 종료 실패나 전체 통과로 바꾸어 기록하지 않았다. 출력 경로를 분리한 `npm --prefix frontend run test:e2e -- --output ../tmp/verification/e2e-isolated`로 전체 6개를 다시 실행해 통과했다. 같은 결과 경로에 E2E를 동시에 실행하지 않는다.

추가 검토에서 종료 헬퍼가 이미 종료된 앱의 코드를 검사하지 않고 반환하는 누락을 재현했다. 실제 헬퍼에 exit 7·강제 종료·정상 종료 통제를 적용해 수정 전 실패와 수정 후 거절/통과를 확인했다. 통제 실험의 첫 TypeScript 추출은 제네릭 제거 누락으로 실패했고 실험 코드만 고쳐 다시 확인했다. 이제 모든 종료를 검사하고 `close` 이벤트로 stdout 완료까지 기다린다. 제품 코드·시간값 변경 없이 정상 재빌드 후 `--output ../tmp/verification/e2e-final`로 전체 6개 회귀를 다시 실행해 통과했다. B 빌드 뒤 Rust 36개·clippy·fmt·타입·manifest 검사도 통과했다.

## macOS 실제 Chrome 장시간 검증 · 2026-10-25

**24분 부분 관측 / 전체 검증 미완료**다. T-021 최종 감사에서 현재 Mac의 설치된 Chrome으로 수행할 수 있는 장시간 검증을 확인하여 기존 headless 회귀와 별도로 착수했다. 정상 API의 재료 등록·상세 조회·새로고침을 마친 뒤 실제 최소화/hidden 상태에서24개 매분 표본을 확보했다. 마지막 관측은1,440,121ms이며 모든 표본의 hidden·minimized·앱 생존이 true이고 최대 wall-clock 관측 간격은60,007ms였다. 이를30분 전체 통과나 관측 이후의 생존 보장으로 확대하지 않는다. 새 운영 정책·제품 코드·스키마·의존성·시간값은 바꾸지 않았다.

사용자가 앱 종료 검증 생략을 요청하여 원검증기의 자동 후속 단계 진입을 중지했다. 같은 Chrome의 기존 탭에서 남은 백그라운드 관측을 이어가려 했으나 재연결 시 모든 종류의 대상 탭 목록이 비어 있었고 렌더러도 없었다. 대상 탭 소실 원인은 확인하지 않았으며 사용자 행위나 제품 결함으로 추정하지 않는다. **30분 전체 프로토콜·복귀 등록/화면은 미실행이며, 이번 앱 종료·재시작 검증은 사용자 요청으로 생략했다.**

환경은 macOS27.0.1(26A434) arm64·Node24.20.0·설치된 **Chrome155.0.8059.85의 실제 창**이다. T-021의 Chromium156 headless 회귀와 다른 브라우저/실행 조건이다. `target/release/sunchang-hansang`의 SHA-256 `3ca214f35218d3c175465d2e9430c96a5335a38499687fc37430d58e1925da53` 사본과 새 가상 DB·전용 Chrome 프로필을 사용한다. 한글/공백 경로의 앱을 다른 작업 디렉터리에서 PATH 없이 실행하지만 같은 개발 장비이므로 개발 도구가 없는 별도 Mac 검증의 근거로 확대하지 않는다.

앱에는 `--no-browser`를 주고 전용 Chrome 프로세스를 별도로 실행한다. OS 기본 브라우저의 자동 열기 성공을 검증하는 흐름이 아니며 PATH 제거도 Mac의 실제 OS 브라우저 열기 실패 주입을 의미하지 않는다. 기본 브라우저 등록·OS 설정은 변경하지 않는다.

재개용 보조 관측의 첫 시도는 상대 경로 오류로 브라우저 연결 전에 실패했다. 로컬 관측 경로만 보완한 뒤 대상 탭/렌더러가 없음을 확인했으며 제품을 수정하거나 시험 기간을 줄이지 않았다. 정리는 전용 Chrome에 SIGTERM, 중단된 검증기에 SIGKILL을 보내는 범위였다. 검증기 종료 코드-9는 이 취소/정리 결과이며 앱 시험 실패나 앱의 정상 종료 코드가 아니다. 정리 시 앱은 활성 목록에 없어 신호를 보내지 않았고, 이번 앱 종료 원인·코드·120초 유예·재시작은 판정하지 않았다. 남은 시험용 활성 프로세스는0이다. 자원 정리를 종료 시험 성공으로 세지 않는다.

### Safari 자동화 환경 확인

OS 내장 `safaridriver`의 별도 loopback 드라이버에 실제 `POST /session`을 요청했으나 드라이버가500·`session not created`를 반환했다. 원인은 Safari 개발자 설정의 `Allow remote automation` 비활성화다. 드라이버의 상태 응답이 ready인 것만으로 세션 생성을 가정하지 않았다. `--enable`·설정/프로필 변경을 하지 않았고 이번 드라이버만 종료 코드0으로 정리했다. 이는 Safari 자동화 환경 미충족이며 앱 시험 실패나 Safari 지원 불가의 근거가 아니다. **Safari의 실제 앱 UI 검증은 미실행**으로 유지한다.
