# T-019: 이전 DB·JSON 호환과 같은 OS 데이터 이동

- 상태: 대기 — 선행 티켓 완료 후 착수
- 단계: 1차
- 작성일: 2026-10-24
- 관련 요구: D-11~D-13
- 선행: [T-018](T-018-full-state-restore.md)
- 기준: [요구사항](../REQUIREMENTS.md), [최신 운영 결정](../decisions/ADR-007-consumption-and-ticket-scope.md)

## 목적

새 앱으로 교체하거나 폴더를 옮겨도 업무 자료와 사진을 계속 사용한다.

## 포함 범위

업무 스키마 추가에 따른 이전 버전 fixture, 마이그레이션/실패 복구·정상 종료 후 데이터 이동과 수동 앱 교체 절차를 검증한다.

## 제외 범위

자동 업데이트·OS 간 왕복 완료 주장·서버 이관.

## 수용 기준

- [ ] T-019-01: 현재 T-001 DB v2·JSON v1부터 새 버전까지 자료를 보존하여 연다. 합성 fixture와 실제 출시 버전 증거를 구분한다.
- [ ] T-019-02: 새 앱이 이전 DB를 열 수 있고 미래 스키마는 쓰기 없이 거절한다. 변환 실패는 원본을 보존한다.
- [ ] T-019-03: 정상 종료 후 바이너리+db/를 같은 OS의 한글·공백 경로로 옮겨 데이터·사진·정정/배분 참조를 확인한다.
- [ ] T-019-04: DB만 이동했을 때 기록 복구와 JSON만 가져왔을 때 구조화 상태 복원을 구분한다. 사진을 포함하려면 db/ 전체가 필요함을 안내한다.
- [ ] T-019-05: 앱 교체 전 정상 종료·보존 절차, 실패 시 지원되는 복구 절차를 README에 기록한다. 오래된 바이너리로 새 DB를 여는 역호환은 보장하지 않는다.
- [ ] T-019-06: OS 간 왕복 검증은 T-027에 연결하고 이 티켓의 같은 OS 성공으로 대신하지 않는다.

## 검증 방법

과거 fixture→새 앱 변환·손상/미래 버전·변환 실패·같은 OS 경로 이동·사진·정상 종료·수동 교체 통합 시나리오.

구현 티켓은 [공통 완료 조건](README.md#공통-완료-조건)의 실제 명령에서 영향 범위를 선택한다. 후속 구체화 티켓은 먼저 미결정을 확정하고 구현·검증 작업을 나눈다.

## 남은 결정과 구현 메모

운영 정책 질문은 확정됐다. 화면 구성·스키마·오류 표시·정밀도 등은 T-002와 기존 구조에 맞춰 설계한다. 새 운영 판단이 필요하면 예시와 영향을 제시하고 해당 부분만 보류한다.

## 검증 결과

미실행 — 요구사항을 티켓으로 전환한 상태다. 수용 기준 체크는 실제 구현·검증 근거가 생긴 뒤 갱신한다.
