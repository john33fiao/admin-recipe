## 범위와 화면

`/workspace`의 **모아 입력** 화면에 판매·실제 손질/비축 생산·명시 폐기/직원식·선택 실사를 모은다. 입력 목록과 선택한 편집기 한 개를 배치하고 기존 업무 편집기·결과 컴포넌트를 재사용한다. 좁은 화면은 목록과 편집기를 세로로 연결하며 선택/목록 복귀의 키보드 초점을 제공한다. 입고·반품은 기존 기록과 보유 변동으로 연결한다.

저장 단위는 기존 업무 기록 한 개다. 생산·실사의 여러 행은 해당 기록 안에서 기존 원자성을 유지한다. 각 기록을 임시 저장하고 미리보기 뒤 개별 확정한다. 새 날짜별 마감 원장·잠금·재개방, 작업 그룹 DB, 교차 업무 전체 확정·선택 저장 큐, 모든 품목 실사 강제는 추가하지 않는다. T-031~T-033 파일/시트 일괄 입력 백로그와 전체 원자료 이관은 제외한다.

목록은 이 탭의 미저장 입력, DB에 임시 저장된 초안, 확정 기록과 처리 결과 미확인을 구별한다. 각 행의 저장 전후 요약·자동 기록 시각과 원업무/결과 상세 링크를 제공한다. 판매 확정만으로 재고를 차감하지 않으며, 실사 결과에서 확정 소모·배분을 보여준다. 빈 실사 칸과 명시한0을 그대로 구별한다.

## 저장·작성 수명 계약

- 새 로컬 항목마다 독립 identity를 사용한다. 동일 종류·동일 메뉴의 다른 입력이 payload·요청 UUID를 공유하지 않는다. 탭 보조 목록은 화면 선택과 미전송 입력을 돕는 용도다.
- 임시 저장의 정본은 기존 DB 업무 초안이다. 앱과 브라우저를 다시 시작해도 기존 목록/상세 API로 찾아 이어 입력한다. 탭에만 남긴 입력을 DB 임시 저장 완료라고 표시하지 않는다.
- create의 실제 성공 응답을 받은 뒤 같은 화면에서 실제 record ID에 연결한다. 저장된 업무는 일반 업무 상세와 동일 record identity를 사용한다. 응답 유실 때 유사한 이름/수량의 DB 초안을 추측해 합치지 않고 원 identity·UUID·본문을 유지한다.
- 기존 `useBusinessDraft`와 판매/생산/실사·폐기 편집기의 저장·검토·재시도 로직을 재사용한다. 선택적 host 통지는 실제 상태/성공을 목록에 전달하는 좁은 인터페이스다. 같은 identity로 composable을 중복 실행하지 않는다.
- 선택한 편집기 하나만 mount하여 기존 고정 DOM ID·label·오류 초점의 중복을 피한다. 늦은 목록/상세/저장 응답은 generation과 identity를 확인하고 현재 다른 입력을 덮지 않는다.
- A 성공·B 불확실·C 미저장은 각각 표시한다. 전체 성공을 추정하지 않으며 request conflict는 새 UUID로 자동 재전송하지 않는다. 로컬 pending 보존 실패는 기존 규칙대로 전송 전에 안내한다.

## 실사 순서와 최신 상태

실사에는 같은 DB의 실제 확정 입고·생산·반품·폐기와 그 실사 구간에 확정된 판매가 반영된다. 화면에 보이는 항목만 골라 브라우저에서 수량/가치를 재계산하지 않는다. 미확정 생산·폐기·판매는 아직 계산/배분에 포함되지 않았다고 명시하고 필요한 선행 기록을 확정한 뒤 새 실사 미리보기를 안내한다. 모든 초안을 강제로 확정하도록 요구하지 않는다.

영속 변경은 임시 저장도 전역 revision을 바꾼다. 같은 화면의 저장 성공 뒤 이전 미리보기는 재검토가 필요하며 expected revision만 바꾸어 자동 확정하지 않는다. 다른 탭의 변경은 기존 CAS·409 검토 흐름으로 처리한다. 이미 전송한 불확실 confirm은 원 UUID/본문 재생을 유지한다. 같은 작업의 선행 요청이 전송 중이거나 결과 미확인이면 먼저 그 결과를 확인한 뒤 의존하는 실사를 진행한다. 과거 원응답 재생에 포함된 state를 전역 최신 state로 오인하지 않는다.

## 변경 파일과 보호 경계

새 workspace page·얇은 편집기/목록 상태 helper와 필요한 기존 editor host 통지, 탐색·스타일, 새 UI 시험을 추가한다. 서버는 `/workspace` SPA 허용목록과 해당 HTTP 검증만 추가한다. 계산·Store API·schema13·JSON2와 기존 DB 관계는 변경하지 않는다. 정상 업무 API를 이용한 혼합 변동 Store 회귀로 기존 계산 연결을 확인한다.

세션/Host/Origin·라이프사이클·16KiB 및 기존 생산/실사256KiB 경계를 유지한다. 메모/품목명은 텍스트로 표시하고 새 HTML 삽입·파일/셸·외부 서비스·인증 방식을 추가하지 않는다. 공개 시험은 가상 자료를 사용하며 기존 사용자 문서와 개인 자료를 보존한다.

## 수용 검증 계획

| 기준 | 실제 행동과 관찰 계획 |

|01|날짜/마감 입력 없이 네 종류를 작성·저장·확정하고 서버의 자동 시각/seq·원기록을 확인한다. 페이지 열기/미리보기는 쓰기 효과가 없다.|
|02·04|재고 부족·레시피 구성0·0개 판매도 저장/확정되며 Q/V는 변하지 않는다. 실사 전에 확정한 메뉴의 개수 비례 배분을 결과에서 확인한다.|
|03|가상10kg/V10000→입고2kg/2000→생산 투입2kg→반품1kg→폐기1kg→실사6kg. 최신 기준8kg/V9000에서 소모2kg/2250, 잔량6kg/6750이다. A3/B1 판매는1.5kg/1687.5·0.5kg/562.5로 배분한다.|
|04·06|미완성 생산·폐기와 빈칸/0 실사를 개별 임시 저장하고 앱/브라우저 재시작 뒤 DB 초안으로 복원한다. 임시 저장 후에도 확정 전까지 재고/소모가 바뀌지 않는다.|
|05|A 저장 성공 뒤 B 응답 유실·JSON 발행 실패, C 미저장을 각각 표시하고 같은 UUID/본문으로 B를 재생한다. A를 재생성하거나 전체 성공으로 표시하지 않는다.|
|03·05|실사 preview 뒤 다른 항목 임시 저장/확정·다른 탭 변경으로 오래된 요청을 검토한다. 입력을 보존하며 사용자가 새 미리보기를 확인한 뒤 확정한다.|
|06|빈 실사 행은 기존 관측을 유지하고 명시0은 실제0으로 확정한다. 입력/저장/확정 요약과 원기록·배분 상세로 이동한다.|

새 화면 미지원의 실제 HTTP/UI 행동 RED를 먼저 확인한다. UI unit/typecheck 뒤 frontend 변경을 포함한 `node scripts/build.mjs`를 수행하고 Cargo·브라우저를 실행한다. 관련 명령은 `cargo test --locked`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `npm --prefix frontend test`, `npm --prefix frontend run typecheck`, `npm --prefix frontend run test:e2e`, `node scripts/ui-manifest.mjs --check`다. 변경과 관련된 기존 업무/editor·정적 경로 회귀를 함께 검증한다. 실제 결과·최초 실패와 영향 재검증·미검증은 별도 검증 기록에 남긴다.

## RTD Before4

[Step 1] 변경 계획 - PASS: 여섯 기준을 네 업무 입력·개별 저장·순서·부분 결과·DB 복구와 실행 가능한 가상 사례로 연결했다. 변경 범위와 검증 후 다음 단계가 구체적이다.

[Step 2] 계획 검토 - PASS: 기존 정책·전역 revision·원UUID 재생·미확정/미확인 구별·DOM ID/초점·늦은 응답과 기존 사용자 변경을 검토했다. 새 운영 정책 질문은 없다.

[Step 3] 검토 재검토 - PASS: 개별 업무 저장이 티켓의 일관된 저장 단위를 충족하고, DB 초안 복구가 임시 저장 후 재시작 요구를 충족한다. 별도 영속 작업 그룹이나 교차 업무 트랜잭션을 요구하지 않는다는 계약을 기존 DOMAIN §12와 대조했다. 불확실 요청과 일반 초안을 혼동하지 않도록 검증한다.

[Step 4] 계획 단순화 - PASS: 기존 편집기·저장·계산·결과를 재사용하고 새 원장/schema/batch 엔진을 추가하지 않는다. 단계 완료 후 After13·문서·검증한 공개 변경의 커밋을 수행하고 T-015로 이어간다. T-001 외부 장비·절전과 T-021 지정 시연/배포 준비는 별도 미완료로 유지한다.
