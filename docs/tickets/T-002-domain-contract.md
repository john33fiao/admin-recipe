# T-002: 수량·원가와 소모 보정 계산 계약

- 상태: 완료 — 설계·독립 검토·수용 기준 확인 완료, 제품 구현은 후속 티켓
- 단계: 1차
- 작성일: 2026-10-24
- 관련 요구: C-01~C-03, D-02~D-05, D-08, P-02~P-04·P-07~P-11
- 선행: 없음
- 기준: [요구사항](../REQUIREMENTS.md), [최신 운영 결정](../decisions/ADR-007-consumption-and-ticket-scope.md)

## 목적

업무별 계산이 서로 다른 재고·원가를 만들지 않도록 구현 전에 입력·출력과 보존 조건을 고정한다.

## 포함 범위

품목·관리 단위·레시피 버전·재고 변동·소모 배분의 데이터 계약과 가상 수용 사례를 설계한다. 기존 재료 UUID와 DB·JSON 호환을 유지하는 확장안을 작성한다.

## 제외 범위

제품 코드 구현, 새로운 서버·다중 사용자 구조.

## 수용 기준

- [x] T-002-01: g↔kg·mL↔L을 같은 차원으로 환산하고 g↔mL 자동 환산을 하지 않는다. 자유 단위는 명시한 동일 단위 안에서 계산한다.
- [x] T-002-02: 수량·금액 정밀도, 반올림 잔여 배분, 범위 초과·0 나누기·가격 없음·0원과 입력 오류를 정의한다.
- [x] T-002-03: 보유 평균 단가, 보유량 0일 때 마지막 유효 단가, 입고 전 등록 가격의 우선순위와 출처를 정의한다. 가격 등록만으로 수량·보유 가치를 만들지 않는다.
- [x] T-002-04: 판매 자체는 재고를 차감하지 않는다. 직전 품목 실사 수량 + 확정 입고/생산 유입 - 생산 투입/반품/명시 폐기와 이번 실사 수량의 차이로 미기록 소모를 확정한다. 별도 예상 재고를 운영하지 않는다.
- [x] T-002-05: 실사 기간에 그 재료를 직접 참조한 메뉴의 판매 개수 비율로 소모를 배분한다. 0 수량 참조도 대상이며 비축 생산에서 소모한 하위 재료를 판매에 다시 차감하지 않는다. 대상 판매가 없으면 미배분 소모로 보존한다.
- [x] T-002-06: 첫 실사·품목별 다른 실사 시점·입력 중 장부 변경·0원·0 잔량·동일 수량 판매·정정·지연 입고 후 재실사의 가상 수용 사례를 작성한다.
- [x] T-002-07: 레시피 변경은 이후 판매에만 적용한다. 여러 결과물은 주 결과물 원가 100%·나머지 0%를 기본으로 수정 가능하며 합계를 보존한다. 반품은 현재 평균 단가로 가치 차감한다.
- [x] T-002-08: 기존 DB v2·JSON v1의 확장/변환안과 원기록·버전·정정·실사별 배분의 관계를 정의한다.

## 검증 방법

가상 원장의 시작값·각 처리 후 수량/보유 가치/단가/판매 소모를 수계산하여 대조한다. T-003~T-019가 사용하는 계약과 열린 질문이 모순되지 않는지 문서 검토한다.

구현 티켓은 [공통 완료 조건](README.md#공통-완료-조건)의 실제 명령에서 영향 범위를 선택한다. 후속 구체화 티켓은 먼저 미결정을 확정하고 구현·검증 작업을 나눈다.

## 남은 결정과 구현 메모

운영 정책 질문은 확정됐다. 화면 구성·스키마·오류 표시·정밀도 등은 T-002와 기존 구조에 맞춰 설계한다. 새 운영 판단이 필요하면 예시와 영향을 제시하고 해당 부분만 보류한다.

## 검증 결과

2026-10-24 [계산·데이터 계약](../DOMAIN-CONTRACT.md)을 작성하고 독립 검토했다. 8개 수용 기준은 계약 §12의 대응표로 확인했으며 가상 사례 S01~S22를 정의했다. 이 티켓에서는 제품 코드를 변경하지 않았다. 설계 READY이며 실제 앱 계산·저장·시연 성공을 뜻하지 않는다.

변경 파일은 계약, 이 티켓, README, REQUIREMENTS, ARCHITECTURE, TODO, 티켓 색인이다. 연결 기획 노트에는 C-01~C-03·D-02~D-05·D-08·D-11~D-13의 설계 결과를 추가하고 기존 원문·변경 보존을 확인했다. 다음 작업은 T-020 공통 UI 구현·검증이고, 업무 계산은 각 구현 티켓에서 이 계약을 테스트한다.

### 변경 전 검토

[Step 1] 변경 계획 - PASS: T-002-01~08의 단위·정밀도·실사·소모·보정·버전·기존 DB/JSON 호환을 계약과 가상 수계산 사례로 작성한다. 변경 대상은 계약 문서와 이 티켓 두 파일이며 제품 구현·정책 추가·커밋은 제외한다. 문서 재읽기·링크·UTF-8/LF·diff·제외 규칙과 독립 검토로 확인하고 초안 수정으로 되돌릴 수 있다.

[Step 2] 계획 검토 - PASS: 요구사항·ADR-007과 기존 Store/HTTP/UI·v2 스키마·v1 JSON·테스트를 대조했다. 기존 UUID/요청 중복 방지/불변 JSON·MIT 고지를 보존한다. 모든 사례는 가상이며 개인 자료·비공개 링크·개인 경로를 공개 문서에 넣지 않는다. 문서 검증은 현재 환경에서 가능하고 앱 빌드·별도 장비 검증은 이 설계의 근거로 주장하지 않는다.

[Step 3] 검토 재검토 - PASS: (1) 판매가 수량을 차감하지 않음, (2) 실사 경계는 품목별 입력 순서이고 입고일로 소급하지 않음, (3) 과거 원기록과 현재 보정을 구분함을 확인했다. 이 세 전제가 달라지면 계약 전체가 바뀌므로 ADR-007에 맞춰 유지했다. 지연 입고 이후 생산/폐기와 실사 정정의 가치 보존을 별도 사례로 포함한다.

[Step 4] 계획 단순화 - PASS: 기존 저장/세션/heartbeat를 재사용하는 문서 계약만 작성한다. 신규 프레임워크·다중 사용자 구조·운영 정책·중복 요구사항 문서를 추가하지 않는다. PM의 test-scenarios 기준에 따라 시작 조건·순서·관측 결과·오류 사례를 계약 안에 연결한다.

### 실행한 검증

- 두 문서 재읽기, Node를 이용한 UTF-8/LF·상대 링크·개인 경로/토큰 패턴 검사, `git diff --check`를 통과했다. 두 경로에 대한 `git check-ignore --no-index -v`에서 일치하는 제외 규칙은 없었다. 새 문서는 미추적 파일이므로 내용을 직접 확인했다.
- Node `BigInt`로 S04·S05·S08·S14~S16의 반올림·잔여·현재 가치/별도 보정 수계산을 대조했다. 이는 문서 산술 검사이며 제품 구현 테스트가 아니다.
- 레시피 원가는 각 행을 금액 최소 단위로 한 번 반올림한 뒤 정수 합산하도록 단순화했다. 공통 분모의 연쇄 곱셈을 피하고 저장 행과 총합을 일치시킨다.
- 최종 S07·S11·S21·S22까지 Node `BigInt` 검사를 확장했다. 독립 검토에서는 Python `fractions.Fraction`으로 S04·S05·S14~S18을 다시 계산해 일치를 확인했다. 제품 코드 테스트가 아니라 문서의 산술 검증이다.
- 독립 검토 결과 중요한 미해결 결함·새 운영 정책 질문은 없었다. 0 수량 입고의 양수 금액, 초과 없는 실사의 포함분 연결, 여러 단가의 분모 연쇄 곱셈 문제를 수정하고 재검토했다.
- 최종 공개 문서와 연결 노트를 재읽고 상대 링크·UTF-8/LF·`git diff --check`·상태·제외 규칙을 확인했다. 제품 빌드·브라우저 테스트는 이 설계 티켓의 통과 근거에 포함하지 않는다.

### 변경 후 검토

[Step 1] 목적 적합성 - PASS: T-002-01~08을 계약 §12에 연결하고 22개 가상 사례로 설계 완료를 확인했다. 제품 구현과 구분했다.

[Step 2] 오류·중요 문제·보안 - PASS: 0 나누기·수치 범위·참조·원자성·세대/개정 충돌·미래 형식·자산 경로 검증 계약을 검토했다. 공개 예제는 가상 자료이며 개인 자료·경로·인증자료를 넣지 않았다.

[Step 3] 회귀 - PASS: 최신 ADR-007을 우선하고 기존 재료 UUID·요청 기록·v1 JSON 원문 보존을 명시했다. T-001의 별도 장비·절전 미검증을 유지했다.

[Step 4] 파일·함수 크기 - PASS: 하나의 계산 계약을 13개 주제로 나누고 수용 기준/담당 티켓을 연결했다. 제품 함수·스키마 변경은 없다.

[Step 5] 재사용·통합 - PASS: 기존 저장·세션·트랜잭션·outbox를 재사용하도록 설계하고 요구사항·구조 문서에는 계약 링크를 추가했다. 운영 정책을 새로 복제하지 않았다.

[Step 6] 부작용 - PASS: 제품 데이터·의존성·전역 설정 변경은 없다. 전체 스냅샷의 비용은 T-021 측정으로 남겼으며 연결 노트는 기존 바이트를 보존하고 설계 기록만 추가했다.

[Step 7] 전체 변경 재검토 - PASS: 작성자 외 검토자가 최신 요구·8개 수용 기준·가상 산술을 독립 검토했다. 최종 수정 내용과 새 문서를 직접 재읽었다.

[Step 8] 불필요한 잔여물 - PASS: 초안/검토 예정 표시는 최종 상태로 정리했다. 수계산 실행 자료는 로컬 임시 경로에 두고 제품 코드·공개 테스트에 넣지 않았다.

[Step 9] 품질 검증 - PASS: 문서 링크·UTF-8/LF·diff 공백·Git 상태·제외 규칙과 정수/분수 산술 검사를 통과했다. 새 문서는 diff 외 직접 읽기로 확인했다.

[Step 10] 사용자·개발자 흐름 - PASS: README→계약/요구사항→티켓/TODO로 설계와 다음 구현을 추적한다. 공개 계약은 비공개 원자료 없이 이해할 수 있다.

[Step 11] 발견 문제의 원인 - PASS: 표현 범위와 업무별 허용값 혼동, 정상 실사 포함분 누락, 공통 분모 곱의 범위 위험을 각각 입력 조건표·연결 근거·행별 반올림으로 해결했다. 지연 입고 뒤 재실사와 분수 레시피 사례를 추가했다.

[Step 12] READY 판단 - PASS: 설계 범위 READY. 구현·사진/복원·실제 시연과 T-001 실환경 검증은 완료 판단에 포함하지 않는다.

[Step 13] 요청된 커밋 준비 - PASS: 현재 대화의 명시적 커밋 승인에 따라 이 설계의 공개 문서만 후보로 검토했다. 기존 staged 변경이 없고 제외 규칙에 해당하지 않음을 확인하며 실제 staged diff로 메시지를 작성한다. 연결 노트·로컬 상태·개인 자료는 커밋에서 제외한다.
