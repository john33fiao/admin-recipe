# T-016 설계·변경 전 검토

2026-10-25. [티켓](T-016-statistics-and-history.md)의 일곱 수용 기준과 [계산 계약](../DOMAIN-CONTRACT.md), [최신 운영 결정](../decisions/ADR-007-consumption-and-ticket-scope.md)을 따른다. T-014와 T-015 구현 뒤 저장된 원본·현재 유효 정정·실사 배분의 읽기 화면을 추가한다. 운영 규칙·스키마 v14·JSON v2·업무 writer는 유지한다. POS·회계 보고·예상 재고·메뉴별 직접 계량·전체 원자료 이관은 포함하지 않는다.

## 조회 계약

`GET /api/statistics?from=<RFC3339>&until=<RFC3339>`와 `Store::statistics`는 읽기 잠금 안의 단일 `CatalogState`로 판매·관측·확정 업무를 만든다. from/until은 offset 또는 Z가 필수이며 UTC로 정규화한다. 분수초는 계산 정밀도에 맞춰 최대9자리까지 지원하고 더 긴 입력은 조용히 자르지 않고400으로 거절한다. 응답에서도 나노초까지 적용 경계를 보존한다. from 포함/until 제외이고 from<until이어야 한다. 원확정 `recorded_at`으로 기간을 고르며 조회 시점의 유효 정정을 원위치에 적용한다. 사용자 지정 입고일·정정 실제 시각은 원사건의 기간을 옮기지 않는다. 응답 range에 UTC 경계·원입력 시각 기준·현재 정정 기준을 명시한다.

알 수 없는/중복/누락 query key, 잘못된 인코딩·시각·역전은400이다. 원 query는4096바이트까지이며 초과는414다. 응답의 상세·중첩 행은 합계10,000개까지이며 직렬화되는 모든 배열의 원소를 재귀적으로 센다. 상한을 넘으면400 `report_too_large`와 기간 좁히기 안내를 반환하고 부분 행·부분 합계를 성공으로 보내지 않는다. 상한은 조회 자원 경계이며 데이터 보관이나 업무 허용량 제한이 아니다. 전체 history를 읽는 비용까지 일정하다고 보장하지 않는다. 조회는 기존 Host·세션·Origin 보호를 사용하며 파일·DB·revision·JSON을 변경하지 않는다.

응답은 `range`, `state`, `sales`, `observations`, `operations`다. 영역별 `coverage`는 기간 일치 원기록 수와 전체 원기록 수를 구분한다. 표·차트는 같은 판매 rows를 사용하며 별도 일/월 집계나 빈 날짜0 채우기를 만들지 않는다. 합계는 checked i128 정수로 누적한 decimal string이다. null·명시0·취소·초기 기준·미배분·기간 밖을 분리하며 서로 다른 품목/단위의 수량을 더하지 않는다.

### 판매·소모·원가

- 판매는 불변 `SaleOriginal`과 유효 count/amount, 원확정 참조·현재 유효 참조·실제 정정 참조를 제공한다. 당시 recipe cost와 현재 실사 배분 cost를 분리한다. 원본에 없는 최초 count/amount를 추정하지 않으며 해당 값은 기존 판매 상세 최초 버전에서 확인한다. 현재 레시피 가격·보관 상태가 과거 원가를 바꾸지 않는다.
- 활성 판매만 수량/알려진 금액 합계에 넣는다. 금액 null은 미계산 건수이며0원으로 그리지 않는다.0개이면서 가격 미등록인 유효 판매도 기존 계약대로 금액 null이다. 취소는 별도 상태다.
- 판매 소모는 당시 직접 구성 품목별 실제 유효 배분 후보를 연결한다. 후보가 없으면 `no_effective_allocation`이며 실사 없음/소모0으로 단정하지 않는다. 실제 초기 기준이 확인되는 경우에만 그 근거를 표시한다. 기간 밖 관측에 연결된 배분도 유지하고 기간 밖임을 명시한다.
- 관측은 stable observation과 원실사 batch·행 위치를 기준으로 원시각을 보존한다. 원품목/version/이름/단위/position은 최초 관측에서 별도로 제공하여 취소 뒤에도 표시한다. 유효 effect는 실제 Stocktake Replace/Void와 최신 projection을 대조한다. void 뒤 남아 있는 옛 effect를 활성값으로 쓰지 않는다. 실제 observation version과 취소 projection ID를 분리한다.
- Initial은 시작 기준이며 소모/배분0을 만들지 않는다. Settlement의 실제 C/K와 최신 `actual_allocations`를 사용하고 공개 seq로 최신 결과를 선택한다. 계산 `as_of_revision`을 공개 순번으로 오인하지 않는다. 빈 실사 입력에는 관측 ID나 수량0을 만들지 않는다.
- 기간 내 활성 Settlement에 대해 품목·단위별 총소모=판매별 배분+미배분을 확인한다. 판매 후보가 기간 밖이어도 제거·재배분하지 않는다. 판매 없음과 분모0을 구분하며 판매 개수 비율의 계산임을 표시한다. 집계명은 현재 품목명과 해당 표시용 버전을 명시하고 원관측 당시 이름을 덮지 않는다.

### 업무 이력과 실제 링크

입고·생산·폐기·반품·실사를 기존 typed effect로 표시하고 판매 소모와 합산하지 않는다. 일반/포함입고는 `receipt_basis={original,effective}`의 정규화 R/A·보존 품목/단위·입고일을 제공한다. 유효 정정의 source를 해석하며 현재 품목 head에서 원자료를 추정하지 않는다. 포함입고의 U/Au·dV·별도 금액 보정은 기존 효과로 별도 표시한다. 초안·가격·사진 변경 전체 감사 목록으로 범위를 늘리지 않는다.

원업무 ID는 원행의 `business_record_id`, 원상세는 실제 stable 사건 ID다. 통합 정정은 실제 `CorrectionRecord.id`, 기존 판매 개정은 실제 판매 버전/업무 ID로 구분한다. 생산 effect UUID·관측/소모 version UUID·projection UUID를 다른 종류의 상세 URL에 넣지 않는다. 관측/배분은 소유 원실사로 연결한다. 당시 레시피는 실제 품목 ID와 recipe version ID로 연결한다. 보고서의 값은 조회 state에 고정되며 상세 이동 후 최신 값과 같다고 가정하지 않는다. 전체 다시 조회로 갱신한다.

## 현재 품목 연결

`GET /api/recipes/{material_id}/connections`는 현재 root와 현재 하위 recipe head만 조회한다. 과거 version query를 추가하지 않으며 기존 과거 상세의 직접 참조는 유지한다. 응답에 state·root recipe version·`current_root_current_children` 기준과 실제 각 경로의 recipe version을 둔다. component material version을 child recipe version으로 오인하지 않는다. 직접 구성과 간접 경로를 분리하고 경로에 비용/소모 집계를 추가하지 않는다. 직접 사용은 기존 `/api/materials/{id}/recipe-uses`의 현재 역참조를 사용한다.

각 단계는 해당 owner 레시피의 실제 `basis_count`도 제공하여 분자 수량을 몇 개 기준의 배합인지 해석할 수 있게 한다. 서로 다른 단계의 기준 개수를 같다고 추정하지 않는다. 경로별 visited set과 root부터 edge 수64·직접/간접 경로 합계1,000개 상한으로 순환/폭발을 방어한다. 상한 초과는400 `connections_too_large`로 전체 실패하고 잘린 graph를 반환하지 않는다. 순환은 자료 모순 오류로 거절한다. 원물에 recipe가 없으면404를 정상 없는 상태로 표시하고 가짜 recipe를 만들지 않는다. 과거 version 등 지원하지 않는 query는400으로 거절한다. 현재 연결을 판매 당시 전체 중첩 배합으로 설명하지 않는다.

## 화면

`/statistics`에 기간 form, 판매 표·시계열, 품목별 실사 소모·배분, 종류별 이력과 품목 연결을 둔다. 기존 디자인 토큰·탐색·테마·오류/로딩 패턴을 재사용한다. 최초 진입은 PC 현지 오늘 날짜를 편의 기본값으로 조회한다. 사용자가 고른 마지막 날짜는 포함이며 다음날의 현지 시작을 각각 UTC로 변환한다. DST에서 하루를86,400,000ms로 더하지 않는다.

적용된 절대 from/until과 표시 시간대를 URL에 보존한다. OS 시간대가 바뀌거나 뒤로가기/재조회해도 기존 UTC 범위를 재해석하지 않는다. 새 날짜 조회만 현재 PC 시간대를 사용한다. 입력 중 날짜와 적용된 기간, 새 조회 실패와 이전 결과를 구분한다. stale 응답은 결과를 덮지 않는다. 표시 시간대는 통계 API query에 보내지 않는다.

미계산 금액·초기/미확정 소모·명시0·취소·기록 없음·기간 밖을 문구로 구별한다. 정확한 원문 숫자를 표·차트 설명에서 공유하며 chart 좌표만 제한된 비율로 변환한다. 표의 키보드 선택으로 같은 점의 시각/값을 확인하고 모든 점에 불필요한 Tab 정지를 만들지 않는다. semantic form/table/figure, 오류 초점과 완료 알림,1440/768/390px·라이트/다크를 검증한다. 직접/간접 연결은 접는 경로 목록이며 편집 graph 도구를 추가하지 않는다.

## 파일·검증·되돌림

## RTD Before4

[Step 1] 변경 계획 - PASS: 일곱 기준의 조회·화면·오류·실행 방법을 정했다. 저장/운영 정책을 바꾸지 않으며 원본과 유효 결과를 구분한다.

[Step 2] 계획 검토 - PASS: 저장·보안/링크·UI 사전 검토를 실제 타입/라우트와 대조했다. void 원품목과 일반입고 표시 근거 누락을 보완했다. 보호 경로와 사용자 변경을 제외하고 정상 API의 가상 자료로 검증한다.

[Step 3] 검토 재검토 - PASS: 옛 effect가 void 후 남는 경우, 최신 배분 공개 seq와 계산 revision이 다른 경우, material version과 child recipe version이 다른 경우를 핵심 가정 세 가지로 확인하고 선택/검증에 반영했다. 운영 정책 질문은 현재 없다.

[Step 4] 계획 단순화 - PASS: 단일 기간 보고서와 현재 연결 조회만 추가한다. 새 저장소·집계 캐시·차트 패키지·과거 중첩 graph·범용 보고서 엔진을 추가하지 않는다. 요구 변경 없는 조회 구현이므로 기존 Obsidian 운영 결정을 바꾸지 않는다.
