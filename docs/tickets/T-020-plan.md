# T-020 구현 계획

- 작성일: 2026-10-24
- 기준: [T-020](T-020-ui-foundation.md), [요구사항](../REQUIREMENTS.md), [ADR-007](../decisions/ADR-007-consumption-and-ticket-scope.md)
- 상태: 완료 — T-002 완료 후 구현·표준 빌드·신규 UI와 기존 흐름 회귀 검증. 최종 근거는 검증 기록 참조

## 목적과 경계

기존 재료 등록→목록→상세를 유지하면서 실제 기능으로 이동하는 공통 탐색, 전송 전 입력 보관, 키보드 포커스와 상태 표시를 마련한다. 운영 개요의 발주·판매·실사 집계는 T-017에서 구현한다. 아직 없는 업무의 숫자나 버튼은 표시하지 않는다.

`/`는 기존 재료 등록·목록 주소로 유지한다. `/overview`는 실제 저장된 재료 수와 재료 작업 이동을 제공하는 시작 화면이다. 자료 관리 등 후속 탐색은 해당 업무의 저장·조회가 구현된 뒤 연결한다. 브라우저 탭의 입력 보관은 업무 임시 기록(T-005)의 확정·JSON 기록과 구분한다.

## 화면 설계

기존 주방 재료 기록의 녹색과 그릇 표식을 보존한다. 한국어가 긴 재료명과 단위를 명확히 읽을 수 있는 작업 화면으로 확장하고, 장식용 집계 카드와 임의 수치는 추가하지 않는다.

| 역할 | 라이트 | 다크 |
| --- | --- | --- |
| 바탕 | `#f6f8f5` | `#18231e` |
| 입력·상세 표면 | `#ffffff` | `#213128` |
| 본문 | `#23352d` | `#edf2ec` |
| 보조 설명 | `#5d6e64` | `#b4c3b8` |
| 주요 동작 | `#235b42` | `#a5cfad` |
| 키보드 포커스 | `#a64f08` | `#f4c87b` |

글꼴은 기존 OS 한국어 산세리프를 사용한다. 외부 폰트·이미지·서비스를 호출하지 않는다. 본문은 왼쪽 정렬하고 입력과 목록의 역할을 구분한다. 넓은 화면은 입력/목록 2열, 모바일은 위에서 아래로 이어진다. 화면 높이를 고정하지 않고 내용에 따라 스크롤한다.

```text
브랜드                              테마
작업 시작 | 재료 관리
연결 상태
제목 / 설명 / 실제 자료 수
┌ 재료 입력 ┐  ┌ 등록한 재료 / 새로고침 ┐
│ 이름     │  │ 이름 · 단위 · 등록시각  │
│ 관리단위 │  │ 상세로 이동            │
│ 등록     │  └───────────────────────┘
└──────────┘
```

초기 안의 모든 업무 메뉴를 나열하는 방식은 구현되지 않은 기능을 오해할 수 있어 제외했다. 별도 디자인 시스템 라이브러리와 범용 폼 프레임워크도 도입하지 않는다. 상태는 색과 함께 텍스트로 설명하며, 실패에는 다시 시도할 동작을 둔다.

## 입력과 이동 계약

- 필수 값 오류는 각 입력에 연결하고 첫 오류로 포커스를 옮긴다.
- 전송 전 이름·단위는 같은 탭의 `sessionStorage`에 보관하고 새로고침 시 복구한다. 새 탭이나 앱 DB의 업무 임시 기록으로 표현하지 않는다.
- 이미 전송한 요청의 UUID와 본문은 기존 방식대로 고정한다. 결과가 불명확할 때 입력을 편집하거나 새 요청으로 바꾸지 않는다.
- 재연결 중 입력·마지막 조회 결과를 유지하고 최신 상태인지 문구로 구분한다.
- 페이지 경로가 바뀌면 본문 시작으로 포커스를 옮긴다. 저장 완료 후에는 이름 입력으로 돌아간다.
- 현재 메뉴를 `aria-current`로 표시하고 본문 건너뛰기 링크를 유지한다.

## 검증 계획

| 범위 | 실제 검증 |
| --- | --- |
| 초안 복구 | 잘못된 저장 문자열·타입을 거부하고 불완전한 입력을 보존하는 단위 테스트 |
| UI 품질 | `node scripts/build.mjs`, `npm --prefix frontend test`, `npm --prefix frontend run typecheck` |
| 화면 행렬 | Chromium에서 1440×900, 768×1024, 390×844와 라이트/다크의 시작·입력/목록·상세 |
| 입력·포커스 | 키보드 탐색, 필수 오류, 저장 완료, 상세 이동과 돌아오기, 초안 새로고침 |
| 상태 | 빈 데이터, 목록 로딩/오류/재시도, 저장 중, 응답 유실 재시도, 연결 끊김과 복구 |
| 회귀 | 기존 `local-app.spec.ts`와 새 `ui-foundation.spec.ts` |
| 파일 | 상대 링크, UTF-8/LF, `git diff --check`, `git status --short`, 후보 경로 제외 규칙 |

UI 변경 후에는 표준 빌드로 생성 자산과 실행파일을 갱신한 뒤 브라우저 검증을 실행한다. 공유 작업 중 빌드·Cargo 검증은 담당자와 순서를 조율한다. 검증 결과는 [T-020 검증 기록](T-020-verification.md)에 기록하며 실제 실행 전 PASS로 처리하지 않는다. 반응형 검증은 네트워크 공동 사용·모바일 서버·별도 장비·절전·OS 간 이동 검증을 대신하지 않는다.

구현 검토에서 `/overview` 직접 접근에 서버의 명시적 SPA 경로 허용이 필요함을 확인했다. 범위에 `src/server.rs`의 해당 경로와 `tests/http.rs`의 GET/HEAD·알 수 없는 경로 검증을 추가했다. API·자산에 대한 범용 HTML fallback은 추가하지 않는다.

## 변경 전 RTD

- [Step 1] 변경 계획 - PASS: 기존 재료 흐름과 공통 탐색·입력 보관·포커스로 범위를 제한하고 화면 행렬 및 오류 검증을 정했다. 변경 대상은 `frontend/app/`, 관련 신규 테스트와 T-020 문서다. 되돌리기는 해당 UI·테스트 변경을 제거하고 표준 빌드로 재생성하며 DB는 변경하지 않는다.
- [Step 2] 계획 검토 - PASS: 가상 자료만 사용하며 실제 운영 데이터·외부 링크·개인 경로를 공개하지 않는다. 기존 UUID 재시도·연결 상태·테마와 루트 주소를 보존한다. 미구현 업무와 실환경 한계를 분리했다.
- [Step 3] 검토 재검토 - PASS: T-002 이후 구현 시작, 현재 재료 API 유지, 후속 업무 탐색은 실제 구현 후 연결이라는 세 가정을 명시했다. 가정이 바뀌면 경로·데이터 계약만 재검토한다.
- [Step 4] 계획 단순화 - PASS: 기존 Nuxt·CSS·입력 컴포저블을 활용한다. 새 UI 프레임워크·외부 폰트·가상 업무 집계·DB 변경은 제외했다.
