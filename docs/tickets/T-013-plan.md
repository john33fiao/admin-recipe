# T-013 구현 계획과 변경 전 검토

2026-10-25. 상태: 설계·구현·수용 검증과 RTD 완료. 실제 근거는 [검증 기록](T-013-verification.md)을 따른다. [T-013](T-013-purchase-returns.md)의 여섯 수용 기준, [계산 계약](../DOMAIN-CONTRACT.md) §2·4·5·7·8·9, [ADR-007](../decisions/ADR-007-consumption-and-ticket-scope.md) P-10/Q-05를 따른다. T-007·T-012는 검증 및 커밋 완료다. RTD Before와 PM의 test-scenarios, UI design 및 security 검토를 적용한다.

## 범위와 데이터 계약

- 일반 업무 `purchase_return` v1에 원입고 UUID, 선택한 유효 입고 버전 UUID, 수량·입력단위·메모를 저장한다. 미완성 문자열 초안, revision/epoch, 확정 UUID의 동일 응답 재생을 기존 공통 업무에서 재사용한다. 기본 요청 크기는16KiB다.
- 원입고의 실제 수량 R에서 현재 유효 반품 합을 뺀 미반환 한도와 현재 정산 수량 Q를 각각 확인한다. 포함 입고의 미포함 수량 U를 반품 한도로 사용하지 않는다. 원반품과 그 개정은 한 번만 합산한다.
- 확인된 Q/V에서 부분 반품 q의 차감액은 `round(V*q/Q)`이며 전량은 남은 V 전부다. 반품 후 Q/V를 함께0으로 만들고 마지막 유효 단가는 직전 실제 평균에서 이어받는다. 알려진0원은 허용하고 미확인 가치·부족 수량은 입력을 보존하며 입고·실사·원기록 확인을 안내한다. 부분 폐기의 가치 유지 계산은 사용하지 않는다.
- 효과에는 원입고의 당시 수량·금액·단위, 유효 입고 R/A와 참조, 사건 직전 반품 합/한도, 품목·입력 수량/단위, 전후 보유 Q/V·근거와 실제 차감액을 보존한다. 원입고가 다른 단위의 품목으로 명시 정정된 경우에도 원구입 참고 단위를 현재 단위로 잘못 표시하지 않는다. 환급액이나 부분 환급 추정액은 추가하지 않는다.
- 반품 기록은 원확정/업무/시각/seq와 원효과를 불변 보존한다. 현재 유효 상태는 통합 정정 event head를 통해 active/void로 조회한다. 별도 반품 개정 저장기를 만들지 않는다.

## 조회·화면·정정

- `GET /api/receipts/{id}/return-source`는 원입고와 현재 유효 R/A·품목·반환합·한도·실제 버전/논리 순번을 반환한다. 존재하지 않는 원입고는404, 취소된 원입고는 원문과 `current:null`이다.
- `GET /api/purchase-returns`, `GET /api/purchase-returns/{id}`는 원기록과 현재 유효 상태를 구분한다. 목록에는 원입고/품목 필터를 제공한다. 생성은 기존 `/business?kind=purchase_return&receipt_id=...`, 목록/상세는 `/purchase-returns`를 사용한다.
- 입고 선택→반환 가능 수량/현재 보유 가치 확인→수량 입력→영향 미리보기→확정→상세/정정으로 이동한다. 원구입 참고 금액과 실제 평균 차감액은 별도 제목이다. 미완성·오류·불확실 요청을 보존하고 늦은 source 응답이 다른 선택이나 pending 원문을 덮지 않는다. 연속 반품은 새 작성 수명이며 미확인 전송은 원 UUID/본문을 재생한다.
- 통합 정정에 PurchaseReturn 대상·참조·대체 입력·사건 값을 추가한다. 과거 원논리 위치의 유효 반품만 교체하며 실제 정정 시각에 새 반품을 중복 차감하지 않는다. 뒤의 실제 관측 수량은 유지한다.
- 신규/명시 반품 대체 요청에만 선택 source 버전 CAS를 검사한다. 과거 감사 입력의 CAS를 현재 버전으로 덮거나 재생 때 새 요청처럼 거절하지 않는다. 유효 source의 원논리 위치는 반품보다 앞서야 한다.
- 원입고 취소·다른 품목으로 교체·R 축소가 유효 반품을 침범하면 관련 반품 ID/한도를 안내한다. 반품을 먼저 정정/취소한 뒤 입고를 정정하고 필요하면 반품을 복원한다. 자동 source 교체·한도 축소·임의 연결 반품 일괄 배열은 추가하지 않는다.
- 취소한 반품의 복원용 `replacement_template`은 같은 stable source의 실제 현재 버전만 갱신한다. source 취소 시 버전을 null로 두고 명시 선택을 요구한다. 원입력·원효과·서버 초안·이미 전송한 pending은 변경하지 않는다.

## 재생·저장·보호 경계

반품을 보유 변동과 값/포함 근거 재생에 명시 추가한다. 현재 혼합 Q의 같은 비율로 원천 지분을 취출하며 이미 사용한 포함 예약 한도는 부활시키지 않는다. 뒤늦은 금액 D에서 이미 반품한 몫은 별도 보정이고 원반품 차감액을 소급 덮지 않는다. D 뒤의 새 반품은 수정된 현재 V를 사용한다. 다음 실사에서는 반품을 확정 변동으로 한 번만 제외한다.

schema13은 반품 원기록 관계와 보유 원천 FK를 추가한다. frozen12는 T-012 최종 커밋의 닫힌 DTO를 기준으로 만들고 정상 release API로 생성한 가상 schema12 자료를 사용한다. 과거 원요청·응답·JSON 바이트와 기존 컬럼은 보존하고 schema12에서 새 반품 태그를 거절한다. SQL/JSON의 source·confirmation·seq·품목·Q/V를 대조하며 의미 검증도 같은 transaction에서 실패시 전체 롤백한다. session/Host/Origin·라이프사이클·정적 경로 허용목록은 유지한다.

대상 파일은 새 도메인/저장 반품 모듈, 공통 business/server/holding, 기존 correction·reconciliation 재생/검증, schema/snapshot/frozen12, 관련 Nuxt 화면/타입과 시험이다. 기존 사용자 백로그 문서 변경과 Git 제외 자료는 커밋하지 않는다. 미입고 취소는 기존 주문 Cancel을 재사용하며 반품으로 완료 주문을 자동 재개하지 않는다. 고객 환불·결제·세금, 입력 날짜 추가, 전체 자료 이관, T-022 이후 구현은 제외한다.

## RTD Before4

[Step 1] 변경 계획 - PASS: 여섯 수용 기준을 입력·한도·평균 가치·조회·정정/재시도와 실행 가능한 가상 사례로 연결했다. 이전 버전 정상 자료를 보존한 격리 DB로 이관을 확인하며 제품 DB를 수작업 변경하지 않는다.

[Step 2] 계획 검토 - PASS: 원입고 R과 현재 Q, 원구입 참고 단위와 현재 단위, 당시 입력 CAS와 현재 편집 CAS를 구분했다. 공개/개인 자료 경계·기존 변경·원자성/관계·요청 크기·입력 보존을 검토했다. 새로운 운영 판단은 필요하지 않다.

[Step 3] 검토 재검토 - PASS: 핵심 가정은 유효 반품 합만 한 번 계산, 정정 전후 원논리 위치 유지, 지연 금액의 과거 반품 몫 별도 보정이다. 각각 한도·후속 실사·가치 보존 시험으로 확인한다. 실제 OS/절전 검증과 지정 시연은 이번 티켓의 완료 근거로 대신하지 않는다.

[Step 4] 계획 단순화 - PASS: 공통 업무·정정·원자 저장과 기존 주문 취소를 재사용한다. 별도 반품 개정 엔진·환급 계산·실물 로트 정책·임의 batch 수정은 추가하지 않는다. 검증을 마친 공개 변경만 논리 단위 커밋하며 실패시 이전 정상 바이너리/격리 자료로 재현한다.
