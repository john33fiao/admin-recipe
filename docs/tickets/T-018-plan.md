# T-018 설계·변경 전 검토

2026-10-25. [티켓](T-018-full-state-restore.md) 01~06과 [계산·데이터 계약](../DOMAIN-CONTRACT.md) §10, [최신 운영 결정](../decisions/ADR-007-consumption-and-ticket-scope.md)을 따른다. 선택 시점의 전체 활성 상태를 복원한다. 선택 이후 업무를 일부 합치지 않으며 기존 JSON 원문·사진·요청 중복 방지 기록은 보존한다. 선택 품목 병합, 클라우드 백업, 자동 삭제, 비밀번호, 전체 원자료 이관은 제외한다.

## 상태와 보존 기록

스키마15에서 활성 자료의 순번 참조와 실제 원문 발행 대기열을 분리한다. 기존 `snapshot_outbox`를 순번 관계로 바꾸고 실제 원문은 별도 동일명 outbox에 그대로 보존하는 마이그레이션을 사용한다. 이전 FK와 행·원응답·JSON bytes를 보존하며 가져온 JSON의 과거 순번에 가짜 원문을 만들지 않는다. 새 순번은 현재 보존 기록과 선택 자료의 모든 순번보다 크다.

선택 자료의 품목·모든 버전·레시피·업무 초안/확정·정정·보유·관측·배분·사진 연결·구입처를 한 트랜잭션에서 교체한다. 활성 요청 근거와 전역 재실행 방지 원장을 분리한다. 선택 이후 요청을 활성 업무에 섞지 않으며 동일 UUID에 다른 명령·입력·원응답이 대응하면 자동 병합하지 않는다. 선택 이후 등록 사진도 별도 보존 관계를 통해 계속 확인할 수 있다. 미등록 임시 파일을 등록된 사진으로 취급하지 않는다.

복원 직전의 실제 전체 상태는 불변 JSON으로 별도 보존한다. 초기 revision0이나 DB 마이그레이션 직후처럼 마지막 기존 JSON과 실제 현재 구조가 다른 경우도 포함한다. 이 보존물은 과거 변경 원문을 꾸민 기록이 아니며 목적과 원기준을 명시한다. 복원 기록은 선택 대상·직전 보존 대상·해시·새 epoch와 순번을 연결한다. 원문을 다른 스냅샷 안에 재귀적으로 넣지 않는다.

자료 검증·사진 확인 뒤 직전 상태를 안전하게 보존하고, 현재 상태 CAS·활성 자료 교체·요청 기록·새 전체 JSON을 같은 SQLite 트랜잭션에 넣는다. commit 전 오류는 활성 상태와 요청 처리를 바꾸지 않는다. commit 후 JSON 발행 실패는 이미 DB에 적용됐을 수 있음을 알리고 같은 UUID로 복구한다. 기존 `recover`와 성공 응답 전 발행 조건을 유지한다.

전체 역변환의 사전 검증은 writer 잠금 아래 SAVEPOINT에서 SQL 제약·FK·전건 readback을 확인하고 항상 rollback한다. 검증 상태를 commit하거나 파일로 발행하지 않는다. v1에 없는 초기 기술 버전/epoch는 원문 hash와 품목 UUID에서 결정적으로 파생한 UUIDv8로 표현하며 원사건 ID·새 업무로 취급하지 않는다. 실제 복원의 새 epoch는 별도로 생성한다. 선택 사항과 영향은 [ADR-009](../decisions/ADR-009-full-state-restore-and-replay.md)에 기록했다.

## 입력과 API 경계

- `GET /api/restore-targets`: 보존된 변경 기록과 가져온 자료의 지점을 조회한다. 서버 발급 `journal:<정규 양의 순번>` 또는 `import:<소문자 SHA-256>`만 대상 ID로 사용한다. ID는 조회 키이며 임의 경로가 아니다.
- `POST /api/restore-targets/import`: 원 JSON bytes를 `application/json` 단일 본문으로 받는다. 64MiB·60초·동시 수입1개를 한도로 하며 파일명·경로·URL·ZIP을 받지 않는다. 동일 bytes는 동일 hash 대상이다. 일반 작은 API의 본문 한도를 넓히지 않는다.
- `POST /api/restore/preview`: 선택 target/hash와 현재 상태를 결합해 전체 검증·현재/선택 자료 건수·사진 검사와 복원 가능 여부를 반환한다.
- `POST /api/restores`: 원 요청 UUID·현재 epoch/revision·선택 target/hash를 받아 다시 검증하고 전체 복원한다. 같은 요청의 응답 유실 재시도는 새 복원을 만들지 않는다.

목록은 source가 journal 또는 import이고 기본값은 journal이다. 고정25행의 keyset 방식으로 journal은 순번 내림차순, import는 hash 오름차순이다. `cursor`는 마지막 반환한 순번 또는 hash이며 같은 source의 다음 행부터 조회한다. `next_cursor=null`이면 끝이다. 미지/중복/빈 query와 비정규 cursor는400, 원 query4096바이트 초과는414다. 새 지점은 첫 페이지를 다시 조회하면 나타나며 서로 다른 source를 하나의 offset으로 합치지 않는다. 각 행은 target_id/source/hash/정확 byte_length/format_version/schema_version/원 sequence/request_id/recorded_at을 반환한다.

미리보기 입력은 `{target_id,expected_sha256}`, 확정은 여기에 기존 strict 업무 `meta`를 더한다. 미리보기는 target, 현재 state, before/after 영역 건수, 사진 전건 검사, blocker와 can_restore를 반환한다. 사진 문제 예시는20개까지지만 전체 검사 건수·종류별 건수·생략 여부를 명시한다. 확정 결과는 restore_id, target, previous_target, recorded_at, 새 state다. 미래 복원 UUID/epoch는 미리보기에서 만들지 않는다.

v1과 스키마별 v2를 닫힌 형식으로 읽고 현재 구조로 변환한다. v1의 재료 UUID·이름·자유 단위를 유지하며 없던 가격·업무·사진·요청 사실을 만들지 않는다. 재고 시작 기준은 미확인이다. 미래 버전·알 수 없는 필드/업무·중복 JSON key/ID·비정규 숫자·깨진 참조·수량/가치 불일치는 쓰기 전에 거절한다. 실제 입력을 SQL로 실행하거나 DB 파일 업로드 기능을 추가하지 않는다.

수입/직전 상태 원문은 앱 소유 디렉터리의 열린 핸들 아래 고정 해시 키로 보관한다. 중간 junction/symlink·파일 symlink·비정규 파일을 거절하고 실제 열린 파일의 bytes/hash를 검증한다. 기존 파일은 덮어쓰지 않는다. 사진은 전체 참조의 descriptor·hash·길이·형식·치수를 확인하며 외부에서 내려받지 않는다. 누락/손상은 미리보기에서 명시하고 확정을 막는다. JSON만 가져오면 사진 원본이 포함되지 않는다는 점을 표시한다.

기존 loopback·세션·Host·Origin 보호와 작업 수락/정상 종료 대기 규칙을 유지한다. body 수락 전 취소·초과·timeout은 활성 DB 변경이 없다. Store가 수락한 작업은 클라이언트 연결 종료와 무관하게 commit/발행을 마친다. Windows 파일 sync·SQLite 복구 시험을 전원 차단이나 다른 OS 검증으로 확대 해석하지 않는다.

## 예전 요청과 여러 탭

같은 UUID·다른 명령/본문은 기존 `request_conflict`를 우선한다. 같은 세대의 revision 충돌은 기존 `stale_state`다. 복원으로 세대가 달라진 요청은 별도409 `stale_generation`과 `request_status: already_processed | not_processed`, 실제 현재 상태를 반환한다. 과거 원응답을 보존하되 현재 유효한 성공으로 재적용하지 않는다. 복원 자체의 반복 요청도 결과 세대가 현재일 때만 원성공을 재생하고 다음 복원 뒤에는 이미 처리된 과거 요청으로 안내한다.

세대 정보가 없는 기존 재료 등록의 새 요청은 첫 복원 뒤 상태 정보를 요구한다. 기존 요청은 원입력 비교와 처리 사실을 보존하며 현재 활성 품목에서 빠졌다고 다시 등록하지 않는다. 새 앱의 정상 등록 화면은 현재 metadata를 사용한다.

UI는 원 UUID/body와 미저장 입력을 보존한다. 복원 후 자동으로 새 UUID나 현재 metadata를 대입해 재전송하지 않는다. 이미 처리된 요청과 미처리 요청을 구분해 명시적으로 현재 자료를 확인하도록 한다. 복원 전 서버에서 성공한 응답이 복원 후 늦게 도착하는 경우도 이전 세대의 성공으로 식별한다. 세대 변경을 확인한 후 늦은 응답으로 현재 상태를 되돌리지 않는다.

## 화면

`/restore`의 ‘자료 복원’ 한 화면에서 지점 선택 또는 JSON 파일 검증 → 전체 영향 미리보기 → 명시 ‘이 기록의 전체 상태로 복원’ → 결과와 직전 보존 지점 확인을 제공한다. 현재/선택 품목·업무·초안·버전·배분·사진 연결을 서버 건수로 비교한다. 현재 활성 자료에서 빠지는 내용도 보존 기록에서는 유지된다는 점을 표시한다. 별도 문구 입력·비밀번호·자동 복원을 도입하지 않는다.

파일 bytes를 파싱·재직렬화하지 않고 전용 호출로 전송한다. pending 보관 실패면 전송하지 않는다. 전송 결과가 불확실하면 원 요청 확인을 우선하며 새 복원을 만들지 않는다. 사라진 상세의 입력도 읽을 수 있게 보존하고 현재 DB 초안과 구분한다. 사진 File 재선택은 기존 원 hash를 확인한다. 전체 sessionStorage 삭제나 강제 새로고침을 복원 성공 처리로 사용하지 않는다.

선택 대상·조회 세대가 달라진 뒤 도착한 미리보기는 버린다. 다른 탭의 복원 통지는 새 상태 조회를 유도하는 힌트이며 서버 검증을 대신하지 않는다. 기존 라이트/다크 토큰·semantic form·오류 초점·명시 완료 안내를 사용한다. 1440/768/390px과 Tab/Enter/Space를 실제 확인한다.

가상 자료만 공개 시험에 사용한다. 정상 흐름은 Store/API로 만들고 오류 주입·구형 fixture 설치와 구분한다. 기존 정상 스키마14 자료의 DB·원문·원응답을 보존한 fixture로 Rust 번들 SQLite의 실제 마이그레이션을 검증한다. 메모리 SQLite의 사전 구조 실험만으로 앱 검증을 통과했다고 하지 않는다.

frontend 동결 뒤 `node scripts/build.mjs`, `cargo test --locked`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, UI 단위/타입·관련 브라우저, manifest/산출물·문서·제외 규칙 검사를 수행한다. 각 실제 로그·종료 코드·최초 실패와 수정 근거는 검증 기록에 남긴다. 전체 검증은 변경 범위가 넓은 저장 구조와 기존 writer 회귀를 포함한다. 실제 다른 장비·절전·정식 배포·T-021 지정 시연은 이번 합성 시험으로 완료하지 않는다.

## 예상 변경과 되돌리기

`src/store.rs`, `src/store/{schema,mutation,catalog,profile,snapshot,restore}.rs` 및 snapshot의 구형 변환/수입, `src/restore.rs`, 안전한 JSON 파일 보관, server 경로/오류와 관련 Rust 시험, frontend 복원 화면/상태 보존·시험을 변경한다. README·ARCHITECTURE·DOMAIN-CONTRACT·결정·티켓/색인/TODO를 실제 구현과 맞춘다. 데이터 구조 결정은 연결 기획 노트에 같은 D-11~D-13 근거로 동기화한다.

이전 DB 마이그레이션 전 일관된 SQLite 백업을 유지한다. 새 스키마를 이전 실행 파일로 열지 않는다. 코드 되돌림에는 호환 실행 파일과 정상 종료한 이전 DB 사본이 필요하다. 복원된 활성 상태를 다시 바꿀 때는 보존된 직전 지점을 정상 복원 경로로 선택한다. 사용자 기존 변경과 로컬 전용 자료는 작업 커밋에서 제외한다.

### 통합 회귀에서 발견한 시작 포트 경계

기존 브라우저 시험에서 OS가 배정한6000 포트를 Chromium이 `ERR_UNSAFE_PORT`로 거절했다. 가상 HTTP 서버는 같은 포트에서200을 반환했지만 실제 Chromium 탐색은 차단되는 것을 따로 재현했다. [Fetch의 포트 차단 규칙](https://fetch.spec.whatwg.org/#port-blocking)과 현재 Chromium 구현을 대조했다. 운영 정책·OS 설정을 바꾸지 않고 앱이 배정받은 포트가 차단 목록에 있으면 다른 loopback 포트를 선택한다.

[추가 Step 1] 계획 - PASS: 서버 시작의 포트 선택만 보완하고 브라우저 보안 옵션·방화벽·시스템 할당 범위는 유지한다. 실제6000 재현·할당 재시도/해제·오류 전파 시험과 시작/재시작 브라우저 재검증으로 확인한다.

[추가 Step 2] 검토 - PASS: 거절한 소켓을 선택이 끝날 때까지 유지해 같은 포트 재할당을 피하고 차단 목록 수에 따른 유한 횟수로 제한한다. 반환/실패 시 소켓은 해제한다.

[추가 Step 3] 재검토 - PASS: OS의 빈 포트가 브라우저에서도 허용된다는 기존 가정을 실제 실패로 반증했다. 전체 복원·재시작 검증에서 드러난 실행 결함을 고치며 별도 장비·실제 절전 완료로 확대하지 않는다.

[추가 Step 4] 단순화 - PASS: 기존 `bind(127.0.0.1:0)`와 서버·세션·종료 흐름을 유지하며 작은 포트 선택 함수만 추가한다. 고정 포트나 새 설정을 도입하지 않는다.

[Step 1] 변경 계획 - PASS: 여섯 수용 기준을 전체 상태·보존·사진·입력 거절·동시 요청·재시작 시험으로 연결했다. 포함/제외·입출력·파일·실제 검증·되돌리기를 정했다.

[Step 2] 계획 검토 - PASS: 저장·API/보안·UI를 독립 검토해 활성57관계와 보존 기록, raw JSON 한도/경로, 전역 요청 충돌, 빈 상태 보존, 사진과 여러 탭의 입력 보존을 보완했다. 기존 사용자8경로와 원실행 파일을 별도 보존했다.

[Step 3] 검토 재검토 - PASS: 핵심 가정은 ① 순번 FK 분리와 원행 보존 ② 모든 typed 관계의 역변환 ③ 옛 요청/늦은 성공의 세대 구분이다. 전체 구조의 메모리 실험은①의 사전 근거이며 실제 Rust 마이그레이션, 전건 readback과 물리 제약, 처리 여부별 요청·UI 시험을 구현 완료의 필수 검증으로 둔다.
