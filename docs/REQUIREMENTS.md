# 요구사항

2026-10-24 기준으로 확정한 1차 운영 요구사항과 남은 기술 설계를 정리한다. 구현 완료를 뜻하지 않는다. 개발 범위는 [ADR-002](decisions/ADR-002-first-release-and-local-storage.md), 기본 운영·저장은 [ADR-003](decisions/ADR-003-inventory-events-and-portable-data.md), 운영 예외 O-01~O-04는 [ADR-004](decisions/ADR-004-inventory-exception-policies.md)를 따른다. 기술스택·로컬 실행과 DB 하위호환 방향은 [ADR-005](decisions/ADR-005-rust-nuxt-local-server.md)에 확정했다. 세부 계산·전체 복원 설계와 OS별 검증은 남아 있다. T-001에서 재료 등록·조회와 SQLite/JSON 기록·복구를 구현했으며 [ADR-006](decisions/ADR-006-local-runtime-and-journal.md)에 기술 결정을 기록했다. 전체 운영 기능의 완료를 뜻하지 않는다.

## 목적과 개발 단계

셰프 1명이 단일 PC의 웹 UI 기반 설치형 앱에서 레시피·원가·발주·입고·판매·재고를 관리한다. 다른 PC 또는 Mac으로 데이터를 옮겨 호환되는 OS별 빌드에서 동일 내용을 사용할 수 있어야 한다.

| 단계 | 범위 |
| --- | --- |
| 1차 우선 개발 | 레시피·식재료 원가·발주·입고·판매·재고, 손질·비축메뉴, 마감 판매·폐기, 선택 품목 및 일괄 재고검사 |
| 2차 | 내일 메뉴 계획·작업시간 기록 |
| 백로그 | 시설 점검·부분 입고·보관 위치 |
| 현재 제외 | 소비기한 추적·초기 자료 이관·네트워크 공동 사용·비밀번호 잠금·POS 연동 |

소비기한이 지난 재료는 기존 폐기 기능으로 처리한다. 자료 이관은 별도 요청 때 다루며, 직접 DB에 넣는 방식은 향후 검토 아이디어다. 포장재·소모품·인건비 원가는 이후 확장한다.

## 재료·메뉴

- 재료는 이름과 별개인 고유 ID로 식별한다. 기본 단위는 g이며 mL·개·장 등도 재료 종류와 무관하게 선택한다. 레시피 사용량·재고·단위당 원가는 선택한 재료의 관리 단위를 함께 따른다.
- 업무 구조는 **원물 → 손질 → 비축메뉴 → 판매메뉴**다. 판매 전 주방의 식재료·음식은 모두 재고로 관리한다.
- 메뉴 등록 시 원물인지 손질분인지 구분해 선택한다. 예를 들어 무의 기본손질 완료는 세척·껍질 제거 상태다. 소스·육수·미리 만든 음식은 비축메뉴의 생산량·잔량을 관리한다. 모든 메뉴에 네 단계 입력을 강제하지 않는다.
- 판매·가격·원가는 단일 **메뉴 1개**를 기준으로 한다. 소·중·대는 별도 메뉴로 등록한다.
- 메뉴 복제 기능을 제공한다. 복제본은 원본과 독립된 메뉴이며 기본 이름은 `원메뉴명 (2)` 형식이다. 사용자가 소·중·대 등으로 이름과 구성을 수정할 수 있다.
- 메뉴에서 구성 재료·분량·조리 정보·원가를, 재료에서 사용하는 메뉴를 조회한다.
- 재료·메뉴의 사진·간단한 설명·주요 구입처 링크와 설명을 입력하고 조회한다.

## 검색·조회·운영 개요

- 메뉴·재료를 이름으로 검색하고 상세로 이동한다. 메뉴에서 구성 재료를, 재료에서 사용하는 메뉴를 찾는다. 별칭·고급 필터는 별도 설계다.
- 메뉴 상세에서 재료 상태·분량·조리 공정/시간 정보·재료별 비용과 메뉴 전체 식재료 원가를 확인한다. 기존 조리 정보 조회와 2차의 실제 작업시간 측정 이력은 구분한다.
- 판매 수량의 간단한 통계표와 시계열 그래프를 제공한다. 날짜별 입력을 강제하지 않으며 자동 기록한 시각을 기준으로 조회한다.
- 재료별로 어떤 메뉴에 얼마나 쓰였는지 판매 수량·레시피로 계산한 예상 사용량을 조회한다. 실사 차이는 재료 전체의 차이로 표시하며 특정 메뉴가 실제로 더 썼다고 단정하지 않는다.
- 1차 운영 개요에서 발주 내역·주문량, 입고 현황, 현재 재고와 예상 재고, 최근 판매·소진·실사 차이를 함께 확인한다. 실제 보유 재고와 미입고 주문량을 구분하며 미입고분을 판매 가능한 재고로 합치지 않는다. 내일 제공 가능 메뉴·계획 수량 계산은 2차다.

## 후속 범위 보존

- 2차 메뉴 계획: 보유 재료·입고 예정량과 추가 주문을 바탕으로 내일 제공할 메뉴·수량을 검토한다.
- 2차 작업시간: 종종 측정한 실제 작업시간을 사후 입력하고 장기간 시계열로 조회한다. 인건비 계산은 별도 후속 확장이다.
- 시설 점검 백로그: 고정 목록 대신 관리페이지에서 카테고리·하위 점검항목을 편집하고 일일 완료를 기록한다. 부분 입고·보관 위치도 백로그이며 첫 구현의 선행 조건이 아니다.

## 입력 시점과 재고 처리

날짜별 장부나 영업일 마감 절차를 두지 않는다. 재고·판매·소진은 입력 시점별로 기록하고 시계열 그래프로 조회한다. 그래프와 처리 순서에 필요한 입력 시각은 자동 기록하며 사용자가 날짜를 매번 지정하지 않는다.

**입고일은 예외**다. 과거에 구입한 재료를 늦게 등록할 수 있도록 사용자가 입고일을 지정한다. 실제 입력 시각과 입고일은 별도로 보존한다. 예: `무 / 3kg / 30,000원 / 입고일 2026-10-24`. 지연 입고는 현재 입력 시점에 반영하고 과거 판매·원가를 소급 재계산하지 않는다. 이미 실사에 포함된 수량은 중복 추가하지 않는다(O-01).

| 작업 | 입력과 처리 |
| --- | --- |
| 발주 | kg·L 등 실제 수량 단위로 주문량을 직접 입력한다. 박스·봉 단위 포장 환산을 기본 흐름으로 요구하지 않는다. |
| 입고 | 입고 시 계량한 실제 수량과 구입금액·입고일을 등록해 해당 재료 재고에 추가한다. |
| 손질·비축 | 마감 재고정리에서 실제 수량으로 원물을 차감하고 손질재료·비축메뉴를 추가한다. 원물에서 결과물로 원가를 넘긴다. 기준 수율로 재고를 계산하지 않는다. |
| 메뉴 판매 | 마감 시 메뉴별 판매 개수를 입력하고 레시피가 직접 참조하는 재고에서 사용량을 차감한다. 예: `무채나물 3개 판매`. |
| 임의소진 | 지정 재료의 수량을 직접 차감한다. 예: `무(나박) 1kg 폐기`. 직원식도 폐기에 포함한다. |
| 취소·반품 | 동일한 반환 흐름으로 해당 수량과 구입에 사용한 금액을 차감한다. 실제 계상된 재고·금액에 대해 처리하고, 미입고 주문을 취소하며 없는 재고까지 차감하지 않도록 검증한다. |
| 재고검사 | 확인한 품목의 현재고를 입력한다. 일괄 입력도 지원하며 미확인 품목의 장부값은 유지한다. |

판매·명시적 폐기·손질 전환을 반영한 뒤 실사와 비교한다. 비축 생산에서 소비한 하위 재료를 판매 때 다시 차감하거나, 이미 기록한 폐기를 실사 차이로 다시 차감하지 않는다. 동일 입력의 중복 저장도 재고를 중복 변경하지 않도록 설계한다.

## 일괄 재고검사와 자동 폐기

창고검사처럼 `무 10kg`, `간장 20L` 등 현재고를 여러 품목에 입력할 수 있어야 한다. 각 품목의 관리 단위와 호환되는 단위로 비교한다.

- 실제 현재고가 판매·기록된 폐기 등을 반영한 예상 재고보다 적으면 그 차이를 자동 폐기로 기록한다.
- 부족하지 않은 품목에 자동 폐기를 만들지 않는다. 미확인 품목은 0이나 폐기로 처리하지 않는다.
- 직접 입력한 폐기와 실사에서 생성한 폐기를 구분해 조회할 수 있도록 한다.
- 남은 수량을 새 현재고로 사용하고 이전 예상값·차이·입력 시각을 보존한다.
- 실사 초과는 누락 기록을 먼저 확인한 뒤 원인 불명 증가분에 기존 단가를 적용한다(O-03). 전량 폐기는 남은 원가를 별도 손실로 기록하고 보유 금액을 0으로 종료한다(O-02).

## 원가

**현재 보유 재고의 평균 원가**를 사용한다. 단가는 보유 재고 원가 총액을 같은 관리 단위의 보유 수량으로 나눈 값이다. 입고 수량·구입금액을 반영하며, 구입 건별 단가의 단순 평균을 사용하지 않는다.

손질로 수량이 줄어도 투입한 원가 총액은 결과물에 유지한다. 메뉴 원가는 현재 재료 단가에 메뉴 1개분 사용량을 곱해 합산한다. 결과물과 하위 원재료 비용을 이중 합산하지 않는다.

| 설명용 사례 | 계산 |
| --- | --- |
| 무 3kg을 30,000원에 구입하고 손질 후 2kg 확보 | 손질재료 총원가 30,000원 유지, 1g당 15원 |
| 해당 손질재료를 메뉴에 100g 사용 | 메뉴에 반영할 식재료비 1,500원 |
| 장부 10kg·100,000원인데 실사 8kg | 2kg 자동 폐기, 총원가 100,000원을 남은 8kg에 배분해 1kg당 12,500원 |

폐기 후 잔량이 남으면 손실을 남은 재고에 배분한다. 전량 폐기는 남은 원가를 별도 손실로 기록하고 보유 금액을 0으로 종료한다(O-02). 판매로 정상 사용한 재료의 원가 차감과 폐기로 수량만 감소시키는 원가 처리를 구분한다. 단가 변동을 반영해 **현재 보유량·원가 총액·단위당 가격**을 재료 상세에서 조회한다.

잔량 0일 때 나눗셈을 하지 않는다. 전량 폐기는 원가를 별도 손실로 종료하고, 실사 초과는 기존 단가 조정, 지연 입고는 현재 시점 반영으로 확정했다(O-01~O-03). 여러 손질 결과물·반품 금액 차이·반올림은 확정한 원칙으로 계산안을 구체화하고, 그 원칙만으로 결과가 정해지지 않는 사례는 따로 확인한다. 목표 원가율 경고나 세금 표시 같은 부가 정책은 위 원가 계산을 바꾸는 확정 요구로 취급하지 않는다.

## 실행·파일·복원

- 백엔드는 Rust, 프론트엔드는 Nuxt다. Windows·macOS용 빌드에서 로컬 서버를 실행하고 바이너리를 열면 웹브라우저가 자동으로 열린다.
- 바이너리와 브라우저는 WebSocket heartbeat로 연결을 확인하며 일정 시간 이상 연결이 끊기면 바이너리도 종료한다. 간격·유예 시간·복수 탭·절전 복귀·저장 중 안전 종료는 구현 설계다.
- 앱 내부 업데이트는 현재 제외한다. 새 버전 앱은 이전 버전 DB를 계속 열어 사용할 수 있어야 한다. 이전 앱의 새 DB 사용은 보장하지 않는다. 마이그레이션·실행파일 수동 교체 절차는 설계한다.
- Electron 확장은 향후 가능성으로만 남기며 현재 고려하지 않는다.
- 초기에는 단일 PC에서 사용한다. 네트워크를 통한 동시 사용이나 모바일 접속을 1차 조건으로 두지 않는다.
- **바이너리 하나와 그 옆의 `db/` 폴더 하나**로 실행할 수 있어야 한다.
- `db/` 안에 SQLite DB, JSON 변경 기록, 사진 등 자산을 모두 보관한다. 이전의 DB·JSON을 바이너리와 같은 폴더에 직접 두는 결정은 이 구조로 대체한다.
- SQLite를 기본 저장소로 사용하고 **데이터가 변경될 때마다 JSON으로 기록**한다. 기록은 무기한 보관하며 복원은 선택한 기록의 전체 상태로 현재 데이터를 되돌린다.
- 비밀번호 잠금은 제공하지 않는다.
- 사진은 해시 등 고유명칭을 사용해 `db/` 안에 저장한다. 다른 PC의 원래 절대경로에 의존하지 않도록 한다.
- SQLite DB 또는 JSON을 가져가 다른 PC·Mac의 호환 빌드에서 동일한 구조화 데이터를 열거나 복원할 수 있어야 한다. 사진까지 포함한 온전한 이동은 `db/` 폴더 전체를 함께 가져가는 구성이다.
- JSON의 스냅샷·변경 기록 형식, 파일명, DB·JSON·사진 간 일관성, 전체 복원과 이식성 검증은 구현 설계 항목이다.
- 안정화 후 별도 서버로 이관하는 방향은 유지한다.

## 확정한 운영 예외

기본 범위와 정상 처리 규칙에 더해, 사용자가 2026-10-24에 O-01~O-04의 권장 방향을 모두 채택했다. 아래 네 정책은 **확정 사항**이다. 기술스택 인터뷰에서 다시 선택받지 않고 구현·검증 기준으로 사용한다.

| ID | 항목 | 확정 처리 |
| --- | --- | --- |
| O-01 | 지연 입고 | 실제 입고일과 입력 시각을 별도로 보존하고 현재 입력 시점에 반영한다. 과거 판매·원가를 소급 재계산하지 않는다. 이미 지난 실사에 포함된 수량은 중복 추가하지 않고 현재 상태를 보정한다. |
| O-02 | 전량 폐기 | 잔량이 0이면 남은 원가를 전량 폐기 손실로 별도 기록하고 현재 재고 금액을 0으로 만든다. 이전 손실을 다음 입고에 넘기지 않는다. |
| O-03 | 실사 초과 | 누락 입고·전환·오입력을 먼저 확인한다. 원인 불명 증가는 기존 단가를 적용한 재고 조정으로 기록한다. 적용할 단가가 없으면 금액을 확인한 뒤 확정한다. |
| O-04 | 오입력·재고 부족 | 원기록을 보존하는 취소·정정 흐름을 사용한다. 미완성·재고 부족 입력은 임시 저장하고 누락 입고·손질 등 원인을 해결한 뒤 확정한다. 임시 기록은 확정 재고·원가에 반영하지 않는다. |

실사한 10kg에 이미 포함된 과거 입고 3kg을 늦게 등록해도 현재고를 13kg으로 만들지 않는다. 지연 입고 보정과 취소·정정은 현재 시점의 이력으로 남기며 날짜별 마감 재개방은 도입하지 않는다.

품목 ID, 같은 차원의 단위 환산, 소수 정밀도, 메뉴 복제 이름 충돌, JSON 파일 구조·저장 정합성·사진 보존, DB 이동 절차와 위 정책의 구체적인 보정 알고리즘은 기술 설계 항목이다. 여러 손질 결과물·반품 차액도 확정한 원가 원칙에 맞춰 계산안을 만들고, 실제 사례가 그 원칙으로 설명되지 않을 때만 새 판단을 요청한다.

## 화면 초안과 변경 관리

기존 Figma는 레이아웃 참고안이며 최종 GUI가 아니다. 기능 요구에 맞춰 전면 재설계할 수 있다. 라이트·다크와 PC·태블릿·모바일 크기 대응의 디자인 요구는 유지하되 초기 단일 PC 실행 범위와 구분한다. 대시보드·입력·상세 화면의 탐색을 단순하게 구성하고 긴 화면은 콘텐츠 높이에 맞춰 스크롤하며 FHD 높이에 고정하지 않는다.

중대한 요구사항은 이 문서·관련 ADR·TODO와 연결된 기획 노트에 같은 작업에서 반영한다. 사용자 확정과 구현 설계를 구분한다. 공개 문서에는 실제 운영 자료·비공개 링크·개인 경로를 포함하지 않는다.
