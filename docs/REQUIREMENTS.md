# 요구사항

2026-10-24 기준의 기획 초안이다. 아래 확정 사항은 개발 방향이며 구현 완료를 뜻하지 않는다. 세부 수용 기준과 미결정 정책은 계속 구체화한다. 이번 결정은 [ADR-002](decisions/ADR-002-first-release-and-local-storage.md)에 기록했다.

## 목적과 개발 단계

셰프 1명이 웹 UI에서 레시피·원가·발주·입고·판매·재고를 관리한다. 초기에는 로컬 설치형 앱으로 사용하고, 안정화 후 별도 서버로 이관한다.

| 단계 | 범위 |
| --- | --- |
| 1차 우선 개발 | 레시피·식재료 원가·발주·입고·판매·재고. 손질·비축메뉴 재고, 하루 마감과 임의소진 포함 |
| 2차 | 내일 메뉴 계획·작업시간 기록 |
| 백로그 | 시설 점검 |

1차 내부의 구현 순서와 티켓별 수용 기준은 아직 정하지 않았다. 포장재·소모품·인건비 원가는 이후 확장 요구이며, 작업시간 기록의 2차 포함이 인건비 계산까지 확정한 것은 아니다.

## 확인된 요구

| 영역 | 요구 |
| --- | --- |
| 재료 | 이름과 별개인 고유 ID로 식별하고 단가를 관리한다. |
| 단위 | 기본값은 g이며 mL·개·장 등을 재료 종류와 무관하게 선택한다. 레시피는 선택한 재료의 관리 단위를 따른다. |
| 재고 범위 | 판매메뉴를 구성하기 전 주방에 있는 원물·손질재료·소스·육수·미리 만든 음식을 모두 재고로 관리한다. |
| 손질 선택 | 실측 투입량·완성량 입력 또는 기준 수율 계산을 사용자가 선택할 수 있게 한다. 메뉴 등록 시 재료가 원물인지 손질분인지 확인해 선택한다. |
| 레시피 | 메뉴에서 재료·분량·조리 정보·식재료비를, 재료에서 사용하는 메뉴를 찾는다. |
| 설명 | 재료·메뉴의 사진과 간단한 설명, 주요 구입처 링크·설명을 입력하고 조회한다. |
| 발주·입고 | 주문량·실입고량·현재 재고·예상 재고를 구분한다. |
| 비축메뉴 | 미리 만든 음식의 생산량과 남은 양을 재고로 관리하고 판매메뉴 구성에 연결한다. |
| 판매·마감 | 하루 마감에 메뉴별 최종 판매 합계를 직접 입력하고 재고를 맞춘다. 직원식·폐기도 입력할 수 있게 한다. POS 연동은 제외한다. |
| 임의소진 | 메뉴 판매 이외의 소진을 기록한다. 직원식은 현재 폐기로 취급한다. |
| 재고확인 | 예상 소진량과 실제 잔량의 차이를 파악한다. 메뉴별 실제 사용량의 일일 입력은 요구하지 않는다. |
| 원가 | 1차는 식재료비를 대상으로 한다. 포장재·소모품·인건비는 이후 확장한다. |
| 메뉴 계획 | 2차. 보유 재료와 입고 예정량에 따른 메뉴·수량, 추가 발주 후 가용량을 확인한다. |
| 작업시간 | 2차. 비정기적으로 측정한 시간을 사후 기록하고 시계열로 조회한다. |
| 시설 점검 | 백로그. 카테고리·하위 항목을 설정하고 매일 완료 처리한다. |
| 화면 | PC·태블릿·모바일 크기에 대응하는 웹 UI와 라이트·다크 테마 요구를 유지한다. 설치 대상과 기기 간 연결 방식은 별도 결정한다. |
| 저장·배포 | 웹 UI 기반 설치형 앱을 단일 바이너리로 배포한다. 기본 데이터는 로컬 SQLite에 저장하고 JSON 파일로 백업한다. SQLite DB 파일과 JSON 백업 파일은 모두 실행 바이너리가 위치한 폴더에 보관한다. 안정화 후 별도 서버로 이관한다. |

## 재고와 메뉴의 관계

**원물 → 손질 → 비축메뉴 → 판매메뉴**를 업무 구조로 삼는다.

- 원물과 손질분의 상태를 구분하고 사용자가 메뉴에 필요한 상태를 선택한다.
- 비축메뉴에는 미리 만들어 보관하는 음식과 소스·육수·양념 같은 반제품이 포함된다.
- 원물을 바로 쓰는 메뉴와 손질재료를 다시 손질하는 기존 요구도 유지한다. 모든 메뉴에 네 단계 입력을 강제하지 않는다.
- 업무 단계 구분은 확정했지만, 별도 품목 ID와 동일 품목 아래 상태 중 어떤 데이터 구조를 쓸지는 미정이다.
- 실측값과 수율로 계산한 예상값을 구분해야 한다. 입력 방식 선택 UI와 필수값은 설계 단계에서 정한다.
- 비축 생산에서 이미 사용한 하위 재료를 판매 시 다시 차감하지 않아야 한다. 마감에 기록한 임의소진도 실사 차이로 중복 차감하지 않아야 한다. 차감 시점과 정정 순서는 C-02·D-02에서 구체화한다.

## 결정 상태와 남은 항목

식별자는 기획 검토의 연속성을 위해 유지한다. 확정한 방향과 남은 세부 판단을 구분한다.

| ID | 현재 상태와 남은 판단 |
| --- | --- |
| C-01 | 네 단계와 재고 범위 확정. 별도 품목 ID 또는 동일 품목 아래 상태 관리, 전환 전후 단위는 미정 |
| C-02 | 비축 생산량·잔량·임의소진 관리 확정. 손질·생산·판매의 차감 시점·대상과 중복 방지 방식은 미정 |
| C-03 | 실측/수율과 원물/손질분을 사용자가 선택하는 방향 확정. 선택 UI·필수값·수율 미등록 처리·중간 단계 추적 수준은 미정 |
| C-04 | 기존 운영 사례의 배분량이 원물 기준인지 손질 후 기준인지 미정 |
| C-05 | 이관 시 실제 자료와 대조할 기준값·단가·생산량은 미정 |
| D-01 | 1차·2차·백로그 구분 확정. 1차 내부 구현 순서·수용 기준은 미정 |
| D-02 | 하루 마감 판매 합계·재고확인·직원식/폐기 입력 확정. 마감 후 정정·재개방·영업일 기준은 미정 |
| D-03 | 하루 마감 재고 대조 확정. 확인 대상·입력 부담·차이 표시 임계값·허용 범위는 미정 |
| D-04 | 원가 적용 단가·평균 기간·수율·부산물 비용 배분·판매가와 세금 기준은 미정 |
| D-05 | 단위 추가·변경·포장 환산·소수 정밀도는 미정 |
| D-06 | 작업시간은 2차. 측정 범위·표준시간·배치·설비 조건과 인건비 확장 범위는 미정 |
| D-07 | 시설 점검은 백로그. 입력 형식·설정 변경 시점·휴무·해당 없음은 착수 시 검토 |
| D-08 | 임의소진 지원과 직원식의 폐기 처리는 확정. 소진 사유·정정, 부분 입고·취소·반품·보관 위치·기한·입고 마감은 미정 |
| D-09 | 기존 화면은 레이아웃 참고안. 요구사항 정리 후 GUI 재설계 가능. 검색·사진·설명·구입처·반응형·테마·빈 화면·오류 상태를 구체화 |
| D-10 | 다중 사용자·매장·권한·유료 서비스 범위는 미정 |
| D-11 | 로컬 SQLite와 실행 바이너리 옆 DB 파일 보관 확정. DB 파일명·사진 위치와 저장 방식·기기 간 공유·스키마 버전 정책은 미정 |
| D-12 | 웹 UI 설치형·단일 바이너리와 안정화 후 서버 이관 방향 확정. 대상 OS·아키텍처·업데이트·전환 조건·외부 접속은 미정 |
| D-13 | JSON 백업과 실행 바이너리 옆 보관 확정. 파일명·주기·자동화·보존 기간·사진 포함·복원 검증, 로컬 인증·잠금과 서버 계정·권한은 미정 |

## 화면 초안의 역할

기존 Figma는 기본 레이아웃을 확인하기 위한 참고안이다. 메인 GUI나 구현 명세로 확정하지 않는다. 현재 기획은 대체로 적절하다는 사용자 평가가 있지만, 기능 요구사항이 정리되면 전체를 다시 설계할 수 있다. 기존 화면 수·배치·임시 수치를 구현 조건으로 삼지 않는다.

사진·설명·구입처 정보는 화면 초안 이후 추가된 요구이며 새 GUI 설계에 포함한다. 화면의 존재가 해당 기능의 1차 포함을 뜻하지 않는다.

## 요구사항 변경 관리

중대한 범위·업무 규칙·데이터 구조·저장 및 배포 변경은 이 문서, 관련 결정 기록·TODO와 연결된 기획 노트에 같은 작업에서 반영한다. 사용자 확정·설계 제안·미결정을 구분하고 결정일과 관련 ID를 맞춘다.

공개 문서는 비공개 원본 없이 개발 요구를 이해할 수 있어야 한다. 실제 운영 자료·비공개 화면 링크·개인 경로를 공개 문서에 복사하지 않는다. 로컬 노트 연결과 작업 절차는 로컬 지침에서 관리한다.
