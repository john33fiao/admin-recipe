# 요구사항

2026-10-24 기준의 운영 요구와 티켓 범위다. 구현 완료를 뜻하지 않는다. 최신 사용자 결정인 [ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)을 우선한다. ADR-003·ADR-004의 판매 즉시 재고 차감, 실사 부족 자동 폐기, 재고 부족 확정 금지는 아래 기준으로 대체했다. 실행 기반과 재료 이름·단위 저장/조회만 T-001에서 구현했고 전체 업무는 후속 티켓이다.

## 목적과 개발 단계

셰프 1명이 단일 PC의 웹 UI 기반 설치형 앱에서 재료·레시피·원가·발주·입고·판매·실사를 관리한다. 입고 전에도 재료와 가격을 등록해 메뉴 원가를 계산한다.

| 단계 | 범위 |
| --- | --- |
| 1차 | 재료·레시피·식재료 원가, 발주·입고, 손질·비축, 판매 수량/금액, 명시 폐기, 선택/일괄 실사와 판매 소모 배분, 이력·통계·운영 개요, 사진·전체 복원 |
| 2차 | 내일 메뉴 계획, 실제 작업시간 기록·시계열 |
| 백로그 | 시설 점검, 부분 입고, 보관 위치, Windows↔macOS 데이터 왕복 검증, 소모를 연결할 판매 직접 선택 |
| 안정화 이후 검토 | 별도 서버 이관, 포장재·소모품·인건비 등 원가 확장 |
| 현재 제외 | 소비기한 추적, 초기 자료 이관, 네트워크 공동 사용, 비밀번호 잠금, POS, 고객 환불, 발주서 출력·외부 전송, 세금 자동 분리·할인·결제 관리 |

소비기한 경과분은 명시 폐기로 기록한다. 초기 자료 이관과 직접 DB 주입은 별도 요청 때 다룬다. 기존 화면 초안·엑셀 분석의 미확정 기능을 자동으로 개발 범위에 넣지 않는다.

## 재료·단위·버전

- 재료는 이름과 별개인 고유 ID로 식별한다. 같은 이름도 ID로 구별한다.
- 기본 단위는 g이고 mL·개·장 등 자유롭게 선택한다. kg↔g, L↔mL 등 같은 차원만 환산하며 g↔mL는 임의 환산하지 않는다. 레시피·실사·원가에 같은 관리 단위를 사용한다.
- 원물 → 손질재료 → 비축메뉴 → 판매메뉴를 연결하되 모든 단계를 강제하지 않는다. 원물 직접 사용·손질분 재손질을 허용하며 판매 전 식재료·음식은 모두 관리 대상이다.
- 재료·메뉴의 이름·설명·레시피를 수정할 수 있다. 원기록과 당시 버전을 보존하고 삭제 대신 아카이빙한다. 과거 참조는 계속 조회할 수 있어야 한다.
- 다른 차원으로 관리 단위를 바꾸려면 새 품목을 등록한다. 과거 수량·단위를 새 의미로 덮어쓰지 않는다.
- 수량·금액 정밀도, 같은 차원 단위의 표시 변경, 이름 충돌과 참조 구조는 [T-002](tickets/T-002-domain-contract.md)에서 검토한 [계산·데이터 계약](DOMAIN-CONTRACT.md)을 따른다. 배치 레시피의 구성 분자/기준 개수, 실사 구간·정정·이전 DB/JSON 보존도 이 기술 계약에 정의하며 실제 구현 완료와 구분한다.

## 레시피·사전 원가·메뉴

- 판매·가격·레시피 원가는 메뉴 1개 기준이다. 소·중·대는 별도 메뉴다.
- 메뉴 구성 재료는 원물·손질분·비축품을 구분해 직접 선택한다. 구성 수량의 기본값은 0이며 ‘적당량’ 등의 메모를 보존한다. 수량이 없어도 판매를 등록할 수 있다.
- 수량을 나중에 입력하거나 레시피를 수정하면 **이후 등록하는 판매부터 새 버전을 적용**한다. 과거 판매를 자동 또는 일괄 재계산하는 기능은 현재 범위에서 제외한다.
- 메뉴 복제본은 독립된 ID·구성으로 만들고 기본 이름은 `원메뉴명 (2)` 형식이다. 충돌 시 다음 번호를 선택하고 원본 편집과 분리한다.
- 조리 공정·설명·시간 정보 조회는 1차다. 종종 측정한 실제 작업시간 이력은 2차로 구분한다.
- 입고 없이 재료와 계산용 단가를 등록할 수 있다. 가격 등록만으로 실제 수량·보유 가치를 만들지 않는다.
- 보유 재고가 있으면 보유 평균 단가를 사용한다. 보유량이 0이면 마지막 유효 단가로 계산하고, 입출고 이력이 없으면 사전 등록 가격을 사용한다. 가격 없음과 유효한 0원을 구분하고 적용 출처를 표시한다.
- 레시피 원가는 직접 참조한 재료의 단가×메뉴 1개분 수량의 합이다. 비축품과 그 하위 원재료 비용을 이중 합산하지 않는다.
- 판매가·단순 원가율(식재료비÷입력 판매가)·판매금액 합계를 1차에 포함한다. 판매가가 0 또는 없으면 원가율을 나누지 않고 계산 불가로 표시한다. 세금 자동 분리·할인·결제는 제외한다.

## 판매와 실사 중심 재고

**판매 입력만으로 재고를 차감하지 않는다.** 별도의 예상 현재고를 관리하지 않는다. 실제 수량을 확인하는 실사에서 소모를 확정하고 판매 메뉴에 연결한다.

1. 판매 입력은 메뉴·개수·당시 레시피/판매가 버전·판매금액·자동 입력 시각을 기록한다. 레시피 수량 0이나 계산상 재고 부족으로 판매 확정을 막지 않는다.
2. 실사 전에는 품목별 마지막 확인 수량·확인 시각을 표시한다. 그 뒤의 확정 입고·생산·반품·명시 폐기는 별도로 구별한다. 오래된 확인 수량을 현재 실측값처럼 표시하지 않는다.
3. 소모 정산의 기준은 직전 해당 품목 실사에 이후 확정 입고·생산 유입을 더하고, 생산 투입·반품·명시 폐기를 뺀 값이다. 이번 실사 수량과의 차이로 미기록 소모를 확정한다. 이 기준을 별도의 예상 재고 기능으로 운영하지 않는다.
4. 판매 소모는 **직전 해당 재료 실사 이후부터 이번 실사까지**, 그 재료를 당시 레시피에서 직접 참조한 메뉴의 **판매 개수 비율**로 배분한다. 레시피 사용량 비율이 아니다. 수량 0으로 참조한 재료도 연결 대상이다.
5. 대상 판매가 없으면 미배분 소모로 남긴다. 판매를 직접 선택하는 기능은 백로그다. 배분량은 계산 결과이며 메뉴별로 실제 계량한 값이라고 표현하지 않는다.
6. 비축 생산에 이미 투입한 하위 재료·명시 폐기·반품을 판매 소모로 다시 반영하지 않는다. 판매 자체는 차감하지 않으므로 레시피 차감과 실사 차이의 이중 차감도 만들지 않는다.

가상 사례: 직전 확인 10kg, 명시 폐기 1kg, 이번 실사 6kg이면 판매에 연결할 소모는 3kg이다. 대상 메뉴 A 3개·B 1개라면 A 2.25kg·B 0.75kg으로 배분한다. 첫 실사도 알려진 초기 수량/가치와 확정 입출고가 있으면 이를 기준으로 정산한다. 초기 기준을 알 수 없으면 실제 시작 수량/가치를 확인하며 이전 판매만으로 소모를 임의 역산하지 않는다.

날짜별 영업일 장부·마감 잠금·재개방을 요구하지 않는다. 기록 시각을 자동 보존하며 판매 입력 때 날짜를 매번 지정하지 않는다. 입고일만 별도로 사용자 지정한다.

## 발주·입고·손질·반품

| 작업 | 입력과 처리 |
| --- | --- |
| 발주 | 실제 수량 단위로 주문 내역 저장. 거래처명·입고 예정일·예상 금액은 선택. 저장만으로 재고·가치가 늘지 않음 |
| 입고 | 실제 계량 수량·구입금액·입고일 등록. 발주 없이 직접 입고 가능. 실제 입력 시각과 입고일 분리 |
| 주문 종료 | 한 번의 실입고로 종료하고 원주문량·실입고량·차이 보존. 10kg 주문→9.8kg 입고의 나머지 0.2kg을 계속 미입고로 추적하지 않음 |
| 손질·비축 | 실제 투입량을 차감하고 실제 결과물을 추가. 기준 수율 계산 없이 투입 원가 이월 |
| 여러 결과물 | 주 결과물 원가 100%·나머지 0%를 기본으로 수정 가능. 배분 합계는 투입 원가 보존. 원가 0인 결과물 허용 |
| 명시 폐기 | 지정 재료의 실제 폐기 수량을 기록. 직원식도 이 범주. 판매 소모에서 별도 제외 |
| 미입고 취소 | 주문 상태만 변경하며 없는 재고·가치를 차감하지 않음 |
| 입고 후 반품 | 해당 수량을 반환하고 **반품 시점 현재 평균 단가**로 보유 가치 차감. 구입 당시 금액은 원입고/반품의 참고 금액으로 보존 |

반품 가상 사례: 현재 2kg·20,000원에서 1kg을 반품하면 1kg·10,000원이다. 원구입 금액이 30,000원이더라도 보유 가치에서 그 금액을 직접 차감하지 않는다. 이 결정은 이전 구입금액 차감 규칙을 대체한다. 부분 입고는 백로그이며 부분 수량 반품과 구분한다.

지연 입고는 현재 입력 시점에 반영하고 입고일 때문에 과거 판매·원가를 소급 재계산하지 않는다. 사용자가 관련 실사와 **이미 포함된 수량**을 확인하며 중복 수량을 더하지 않고 금액 보정안을 보여준 뒤 확정한다. 실사 10kg에 이미 포함된 과거 입고 3kg을 늦게 등록해 13kg으로 만들지 않는다.

## 실사·원가·정정

- 확인한 품목의 현재고만 입력하며 미확인 품목은 유지한다. 일괄 입력을 지원하고 빈칸과 0을 구분한다.
- 실사 소모를 자동 폐기로 분류하지 않는다. 판매 개수 비례 배분 또는 미배분 소모로 기록한다.
- 원인 불명 초과는 누락 입고·생산·오입력을 먼저 확인한 뒤 기존 단가로 조정한다. 적용할 단가가 없으면 금액을 확인한다.
- 보유 평균 단가는 같은 관리 단위의 보유 원가 총액÷수량이다. 입고 건별 단가의 단순 평균이 아니다.
- 손질은 수량이 줄어도 투입 원가 총액을 결과물에 유지한다. 가상 3kg·30,000원을 투입해 2kg이면 15원/g이다.
- 실사에서 확정한 정상 소모는 해당 소모 원가를 보유 가치에서 차감한다. 메뉴별 배분 합계와 미배분 소모의 합은 총소모와 같아야 한다.
- **명시 폐기** 후 잔량이 남으면 손실을 남은 재고에 배분한다. 명시 폐기로 10kg·100,000원에서 8kg이 되면 총원가 100,000원을 유지한다. 이 규칙을 실사에서 확인한 판매 소모에 적용하지 않는다.
- 전량 명시 폐기는 남은 원가를 별도 손실로 종료하고 수량·보유 가치를 0으로 만든다. 다음 입고에 이전 손실을 넘기지 않는다.
- 잔량 0에서 나누지 않는다. 전량 사용·반품 시 정밀도 잔여를 보존/정산하는 구체적 방법은 계산 계약에 둔다.
- 업무 오입력은 원기록을 보존하는 취소·정정으로 처리한다. 후속 실사/배분에 영향을 주는 정정은 영향과 변경 전후를 보여주고 중복 처리하지 않는다. 실제 고객 환불·실물 반환을 판매 정정만으로 추정하지 않는다.
- 임시 저장은 지원하며 확정 전에는 재고·원가를 변경하지 않는다. 정상 판매의 0 수량·재고 부족은 확정 차단 사유가 아니다. 잘못된 참조·단위·형식 등 계산할 수 없는 입력은 별도 검증한다.

## 검색·조회·운영 개요

- 이름으로 재료·메뉴를 검색하고 상세로 이동한다. 메뉴에서 구성 재료를, 재료에서 사용 메뉴를 조회한다. 별칭·고급 필터는 후속 설계다.
- 판매 수량/금액의 표와 입력 시각 기준 시계열, 재료별 입고·생산·반품·폐기·실사·배분 이력을 조회한다.
- 레시피 기준 원가와 실사 소모에 배분한 원가, 소모 미확정/미배분 상태를 구분한다. 현재 레시피로 과거 판매 내역을 덮어쓰지 않는다.
- 운영 개요에서 주문량·입고 현황·마지막 실사 수량/시각·후속 확정 변동·최근 판매/소모를 확인한다. 미입고량을 보유량에 합치거나 예상 재고를 별도 제공하지 않는다.
- 내일 제공 가능 메뉴·계획 수량은 2차다.
- 재료·메뉴별 여러 사진, 대표 사진 1장, 간단한 설명, 여러 구입처 링크·설명을 등록·조회한다. 링크 또는 설명만 등록할 수도 있다.

## 실행·기록·복원·호환

- Rust·Nuxt, 로컬 서버와 기본 웹브라우저 자동 열기, WebSocket heartbeat 종료를 유지한다. 단일 PC·단일 사용자이며 네트워크 공동 사용과 비밀번호 잠금은 제외한다.
- 바이너리 하나와 옆의 `db/` 폴더 하나로 실행한다. SQLite·JSON 기록·사진/자산을 모두 이 폴더 안에 보관하고 기기별 절대경로에 의존하지 않는다.
- SQLite가 기본 저장소이며 영속 데이터 변경마다 JSON으로 기록하고 무기한 보관한다. 기록 형식 변경 때 과거 자료의 복구 가능성을 유지한다.
- 복원은 선택한 기록의 **전체 상태**로 돌아가는 기능이다. 복원 전 상태·이후 기록도 보존하고 복원 자체를 새 기록으로 남긴다. 기록 발행 기능만으로 복원 완료라고 하지 않는다.
- 사진은 고유명칭을 사용하며 교체·연결 해제 후에도 과거 복원 지점이 참조하는 자산을 보존한다.
- 다른 PC·Mac의 호환 빌드에서 DB 또는 JSON의 같은 구조화 자료를 사용한다. 사진까지 포함하면 `db/` 전체를 이동한다. 정상 종료·일관된 복사·복원 절차를 검증한다.
- 새 앱은 이전 DB를 계속 지원한다. 이전 앱의 새 DB 사용은 보장하지 않는다. 마이그레이션 실패 시 원본을 보존한다. 앱 내부 업데이트·Electron은 현재 제외한다.
- 검증 대상 Windows x64·macOS ARM64를 유지한다. OS 간 왕복 검증은 백로그이고 T-001 필수 차단 조건에서 제외한다. 같은 OS 이동·별도 깨끗한 장비·실제 절전 등 다른 미검증 조건은 유지한다.
- 최소 OS·브라우저 보장, 다운로드 실행·서명/공증은 T-001과 T-021의 실제 검증으로 판정한다. 로컬 개발 환경 성공만으로 완료 처리하지 않는다.
- 안정화 후 서버 이관은 별도 설계다.

## 2차·백로그와 후속 검토

- 내일 메뉴 계획은 확인 재료·입고 예정·추가 주문을 바탕으로 메뉴·수량을 검토한다. 공유 재료를 이중 배정하지 않으며 계획용 계산과 실제 재고를 분리한다. 생산량 산정·예약/배정 방식은 T-022 착수 때 정한다.
- 실제 작업시간은 종종 측정해 사후 입력하고 실제 날짜 간격의 시계열로 조회한다. 생산량·측정 범위·레시피 버전을 함께 검토하며 표준시간과 인건비 반영은 별도 결정이다.
- 시설 점검은 관리페이지에서 카테고리·하위 항목을 편집하고 일일 완료를 기록하는 백로그다.
- 부분 입고·보관 위치·OS 간 왕복 검증·판매 직접 선택 배분은 백로그 티켓으로 보존한다.
- 포장재·소모품·인건비와 서버 전환은 후속 검토 티켓이다. 확정 범위를 넘어선 제안을 승인된 구현으로 취급하지 않는다.

## 확정한 운영 예외

O-01의 지연 입고 중복 방지, O-02의 전량 명시 폐기 종료, O-03의 원인 불명 초과 조정, O-04의 원기록 보존 정정은 유지한다. O-04의 재고 부족 확정 금지는 대체했다. 이번 세부 결정은 ADR-007의 P-/Q- 식별자로 추적한다.

## 화면·문서와 티켓

기존 화면 초안은 참고안이다. 기능에 맞춰 재설계할 수 있으며 라이트/다크·PC/태블릿/모바일 너비 대응·콘텐츠 높이에 따른 스크롤을 지원한다. 반응형 화면이 초기 모바일 공동 접속을 의미하지 않는다.

모든 범위의 담당 티켓은 [티켓 색인](tickets/README.md), 순서는 [TODO](TODO.md), 기존 A-01~A-32와의 대응은 [요구사항 재검사](REQUIREMENTS-AUDIT.md)에 둔다. 중대한 변경은 연결 기획 노트와 함께 반영한다. 공개 파일에 실제 운영 자료·비공개 링크·개인 경로를 포함하지 않는다.
