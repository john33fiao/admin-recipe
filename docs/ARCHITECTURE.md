# 구조·기술 결정 현황

## 현재 상태

T-001의 Rust 서버·Nuxt 내장 UI와 재료 등록·저장·조회 흐름을 구현했다. 전체 운영 업무는 아직 구현하지 않았다. 최신 업무 기준은 [ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)이며, 이전 운영 결정은 [ADR-003](decisions/ADR-003-inventory-events-and-portable-data.md)·[ADR-004](decisions/ADR-004-inventory-exception-policies.md)에 보존한다. [ADR-002](decisions/ADR-002-first-release-and-local-storage.md)의 개발 단계·SQLite·서버 이관 방향은 유지한다.

[ADR-005](decisions/ADR-005-rust-nuxt-local-server.md)에서 Rust·Nuxt, 로컬 서버·브라우저 자동 열기·WebSocket heartbeat 종료, 새 앱의 이전 DB 지원을 확정했다. 2026-10-24 D-12의 검증 대상은 Windows x64·macOS ARM64다. 앱 내부 업데이트와 Electron은 현재 범위에 넣지 않는다. [T-001](tickets/T-001-portable-local-app.md)은 Windows 후속 검증과 최신 macOS 재검증을 수행했으며 별도 장비 배포·실제 절전 기준이 남아 있다. 같은 날짜 사용자 결정(D-12·D-13)으로 OS 간 데이터 왕복 검증만 백로그로 옮겨 완료 필수 조건에서 제외했다. 각 환경의 정상 동작과 같은 OS의 경로 이동 검증은 유지한다. 채택 구현은 [ADR-006](decisions/ADR-006-local-runtime-and-journal.md), 실행 결과는 [검증 기록](tickets/T-001-verification.md)을 따른다.

## 실행과 저장 경계

T-020은 `/overview` 작업 시작과 기존 `/` 재료 등록/목록·상세를 공통 탐색으로 연결한다. 미전송 입력은 탭의 sessionStorage에 보관하고, 전송 후 불확실한 요청은 UUID와 본문을 고정해 재시도한다. 서버의 명시적 SPA 경로에 시작 화면을 추가했으며 저장 스키마·세션·Origin·종료 정책은 바꾸지 않았다. 실제 화면/회귀 결과는 [T-020 검증 기록](tickets/T-020-verification.md)을 따른다.

- 단일 PC·단일 사용자, 웹 UI 기반 설치형 앱이다. 초기 네트워크 공동 사용과 비밀번호 잠금은 제외한다.
- 실행 환경은 **바이너리 하나 + 바이너리 옆 `db/` 폴더 하나**다.
- `db/`에 SQLite DB·JSON 기록·사진 자산을 모두 저장한다. 경로는 실행 바이너리 기준이며 현재 작업 디렉터리에 따라 바뀌지 않는다.
- 사진은 해시 등 고유명칭을 쓰고 기기별 절대경로에 의존하지 않는다.
- 다른 PC·Mac의 OS별 빌드에서도 SQLite 또는 JSON의 동일 데이터를 사용한다. 사진을 포함한 이동은 `db/` 전체를 대상으로 한다.
- SQLite가 기본 저장소이며 실제 데이터 변경마다 JSON 기록을 남긴다. 기록은 무기한 보관하고 복원은 현재 데이터 전체를 선택한 시점 상태로 되돌린다.
- 재료·업무 초안/확정 변경의 전체 JSON 스냅샷·내구성 있는 기록 대기열·누락 복구를 구현했다. 사진 보관은 T-015에서 구현했으며 선택 시점 전체 복원은 미구현이다. 현재 요구만으로 JSON을 단일 최신 파일로 덮어써 과거 상태를 잃는 방식으로 해석하지 않는다.
- 안정화 후 서버 이관 방향은 유지한다. Rust 업무·API 계층의 재사용을 제안하며 실제 서버 배포 환경·인증은 전환 때 설계한다.

## 업무·계산 경계

- 품목·레시피는 고유 ID와 버전으로 참조하고 수정 전 상태를 보존한다. 삭제 대신 아카이빙한다.
- 판매는 개수·당시 레시피/판매가·금액·입력 시각을 저장한다. 레시피 수량 0·재고 부족으로 판매 확정을 막지 않고 판매만으로 재고를 차감하지 않는다.
- 품목별 마지막 실사 이후 확정 입고·생산·반품·명시 폐기와 새 실사를 대조해 소모를 확정한다. 별도 예상 현재고를 운영하지 않는다.
- 실사 소모는 해당 재료를 직접 참조한 메뉴의 판매 개수 비율로 배분한다. 대상이 없으면 미배분 소모다. 생산 투입·반품·폐기를 다시 판매 소모로 차감하지 않는다.
- 보유 평균 단가를 기본으로 하며 재고가 없으면 마지막 유효 단가, 입고 전에는 등록 가격으로 레시피 원가를 계산한다. 0원과 가격 없음은 구분한다.
- 실제 손질/비축의 투입 원가를 결과물에 이월한다. 여러 결과물은 주 결과물 100%·나머지 0%를 기본으로 수정 가능하다.
- 정상 소모는 원가를 차감한다. 명시 폐기 손실은 잔량에 배분하고 전량 폐기는 별도 손실로 종료한다. 반품은 현재 평균 단가로 가치 차감하며 원구입 금액은 참고로 보존한다.
- 레시피 수정은 이후 판매에만 적용한다. 업무 오입력 정정은 원기록·실사·배분 연결과 영향 범위를 보존한다.
- 메뉴 크기는 별도 메뉴이며 복제본은 독립적으로 수정한다. 가상 자료만 예제/테스트에 사용하며 MIT·제3자 라이선스 고지를 유지한다.

## 운영 정책과 기술 설계의 경계

[ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)이 ADR-003·ADR-004의 판매 즉시 차감·자동 폐기·부족 확정 금지·원구입금액 반품 규칙을 대체했다. 지연 입고의 현재 반영·실사 중복 방지, 명시 폐기의 손실 처리, 초과 조정, 원기록 보존은 유지한다. [T-002](tickets/T-002-domain-contract.md)의 [계산·데이터 계약](DOMAIN-CONTRACT.md)은 단위·정밀도·실사 구간·원가/정정 계산과 데이터 관계의 설계 검토를 마쳤다. 제품 구현은 후속 티켓에서 진행한다.

실사 정산 기준은 실제 확정 변동으로 만든다. 판매의 레시피 예상 소모를 차감한 장부와 실사를 다시 비교하는 모델을 도입하지 않는다. 마지막 실사 수량·시각과 이후 확정 변동을 표시하고 실사 전 소모 미확정 상태를 유지한다.

T-005는 요청 UUID·트랜잭션·JSON 발행/복구를 공통화하고 사전 가격의 DB 임시 기록·확정·정정 연결에 적용한다. 실제 입고·판매·실사·배분은 각 업무 티켓에서 같은 트랜잭션에 연결한다. 버전·임시 기록·정정·배분도 JSON과 전체 복원 대상이다. 기록·자산 무기한 보존과 사진 연결·복원·이전 DB 호환은 T-015·T-018~T-019에서 통합 검증한다. 저장량과 시작 검사 비용은 T-021에서 가상 누적 자료로 측정한다.

Rust·Nuxt와 브라우저 실행은 확정됐다. 현재 구성은 Nuxt 정적 SPA를 Rust에 내장하고 Axum·Tokio가 HTTP·WebSocket을, rusqlite `bundled`가 SQLite를 처리한다. T-001에서 이 구성을 채택하고 Cargo.lock·frontend/package-lock.json에 버전을 고정했다. Nuxt 자산 생성 후 OS별 release 빌드가 필요하며, 단일 바이너리·추가 런타임 불필요 여부는 배포물로 검증한다. 근거와 대안은 ADR-005를 따른다.

heartbeat는 복수 연결·재연결 유예·관측 공백을 구분하고 수락한 저장의 완료를 기다리도록 구현했다. 순차 마이그레이션·실패 복구·미래 스키마 보호는 합성 fixture 범위에서 검증했다. 실제 절전·정식 이전 버전·과거 JSON과 사진 전체 복원은 별도 검증 대상이다.

T-003은 스키마 v3·JSON 형식 v2로 확장한다. 기존 `materials`·생성 요청·JSON v1 원문은 보존하고 품목 버전/head·사전 가격·불변 변경 응답·epoch/revision을 추가한다. 초기 revision은 0이며 성공한 영속 변경의 seq로 갱신한다. JSON v2의 `state`는 품목 원본·모든 버전/가격·요청 기록을 포함하며 outbox 원문을 재귀적으로 담지 않는다. 같은 요청 재시도는 현재 품목 대신 당시 응답을 반환하며, JSON 복구가 끝나기 전에 성공 응답하거나 다음 변경을 적용하지 않는다.

파일 구성·저장 완료 의미·기존 호환/복구 기준은 ADR-006을 유지한다. 과거 DB 테스트에는 합성 v1과 T-001의 v2 구조 fixture를 사용하며 실제 정식 이전 버전의 회귀 검증을 대신하지 않는다. 상세 확장과 검증 범위는 [T-003 계획](tickets/T-003-plan.md)을 따른다. 실행 시 외부 Node·SQLite 개발 도구를 호출하지 않는다. 기존 macOS 산출물의 동적 의존성은 OS 제공 프레임워크와 라이브러리로 확인했으며 T-003 변경분의 macOS 실행은 별도 미검증이다.

T-005는 스키마 v4·JSON 형식 v2에 업무 원본·입력 revision/head·확정·가격 결과·정정 연결의 여섯 관계를 추가했다. 초안은 원입력과 필요한 수정 이유를 보존하며 효과를 만들지 않는다. 미리보기의 epoch/revision/head에서 확정하고, 가격 효과·확정·사용 버전·요청 원응답·전체 snapshot을 같은 트랜잭션에 저장한다. 원확정은 바꾸지 않고 정정 이유와 대체 확정을 연결한다. 원정정 대상 가격, 현재 사전 가격, 새 가격을 구분한다.

옛 v1/schema1~2·v2/schema3~4는 각각 정해진 필수 필드를 검증한다. 마이그레이션 원 DB보다 미래인 snapshot, 누락된 업무 컬렉션과 미지원 입력 종류/버전은 거절한다. 이전 UUID·epoch/revision·응답·JSON 바이트를 보존하며, catalog 변경도 업무를 포함한 전체 snapshot을 남긴다. [T-005 계획](tickets/T-005-plan.md)과 [검증 기록](tickets/T-005-verification.md)에 기존 v3 fixture·발행 실패·원자성·UI 재시작과 후속 통합 경계를 기록한다.

T-006은 스키마 v5·JSON 형식 v2에 `purchase_orders`·불변 `purchase_order_versions`·현재 `purchase_order_heads`를 추가하고 공통 business 명령에 엄격한 `purchase_order` 입력을 연결했다. 주문 진행 상태와 업무 초안/확정 상태는 구별한다. 새 주문·수정·취소는 주문 버전, 확정 결과, 원요청 응답과 전체 snapshot을 같은 트랜잭션에 기록하며 재고·가격 효과를 만들지 않는다. 기존 가격의 요청·결과 JSON 외형과 schema4 reader는 고정한다. 주문의 같은 품목 수정·취소는 새 업무 기록으로 남고, 오래된 주문 head로 확정할 수 없다.

U0/dV0은 가짜 보유 버전을 만들지 않는다. 정상 입고 상세의 보유 ID는 그대로이며, 보정 입고는 실제 효과가 없으면 null이다. 조회·복구 진입에서 물리 FK/seq/position 열과 JSON을 대조하고, schema/snapshot 검증에서 전체 관계·금액·예약을 순수 계산으로 재검증한다. schema10은 옛 일곱 업무 종류와 네 보유 원천을 닫은 frozen reader로 읽는다. 실제 API fixture의23건 원응답·JSON과 FK를 보존하고, 새 필드·태그를 과거 형식에 섞은 자료는 변환 전에 거절한다.

품목별 포함 근거 조회는 관측 전체와 특정 원천을 구별한다. 초안은 최대20행·기존16KiB이며 입력 누락·0·소수 원문을 유지한다. 화면은 실제 구입 정보, 수량 중복 제외, 현재 가치 변화, 별도 보정과 원기록을 구분하고 CAS 충돌·응답 유실 때 입력/원요청을 보존한다. [T-011 계획](tickets/T-011-plan.md)과 [검증 기록](tickets/T-011-verification.md)에 계산 경계·실행 근거와 후속 정정 writer의 한계를 기록한다.

T-012는 스키마 v12·JSON v2에 `correction` 업무와 정정 원기록·사건 개정/head·효과 개정/head·단가 근거의 여섯 관계를 추가한다. 입고·생산·판매·폐기·실사의 원행과 당시 단가/레시피를 보존하고, 원확정 ID와 현재 유효 개정 ID를 구별한다. 실제 정정 기록 시점은 새 seq이며 계산 위치와 판매 구간은 원사건/관측의 논리 seq를 유지한다. 당시 조회에는 그 시점까지 저장한 개정만 포함한다.

미리보기는 유효 수량 사건과 가치의 시간 순서를 다시 계산한다. 실제 후속 관측량은 고정하고 달라진 소모·초과·원가를 도출하며, 시작/초과 확인의 의미가 바뀌면 기존 실사 정책에 따른 명시 확인을 요구한다. 판매 개수 정정은 확정 총소모와 현재 수량/가치를 유지하고 메뉴별 배분·미배분만 바꾼다. 일반 레시피 수정은 이후 판매에만 적용한다. 원천 축소로 기존 포함 입고 연결을 유지할 수 없으면 영향받은 입고의 명시 개정을 요구하고, 기존 Bv·Ai와 과거 확정 소모를 새 평균으로 자동 대체하지 않는다.

정정으로 유효 수량 근거가 사라진 품목은 미확인 상태로 돌아간다. 확인한0이나 취소된 마지막 단가로 대체하지 않는다. Q0의 정정된 마지막 유효 단가는 실제 별도 근거 행으로 보존한다. 계획에서는 아직 없는 UUID 대신 원사건과 계획 내 참조를 사용하고, 확정 트랜잭션에서 실제 관측·소모·보유·단가·포함 연결·주문 개정 ID를 연결한다. 주문 입고 취소와 재입고는 원래 두 종료 기록을 보존한다.

정정 전용 초안 경로만256KiB를 허용하고 공통16KiB·세션/Host/Origin 규칙을 유지한다. 원본 상세·현재 유효 결과·변경 영향과 정정 이력을 연결한다. 오래된 대상 head는 자동 재지정하지 않으며 불확실한 전송은 같은 UUID/본문으로 재시도한다. 공통 mutation은 전체 snapshot 의미 검증까지 트랜잭션 안에서 수행한 뒤 커밋하고 JSON을 발행한다. schema11은 닫힌 frozen reader로 읽고 원요청·원응답·JSON을 재작성하지 않는다. [T-012 계획](tickets/T-012-plan.md)과 [검증 기록](tickets/T-012-verification.md)에 실행 범위와 남은 검증을 구분한다.

### 구매 반품과 현재 가치

T-013은 스키마 v13·JSON v2에 `purchase_returns` 원기록과 보유 원천 참조를 추가한다. 원입고의 실제 R에서 유효 반품 합을 뺀 한도와 현재 Q를 각각 검사하며 포함 입고의 미포함 U를 반환 한도로 사용하지 않는다. 부분 반품은 현재 `round(V*q/Q)`, 전량은 남은 V 전부를 차감한다. 원구입 수량·금액·단위와 현재 유효 입고, 실제 평균 차감액은 별도 근거다. 가격 미확인과 알려진0원을 구별한다.

반품 초안·미리보기·확정은 공통16KiB 업무 경로를, 정정·취소·복원은 기존 immutable event/projection을 사용한다. 신규/명시 대체는 현재 원입고 버전을 검사하고 과거 입력 CAS는 보존한다. 원입고 취소·품목 변경·수량 축소가 유효 반품을 침범하면 관련 반품과 한도를 안내한다. 복원 템플릿만 동일 원입고의 실제 현재 버전을 반영하며 원입력·서버 초안·미확인 전송을 바꾸지 않는다.

반품은 현재 혼합 원천 지분을 같은 비율로 제거하고 이미 사용한 포함 예약을 부활시키지 않는다. 뒤늦은 금액 보정에서 과거 반품 몫은 별도 보정으로 남기고 기존 반품 차감액을 덮지 않는다. 다음 반품은 보정된 현재 가치를 사용하며 다음 실사에는 확정 변동으로 한 번만 반영한다. schema12의 닫힌149개 DTO와 정상 API 자료로 이전 원컬럼·요청 응답·JSON을 보존한다. 관계·효과 의미 검증은 커밋 전에 수행한다. [T-013 계획](tickets/T-013-plan.md)과 [검증 기록](tickets/T-013-verification.md)에 수용 결과와 한계를 기록한다.

### 모아 입력 작업 화면

T-014의 `/workspace`는 판매·생산·폐기·실사를 한 목록에서 선택하고 기존 업무 편집기 한 개를 활성화한다. 저장 단위는 각 업무 기록이며 생산·실사의 여러 행은 기존 단일 트랜잭션을 유지한다. 날짜별 장부·일괄 확정·별도 저장 API는 추가하지 않는다. 서버의 `/workspace` 정적 경로만 허용 목록에 추가하고 스키마 v13·JSON v2를 유지한다.

새 입력은 고유 로컬 식별자를 사용하고 저장 후 실제 업무 ID로 연결한다. 일반 상세와 같은 ID의 입력·원요청 상태를 공유하며 저장한 초안은 DB에서 다시 읽는다. 부모 목록은 기존 편집기가 발행한 읽기용 상태를 관찰한다. 브라우저 임시 보관 실패, 화면 이탈 중 응답, 이미 편집한 실제 ID로 늦게 연결되는 경우에도 미저장 입력·미확인 원요청을 성공 상태로 덮지 않는다.

현재 서버 revision/epoch와 미리보기 상태를 대조하고 다른 저장 이후에는 명시적으로 다시 검토한다. 선행 미확인 요청은 후속 실사 미리보기·새 확정만 막으며 이미 보낸 확정은 원 UUID/본문으로 확인한다. 실제 확정 순서의 입고·생산·반품·폐기를 기존 실사 계산에 반영하고 저장된 입력·현재 화면 입력·유효 확정 결과를 구분한다. [T-014 계획](tickets/T-014-plan.md)과 [검증 기록](tickets/T-014-verification.md)에 부분 실패·복구·통합 순서의 실제 결과를 기록한다.

### 사진·구입처와 보존 자산

T-015는 스키마 v14·JSON v2에 사진 자산과 품목별 profile 버전·현재 참조·사진 행·구입처 행을 추가한다. 기존 품목 설명과 레시피 조리 설명은 그대로 별도 저장한다. 사진·구입처는 전체 목록을 새 불변 버전으로 저장하며 대표 사진은 한 장 또는 사진이 없을 때 없음이다. 레시피 복제는 같은 트랜잭션 안에서 독립 profile/사진 ID를 만들고 원본 bytes만 공유한다.

JPEG/PNG 원본은 SHA256 상대 key로 `db/assets/photos/`에 보관한다. 원파일명과 기기 절대경로를 저장하지 않는다. 검증한 원본을 임시 기록·sync 후 덮어쓰지 않는 hard link로 게시하고 DB 변경·원응답·snapshot을 저장한다. 파일 게시와 DB는 단일 트랜잭션이 아니므로 실패 뒤 미등록 파일이 남을 수 있으나 조회 API는 등록 자산만 제공한다. 연결 해제·품목 보관·사진 교체 뒤에도 과거 자산을 삭제하지 않는다.

cap-std/cap-fs-ext의 디렉터리 handle과 no-follow 접근으로 경로를 검사하고 실제 파일 길이·hash·형식·치수를 확인한다. image의 JPEG/PNG 전체 decode와 파일·픽셀·할당 상한을 적용한다. hard link 미지원 파일시스템은 저장을 거절하며 Windows directory sync의 내구성을 보장한다고 주장하지 않는다. 세부 상한과 OS 검증 한계는 [T-015 계획](tickets/T-015-plan.md)에 둔다.

multipart 개정 경로만 전체11MiB와 metadata256KiB·사진10MiB를 허용하며 동시 업로드 하나를 body 수신 전부터 제한한다. 본문 수신은60초와 종료 신호로 제한하고 수락한 저장은 기존 writer 경계를 사용한다. 정규 metadata와 실제 파일 descriptor로 원요청을 식별하며 boundary·파일명은 제외한다. 브라우저는 UUID/본문/hash를 보존하고 파일 메모리를 잃으면 같은 bytes를 다시 선택해 재시도한다. JSON 발행 실패를 DB 미저장으로 단정하지 않는다.

시작 시 보존된 고유 자산을 검사하지만 일반 업무 mutation마다 모든 사진 bytes를 읽지 않는다. 과거 schema13은 당시153개 닫힌 DTO로 검증하고 기존 DB 열·행·원요청 응답·JSON 원문을 유지한다. 이전 DB에서 미래 JSON이 발견되면 DDL 전에 거절한다. [T-015 검증 기록](tickets/T-015-verification.md)에 실제 결과를 기록하며 전체 복원 writer와 정식 버전별 호환은 T-018~T-019로 이어진다.

### 판매·소모 통계와 현재 품목 연결

T-016은 스키마 v14·JSON v2를 유지하는 읽기 기능이다. `GET /api/statistics`는 한 `CatalogState`에서 원확정 시각의 from 포함/until 제외 기간과 현재 유효 정정을 적용한다. offset 있는 RFC3339와 최대9자리 분수초를 검증하고 UTC 경계를 그대로 반환한다. 원 query는4096바이트, 응답의 모든 중첩 배열 원소는 합계10,000개까지이며 상한을 넘으면 전체 조회를 거절한다. 전체 기록을 읽는 비용까지 일정하다고 보장하지 않는다.

판매의 정확 합계·당시 레시피 원가·현재 실사 배분 원가를 구분한다. 원관측의 품목/시각과 현재 유효 관측·최신 배분을 따로 선택하며 취소 뒤 남은 옛 효과를 쓰지 않는다. 초기 기준·미계산·명시0·판매 없음·분모0·기간 밖 근거를 별도 상태로 반환한다. 입고·생산·폐기·반품의 효과를 판매 소모에 다시 합산하지 않고 실제 원업무·사건·정정의 상세 ID를 연결한다.

`GET /api/recipes/{material_id}/connections`는 현재 root와 현재 하위 레시피만 조회한다. 각 경로의 실제 recipe version·owner 기준 개수·저장된 구성 행을 보존하며 직접/간접 경로를 비용이나 소모로 합산하지 않는다. 경로별 순환 검사와 깊이64·경로1,000개 상한을 적용하고 초과 시 부분 graph를 성공으로 반환하지 않는다. 직접 역참조는 기존 `recipe-uses`를 사용하며 별도 조회 state가 다르면 화면에 표시한다.

통계 화면의 표와 시계열은 같은 판매 rows를 사용한다. 적용된 절대 기간·표시 시간대·선택 품목을 URL에 보존하고 새 날짜 조회만 현재 PC 시간대를 사용한다. 조회 실패·늦은 응답·연결 끊김에서 이전 결과의 기간과 상태를 유지하며 새 결과로 오인하지 않게 표시한다. [T-016 계획](tickets/T-016-plan.md)과 [검증 기록](tickets/T-016-verification.md)에 경계·보안·화면·실행 결과를 구분한다.
