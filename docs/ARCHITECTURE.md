# 구조·기술 결정 현황

## 현재 상태

T-001의 Rust 서버·Nuxt 내장 UI와 재료 등록·저장·조회 흐름을 구현했다. 전체 운영 업무는 아직 구현하지 않았다. 최신 업무 기준은 [ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)이며, 이전 운영 결정은 [ADR-003](decisions/ADR-003-inventory-events-and-portable-data.md)·[ADR-004](decisions/ADR-004-inventory-exception-policies.md)에 보존한다. [ADR-002](decisions/ADR-002-first-release-and-local-storage.md)의 개발 단계·SQLite·서버 이관 방향은 유지한다.

[ADR-005](decisions/ADR-005-rust-nuxt-local-server.md)에서 Rust·Nuxt, 로컬 서버·브라우저 자동 열기·WebSocket heartbeat 종료, 새 앱의 이전 DB 지원을 확정했다. 2026-10-24 D-12의 검증 대상은 Windows x64·macOS ARM64다. 앱 내부 업데이트와 Electron은 현재 범위에 넣지 않는다. [T-001](tickets/T-001-portable-local-app.md)은 Windows 후속 검증과 최신 macOS 재검증을 수행했으며 별도 장비 배포·실제 절전 기준이 남아 있다. 같은 날짜 사용자 결정(D-12·D-13)으로 OS 간 데이터 왕복 검증만 백로그로 옮겨 완료 필수 조건에서 제외했다. 각 환경의 정상 동작과 같은 OS의 경로 이동 검증은 유지한다. 채택 구현은 [ADR-006](decisions/ADR-006-local-runtime-and-journal.md), 실행 결과는 [검증 기록](tickets/T-001-verification.md)을 따른다.

## 실행과 저장 경계

T-020은 `/overview` 작업 시작과 기존 `/` 재료 등록/목록·상세를 공통 탐색으로 연결한다. 미전송 입력은 탭의 sessionStorage에 보관하고, 전송 후 불확실한 요청은 UUID와 본문을 고정해 재시도한다. 서버의 명시적 SPA 경로에 시작 화면을 추가했으며 저장 스키마·세션·Origin·종료 정책은 바꾸지 않았다. 실제 화면/회귀 결과는 [T-020 검증 기록](tickets/T-020-verification.md)을 따른다.

- 단일 PC·단일 사용자, 웹 UI 기반 설치형 앱이다. 초기 네트워크 공동 사용과 비밀번호 잠금은 제외한다.
- 실행 환경은 **바이너리 하나 + 바이너리 옆 `db/` 폴더 하나**다.
- `db/`에 SQLite DB·JSON 기록·사진 자산을 모두 저장한다. 경로는 실행 바이너리 기준이며 현재 작업 디렉터리에 따라 바뀌지 않는다.
- 사진은 해시 등 고유명칭을 쓰고 기기별 절대경로에 의존하지 않는다.
- 다른 PC·Mac의 OS별 빌드에서도 SQLite 또는 JSON의 동일 데이터를 사용한다. 사진을 포함한 이동은 `db/` 전체를 대상으로 한다.
- SQLite가 기본 저장소이며 실제 데이터 변경마다 JSON 기록을 남긴다. 기록은 무기한 보관하고 복원은 현재 데이터 전체를 선택한 시점 상태로 되돌린다.
- 재료·업무 초안/확정 변경의 전체 JSON 스냅샷·내구성 있는 기록 대기열·누락 복구를 구현했다. 선택 시점 전체 복원·사진은 미구현이다. 현재 요구만으로 JSON을 단일 최신 파일로 덮어써 과거 상태를 잃는 방식으로 해석하지 않는다.
- 안정화 후 서버 이관 방향은 유지한다. Rust 업무·API 계층의 재사용을 제안하며 실제 서버 배포 환경·인증은 전환 때 설계한다.

## 업무·계산 경계

- 품목·레시피는 고유 ID와 버전으로 참조하고 수정 전 상태를 보존한다. 삭제 대신 아카이빙한다.
- 판매는 개수·당시 레시피/판매가·금액·입력 시각을 저장한다. 레시피 수량 0·재고 부족으로 판매 확정을 막지 않고 판매만으로 재고를 차감하지 않는다.
- 품목별 마지막 실사 이후 확정 입고·생산·반품·명시 폐기와 새 실사를 대조해 소모를 확정한다. 별도 예상 현재고를 운영하지 않는다.
- 실사 소모는 해당 재료를 직접 참조한 메뉴의 판매 개수 비율로 배분한다. 대상이 없으면 미배분 소모다. 생산 투입·반품·폐기를 다시 판매 소모로 차감하지 않는다.
- 보유 평균 단가를 기본으로 하며 재고가 없으면 마지막 유효 단가, 입고 전에는 등록 가격으로 레시피 원가를 계산한다. 0원과 가격 없음은 구분한다.
- 실제 손질/비축의 투입 원가를 결과물에 이월한다. 여러 결과물은 주 결과물 100%·나머지 0%를 기본으로 수정 가능하다.
- 정상 소모는 원가를 차감한다. 명시 폐기 손실은 잔량에 배분하고 전량 폐기는 별도 손실로 종료한다. 반품은 현재 평균 단가로 가치 차감하며 원구입 금액은 참고로 보존한다.
- 레시피 수정은 이후 판매에만 적용한다. 업무 오입력 정정은 원기록·실사·배분 연결과 영향 범위를 보존한다.
- 메뉴 크기는 별도 메뉴이며 복제본은 독립적으로 수정한다. 가상 자료만 예제/테스트에 사용하며 MIT·제3자 라이선스 고지를 유지한다.

## 운영 정책과 기술 설계의 경계

[ADR-007](decisions/ADR-007-consumption-and-ticket-scope.md)이 ADR-003·ADR-004의 판매 즉시 차감·자동 폐기·부족 확정 금지·원구입금액 반품 규칙을 대체했다. 지연 입고의 현재 반영·실사 중복 방지, 명시 폐기의 손실 처리, 초과 조정, 원기록 보존은 유지한다. [T-002](tickets/T-002-domain-contract.md)의 [계산·데이터 계약](DOMAIN-CONTRACT.md)은 단위·정밀도·실사 구간·원가/정정 계산과 데이터 관계의 설계 검토를 마쳤다. 제품 구현은 후속 티켓에서 진행한다.

실사 정산 기준은 실제 확정 변동으로 만든다. 판매의 레시피 예상 소모를 차감한 장부와 실사를 다시 비교하는 모델을 도입하지 않는다. 마지막 실사 수량·시각과 이후 확정 변동을 표시하고 실사 전 소모 미확정 상태를 유지한다.

T-005는 요청 UUID·트랜잭션·JSON 발행/복구를 공통화하고 사전 가격의 DB 임시 기록·확정·정정 연결에 적용한다. 실제 입고·판매·실사·배분은 각 업무 티켓에서 같은 트랜잭션에 연결한다. 버전·임시 기록·정정·배분도 JSON과 전체 복원 대상이다. 기록·자산 무기한 보존과 사진 연결·복원·이전 DB 호환은 T-015·T-018~T-019에서 통합 검증한다. 저장량과 시작 검사 비용은 T-021에서 가상 누적 자료로 측정한다.

Rust·Nuxt와 브라우저 실행은 확정됐다. 현재 구성은 Nuxt 정적 SPA를 Rust에 내장하고 Axum·Tokio가 HTTP·WebSocket을, rusqlite `bundled`가 SQLite를 처리한다. T-001에서 이 구성을 채택하고 Cargo.lock·frontend/package-lock.json에 버전을 고정했다. Nuxt 자산 생성 후 OS별 release 빌드가 필요하며, 단일 바이너리·추가 런타임 불필요 여부는 배포물로 검증한다. 근거와 대안은 ADR-005를 따른다.

heartbeat는 복수 연결·재연결 유예·관측 공백을 구분하고 수락한 저장의 완료를 기다리도록 구현했다. 순차 마이그레이션·실패 복구·미래 스키마 보호는 합성 fixture 범위에서 검증했다. 실제 절전·정식 이전 버전·과거 JSON과 사진 전체 복원은 별도 검증 대상이다.

| `src/server.rs` | API·세션·Host/Origin 검증·정적 라우팅·WebSocket 작업 관리 |

| `src/store/catalog.rs`, `src/catalog.rs` | 품목 버전·사전 가격·검색·아카이브와 요청 응답 보존·catalog DTO |

| `frontend/app/` | 한국어 재료 등록·목록·상세·연결 안내·실패 요청 재시도 |
| `scripts/build.mjs`, `build.rs` | 정적 생성·입력/산출물 해시·자산 내장 검증·release 빌드 경로 치환 |
| `scripts/verify-windows.mjs` | 격리 Chrome/Edge의 실제 30분 백그라운드·브라우저 강제 종료 검증 |
| `tests/`, `frontend/e2e/` | 가상 자료로 저장·장애·마이그레이션·HTTP·소켓·브라우저 검증 |

T-003은 스키마 v3·JSON 형식 v2로 확장한다. 기존 `materials`·생성 요청·JSON v1 원문은 보존하고 품목 버전/head·사전 가격·불변 변경 응답·epoch/revision을 추가한다. 초기 revision은 0이며 성공한 영속 변경의 seq로 갱신한다. JSON v2의 `state`는 품목 원본·모든 버전/가격·요청 기록을 포함하며 outbox 원문을 재귀적으로 담지 않는다. 같은 요청 재시도는 현재 품목 대신 당시 응답을 반환하며, JSON 복구가 끝나기 전에 성공 응답하거나 다음 변경을 적용하지 않는다.

파일 구성·저장 완료 의미·기존 호환/복구 기준은 ADR-006을 유지한다. 과거 DB 테스트에는 합성 v1과 T-001의 v2 구조 fixture를 사용하며 실제 정식 이전 버전의 회귀 검증을 대신하지 않는다. 상세 확장과 검증 범위는 [T-003 계획](tickets/T-003-plan.md)을 따른다. 실행 시 외부 Node·SQLite 개발 도구를 호출하지 않는다. 기존 macOS 산출물의 동적 의존성은 OS 제공 프레임워크와 라이브러리로 확인했으며 T-003 변경분의 macOS 실행은 별도 미검증이다.

T-005의 현재 writer는 스키마 v4·JSON 형식 v2다. 업무 원본·입력 revision/head·확정·가격 결과·정정 연결의 여섯 관계를 추가한다. 초안은 원입력과 필요한 수정 이유를 보존하며 효과를 만들지 않는다. 미리보기의 epoch/revision/head에서 확정하고, 가격 효과·확정·사용 버전·요청 원응답·전체 snapshot을 같은 트랜잭션에 저장한다. 원확정은 바꾸지 않고 정정 이유와 대체 확정을 연결한다. 원정정 대상 가격, 현재 사전 가격, 새 가격을 구분한다.

옛 v1/schema1~2·v2/schema3와 새 v2/schema4는 각각 정해진 필수 필드를 검증한다. 마이그레이션 원 DB보다 미래인 snapshot, 누락된 업무 컬렉션과 미지원 입력 종류/버전은 거절한다. 이전 UUID·epoch/revision·응답·JSON 바이트를 보존하며, catalog 변경도 업무를 포함한 전체 snapshot을 남긴다. API는 명시적으로 지원한 사전 가격 업무만 받아들이며 실제 판매/재고 지원을 미리 성공 처리하지 않는다. [T-005 계획](tickets/T-005-plan.md)과 [검증 기록](tickets/T-005-verification.md)에 기존 v3 fixture·발행 실패·원자성·UI 재시작과 후속 통합 경계를 기록한다.

| 영역 | 설계할 사항 |
| --- | --- |
| 재고·소모 | 품목별 실사 구간·확정 변동·판매 개수 배분·미배분과 정정 참조 (T-002·T-005·T-010~T-012) |
| 원가 | 보유/마지막/사전 가격·0원, 명시 폐기·평균 단가 반품·여러 결과물·정밀도·보정 (T-002·T-004·T-008·T-011·T-013) |

| 설치·실행 | Windows·macOS 빌드·UI 내장·브라우저 열기·heartbeat 안전 종료, 수동 교체·바이너리 기준 경로 처리 |

기술 설계 항목은 현재 확정 규칙과 수량·가치 보존으로 도출하고, 설명할 수 없는 새 사례만 확인한다. 전체 실행 순서는 [티켓 색인](tickets/README.md)을 따른다. 부분 입고·보관 위치·초기 자료 이관을 첫 구현의 선행 조건으로 두지 않는다.
