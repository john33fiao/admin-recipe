# 레시피 관리자 어드민

- 식당 "순창한상" 오픈 준비를 위해 사용합니다

셰프 1명이 레시피와 식당 운영 정보를 관리하는 웹 UI 기반 설치형 앱을 직접 개발합니다. 초기에는 로컬에서 사용하고 안정화 후 별도 서버로 이관합니다. 소스코드를 공개할 계획이며, 운영 데이터는 공개 코드와 분리합니다.

## 현재 상태

Rust 서버에 Nuxt UI를 내장한 첫 실행파일과 재료 이름·관리 단위 등록 → SQLite/JSON 저장 → 목록·상세 조회를 구현했습니다. **T-001은 진행 중**입니다. 검증 대상은 Windows x64·macOS ARM64입니다. Windows 후속 검증에 이어 현재 Mac의 빌드·사용자 흐름을 재검증했으며, 별도 깨끗한 장비·실제 절전 등 필수 기준은 남아 있습니다. 2026-10-24 사용자 결정으로 Windows↔macOS 데이터 왕복 검증은 백로그로 옮겼습니다. 재고·원가·판매 등 전체 업무 범위는 아직 완료하지 않았습니다.

- **1차:** 레시피·식재료 원가·발주·입고·판매·재고
- **2차:** 내일 메뉴 계획·작업시간
- **백로그:** 시설 점검·부분 입고·보관 위치·OS 간 데이터 왕복 검증·소모를 연결할 판매 직접 선택
- **초기 운영:** 단일 PC 사용. 바이너리 하나와 옆의 `db/` 폴더 하나로 실행하며 SQLite·JSON 변경 기록·사진을 이 폴더에 보관

1차 목표는 메뉴 판매·명시 폐기를 기록하고, 확인한 품목의 실사로 소모를 확정하는 것입니다. 판매 입력만으로 재고를 차감하거나 예상 현재고를 별도 관리하지 않습니다. 소모는 메뉴 판매 개수 비율로 배분하고 명시 폐기와 구분합니다. 입고 전 가격 등록·마지막 유효 단가 계산, 현재 평균 단가 반품·버전/아카이빙을 포함한 최신 정책은 [ADR-007](docs/decisions/ADR-007-consumption-and-ticket-scope.md), 전체 T-001~T-030의 순서는 [티켓 색인](docs/tickets/README.md)에 있습니다. 재료·발주·실제 입고와 보유 평균, 레시피·현재 원가를 구현했으며 판매·실사·소모 배분은 후속 구현입니다.

현재 재료 등록마다 JSON을 기록하고 무기한 보관하며 비밀번호 잠금은 없습니다. 선택 상태 전체 복원·사진 보관은 후속 구현 범위입니다. 다른 PC·Mac의 호환 빌드에서 같은 데이터를 사용하고 사진까지 옮길 때는 `db/` 전체를 함께 가져가는 것이 확정한 목표입니다.

[T-002 계산·데이터 계약](docs/DOMAIN-CONTRACT.md)의 설계와 독립 검토를 완료했습니다. 정밀도·단위·실사/지연 입고·버전/복원 계약과 가상 수용 사례를 후속 구현의 기준으로 사용합니다. 이는 업무 기능 구현이나 실제 시연 완료를 뜻하지 않습니다.

[T-020 공통 UI](docs/tickets/T-020-verification.md)는 작업 시작·재료 관리 탐색, 같은 탭에서 작성 중인 입력 보관, 라이트/다크와 세 화면 너비의 입력·목록·상세 검증을 완료했습니다. 브라우저의 미저장 입력 보관과 아래 업무의 DB 임시 저장은 구분합니다.

[T-003 재료 관리](docs/tickets/T-003-verification.md)는 종류·설명·이름 검색·정보 수정/보관·사전 가격과 변경 이력을 추가합니다. 0원과 가격 없음은 구분하며 가격 등록으로 실제 재고가 생기지 않습니다. g↔kg·mL↔L 표시는 바꿀 수 있고 다른 차원은 새 재료로 등록합니다. 이전 재료 UUID·원래 등록 응답·JSON 원문을 보존합니다. 실제 보유 평균/마지막 단가 연결은 T-007 입고 원장에서 검증했습니다.

[T-005 업무 기록](docs/tickets/T-005-verification.md)은 사전 가격을 DB 초안으로 저장하고 다시 열어 수정·미리보기·확정하는 흐름을 추가합니다. 미완성 초안은 가격에 반영되지 않으며 확정 시 가격·사용한 재료 버전·요청·시각을 함께 기록합니다. 정정은 원확정과 이유를 보존하고 최신 유효 확정으로 연결합니다. T-007이 실제 입고 효과를 공통 저장 경로에 연결했습니다. 판매·실사와 일반 정정은 후속 티켓에 남으며 현재 검증 상태와 남은 통합을 구분합니다.

[T-006 발주](docs/tickets/T-006-verification.md)는 주문 초안·미리보기·확정, 미입고 주문의 수정·취소와 이력을 구현·검증했습니다. 주문량은 보유 재고·가치에 더하지 않으며 선택 금액의 빈 값과 0원을 구분합니다. 실제 입고에 따른 주문 종료는 T-007에 연결하며 최초·수정 주문량과 실입고량을 따로 보존합니다.

[T-007 입고](docs/tickets/T-007-verification.md)는 직접/주문 연결 입고의 실제 수량·구입금액·과거 입고일을 저장하고 보유 수량·가치와 평균 단가를 계산합니다. 0원과 미입력 금액을 구분하고, 이미 실사에 포함됐거나 포함 여부가 불확실한 입력은 확정할 수 없는 초안으로 보관합니다. 마지막 확인 수량·시각과 정산 기준/이후 변동은 별도 계약이며 실제 실사 화면과 지연 입고 보정은 T-010/T-011에 남습니다. T-007에서 스키마 v6·JSON v2와 이전 원문 보존을 검증했습니다.

[T-004 레시피](docs/tickets/T-004-verification.md)는 직접 구성·배합 기준 개수·조리 내용·판매가와 불변 버전, 독립 복제·양방향 조회를 구현·검증했습니다. 현재 가격을 적용한 원가는 배합 조회와 별도로 계산하며, 0수량·0원·가격 미등록과 판매가 없음/0원의 원가율 사유를 구별합니다. 새 writer는 스키마 v7·JSON v2이며 이전 JSON v1과 v2/schema3~6 원문을 유지합니다. Rust168·UI단위37·브라우저43·화면6종·키보드를 검증했으며 실제 생산·판매와 최종 시연은 후속 티켓에 남습니다.

운영 예외 네 가지와 Rust 백엔드·Nuxt 프론트엔드를 확정했습니다. 바이너리가 로컬 서버와 웹브라우저를 열며 WebSocket heartbeat 연결이 일정 시간 끊기면 종료합니다. 앱 내부 업데이트는 제외하고 새 앱이 이전 DB를 계속 지원합니다. Electron은 현재 고려하지 않습니다. [기술 결정 기록](docs/decisions/ADR-005-rust-nuxt-local-server.md)과 [첫 구현 티켓](docs/tickets/T-001-portable-local-app.md)에 구현 결과·미검증 항목을 정리했습니다. 기존 화면 초안은 레이아웃 참고안입니다.

## 개발·실행

개발 환경은 Rust 1.98 이상과 C 컴파일러/OS SDK, Node `^22.22.3 || ^24.15.0 || >=26.0.0`입니다. 버전은 Cargo.lock·frontend/package-lock.json으로 재현합니다. 빌드 도구는 개발 시 필요하며 배포 실행 시 Node 서버를 사용하지 않습니다.

```sh
npm --prefix frontend ci
node scripts/build.mjs
```

빌드는 UI 생성·내장 검사 뒤 release를 만듭니다. Rust 소스 위치의 개인 경로를 치환하고 최종 실행파일의 홈/프로젝트 경로 잔존을 검사합니다. 별도 `RUSTFLAGS` 등으로 이 설정을 덮어쓰거나 C/링커 입력을 추가했다면 산출물 검사를 다시 확인해야 합니다. 최소 OS·서명·공증의 지원 범위는 아직 확정하지 않았습니다.

macOS 실행파일은 `target/release/sunchang-hansang`, Windows는 `target/release/sunchang-hansang.exe`입니다. 자신이 쓰기 가능한 폴더로 해당 OS의 실행파일을 복사한 뒤 실행하세요. 기본 브라우저가 열리고 실행파일 옆 `db/`에 데이터가 생성됩니다. 브라우저 자동 열기에 실패하면 터미널에 출력된 주소를 직접 엽니다. `--no-browser`로 자동 열기를 생략할 수 있습니다.

모든 화면의 연결이 끊기면 120초 유예 후 종료하며 진행 중인 저장을 기다립니다. 초기 접속 대기도 120초입니다. 같은 `db/`를 중복 실행하면 두 번째 앱은 오류로 종료합니다. 앱을 수동 교체하거나 데이터를 옮길 때는 먼저 정상 종료한 뒤 `db/` 전체를 보존하세요. 이전 앱이 새 DB를 읽는 역방향 호환은 보장하지 않습니다.

JSON 기록 오류가 표시되면 같은 화면의 **같은 요청 재시도**를 사용하세요. DB에는 이미 저장됐을 수 있습니다. 앱 재실행으로 포트가 바뀐 경우 목록을 먼저 확인하세요. JSON 변경 기록은 구현했지만 선택 시점 전체 복원과 사진은 아직 구현하지 않았습니다. 운영 데이터의 영속 저장소는 `db/`이며 Git에 넣지 않습니다.

## 검증

UI를 변경했다면 먼저 `node scripts/build.mjs`를 실행합니다. Cargo 빌드는 누락되거나 오래된 UI 자산을 거절합니다.

```sh
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
npm --prefix frontend test
npm --prefix frontend run typecheck
node --test scripts/ui-manifest.test.mjs
node scripts/ui-manifest.mjs --check
node --test scripts/release-artifact.test.mjs
cd frontend
npm exec -- playwright install chromium
npm run test:e2e
```

실행 결과와 수용 기준별 상태는 [T-001 검증 기록](docs/tickets/T-001-verification.md)과 각 기능 티켓에 있습니다. 브라우저 검증은 가상 데이터를 격리한 임시 경로에 만들고 release 실행파일을 사용하며 한글·공백 경로도 검사합니다. 정상 종료는 모든 테스트 페이지를 빈 페이지로 이동한 뒤 기본 120초 유예·종료 코드·메시지를 확인합니다. Windows의 `kill('SIGINT')`를 정상 종료 증거로 사용하지 않습니다. T-001의 초기 6개 시나리오만 직렬 실행해도 약 14분이 걸리며, 후속 기능의 재시작 검증이 추가됩니다.

Windows에서 설치된 Chrome·Edge를 별도 프로필로 30분 동안 검증하려면 저장소 루트에서 `node scripts/verify-windows.mjs`를 실행합니다. 일반 설치 위치의 두 브라우저가 필요합니다. 테스트 창을 최소화하고 실제 `hidden` 상태·서버 생존을 매분 확인한 뒤 복귀·브라우저 프로세스 강제 종료·앱의 기본 종료 유예를 확인하므로 약 32분 이상 걸립니다. 실행별 증거는 제외된 `tmp/verification/windows-runtime/run-*/`에 남습니다. 테스트 창을 조작하거나 실제 절전이 발생하면 실패할 수 있습니다. 이는 실제 절전 시험을 대신하지 않습니다.

같은 개발 PC에서 PATH를 비운 실행과 DLL/라이브러리 검사는 **개발 도구가 없는 별도 Windows/Mac 검증을 대신하지 않습니다. 실제 절전과 다운로드 서명·공증도 미검증**입니다. Windows↔macOS 데이터 왕복 검증은 백로그이며 현재 완료 필수 기준에서 제외합니다. OS 간 데이터 사용 목표와 같은 OS의 경로 이동 검증은 유지합니다. 현재 Windows 실행파일은 서명하지 않았으며 소스 push는 배포 준비 완료를 뜻하지 않습니다.
