# 레시피 관리자 어드민

- 식당 "순창한상" 오픈 준비를 위해 사용합니다

셰프 1명이 레시피와 식당 운영 정보를 관리하는 웹 UI 기반 설치형 앱을 직접 개발합니다. 초기에는 로컬에서 사용하고 안정화 후 별도 서버로 이관합니다. 소스코드를 공개할 계획이며, 운영 데이터는 공개 코드와 분리합니다.

## 현재 상태

Rust 서버에 Nuxt UI를 내장한 첫 실행파일과 재료 이름·관리 단위 등록 → SQLite/JSON 저장 → 목록·상세 조회를 구현했습니다. **T-001은 진행 중**입니다. 검증 대상은 Windows x64·macOS ARM64입니다. Windows 후속 검증에 이어 현재 Mac의 빌드·사용자 흐름을 재검증했으며, 별도 깨끗한 장비·실제 절전 등 필수 기준은 남아 있습니다. 2026-10-24 사용자 결정으로 Windows↔macOS 데이터 왕복 검증은 백로그로 옮겼습니다. 기능별 구현 결과와 전체 배포 준비 판정은 아래에서 구분합니다.

- **1차:** 레시피·식재료 원가·발주·입고·판매·재고
- **2차:** 내일 메뉴 계획·작업시간
- **백로그:** 시설 점검·부분 입고·보관 위치·OS 간 데이터 왕복 검증·소모를 연결할 판매 직접 선택
- **초기 운영:** 단일 PC 사용. 바이너리 하나와 옆의 `db/` 폴더 하나로 실행하며 SQLite·JSON 변경 기록·사진을 이 폴더에 보관

1차 목표는 메뉴 판매·명시 폐기를 기록하고, 확인한 품목의 실사로 소모를 확정하는 것입니다. 판매 입력만으로 재고를 차감하거나 예상 현재고를 별도 관리하지 않습니다. 소모는 메뉴 판매 개수 비율로 배분하고 명시 폐기와 구분합니다. 입고 전 가격 등록·마지막 유효 단가 계산, 현재 평균 단가 반품·버전/아카이빙을 포함한 최신 정책은 [ADR-007](docs/decisions/ADR-007-consumption-and-ticket-scope.md), 전체 티켓의 순서는 [티켓 색인](docs/tickets/README.md)에 있습니다. 재료·발주·실제 입고와 보유 평균, 레시피·현재 원가, 실제 생산·원가 이월과 판매 기록, 선택 실사·소모 배분·명시 폐기와 지연 입고 보정을 구현했습니다. 업무 오입력 정정·취소와 영향 미리보기, 현재 평균 단가 반품과 실사 연결도 검증했습니다. 판매·생산·폐기·실사를 모아 개별 저장·확정하는 작업 화면도 구현·검증했습니다. 여러 사진·대표 사진·구입처와 과거 자산 보존도 구현·검증했습니다. 판매 통계·실사 소모·원가 이력과 현재 품목 연결도 구현·검증했습니다. 마지막 확인 수량과 이후 변동·전체 목록을 제공하는 운영 개요도 구현·검증했습니다. 사진과 버전 이력을 포함한 전체 복원도 구현·검증했습니다. 이전 자료 호환과 현재 Mac의 전체 폴더 이동·보존 요청·재복원을 검증했습니다. 지정 실제 시연·로컬 통합·규모 측정을 확인했으며 필수 외부 실환경 조건은 T-021에 남아 있습니다.

현재 재료 등록마다 JSON을 기록하고 무기한 보관하며 비밀번호 잠금은 없습니다. 사진은 같은 db/ 안에 보관합니다. 자료 복원 화면에서 선택 시점의 전체 상태를 검증·미리보기한 뒤 복원할 수 있습니다. 기존 기록과 사진, 직전 상태 및 원요청 처리 근거는 보존합니다. 다른 PC·Mac의 호환 빌드에서 같은 데이터를 사용하고 사진까지 옮길 때는 `db/` 전체를 함께 가져가는 것이 확정한 목표입니다.

[T-002 계산·데이터 계약](docs/DOMAIN-CONTRACT.md)의 설계와 독립 검토를 완료했습니다. 정밀도·단위·실사/지연 입고·버전/복원 계약과 가상 수용 사례를 후속 구현의 기준으로 사용합니다. 이는 업무 기능 구현이나 실제 시연 완료를 뜻하지 않습니다.

[T-020 공통 UI](docs/tickets/T-020-verification.md)는 작업 시작·재료 관리 탐색, 같은 탭에서 작성 중인 입력 보관, 라이트/다크와 세 화면 너비의 입력·목록·상세 검증을 완료했습니다. 브라우저의 미저장 입력 보관과 아래 업무의 DB 임시 저장은 구분합니다.

[T-003 재료 관리](docs/tickets/T-003-verification.md)는 종류·설명·이름 검색·정보 수정/보관·사전 가격과 변경 이력을 추가합니다. 0원과 가격 없음은 구분하며 가격 등록으로 실제 재고가 생기지 않습니다. g↔kg·mL↔L 표시는 바꿀 수 있고 다른 차원은 새 재료로 등록합니다. 이전 재료 UUID·원래 등록 응답·JSON 원문을 보존합니다. 실제 보유 평균/마지막 단가 연결은 T-007 입고 원장에서 검증했습니다.

[T-005 업무 기록](docs/tickets/T-005-verification.md)은 사전 가격을 DB 초안으로 저장하고 다시 열어 수정·미리보기·확정하는 흐름을 추가합니다. 미완성 초안은 가격에 반영되지 않으며 확정 시 가격·사용한 재료 버전·요청·시각을 함께 기록합니다. 정정은 원확정과 이유를 보존하고 최신 유효 확정으로 연결합니다. 입고·판매·실사·폐기도 같은 저장 경로를 사용하며 일반 정정은 아래 T-012에 연결합니다.

[T-006 발주](docs/tickets/T-006-verification.md)는 주문 초안·미리보기·확정, 미입고 주문의 수정·취소와 이력을 구현·검증했습니다. 주문량은 보유 재고·가치에 더하지 않으며 선택 금액의 빈 값과 0원을 구분합니다. 실제 입고에 따른 주문 종료는 T-007에 연결하며 최초·수정 주문량과 실입고량을 따로 보존합니다.

[T-007 입고](docs/tickets/T-007-verification.md)는 직접/주문 연결 입고의 실제 수량·구입금액·과거 입고일을 저장하고 보유 수량·가치와 평균 단가를 계산합니다. 0원과 미입력 금액을 구분하고, 포함 여부가 불확실한 입력은 확정할 수 없는 초안으로 보관합니다. 마지막 확인 수량·시각과 정산 기준/이후 변동은 별도 계약입니다. 실제 실사는 T-010, 사용자가 실사 포함분을 확인한 입고는 T-011에 연결합니다. T-007에서 스키마 v6·JSON v2와 이전 원문 보존을 검증했습니다.

[T-004 레시피](docs/tickets/T-004-verification.md)는 직접 구성·배합 기준 개수·조리 내용·판매가와 불변 버전, 독립 복제·양방향 조회를 구현·검증했습니다. 현재 가격을 적용한 원가는 배합 조회와 별도로 계산하며, 0수량·0원·가격 미등록과 판매가 없음/0원의 원가율 사유를 구별합니다. 당시 스키마 v7·JSON v2와 이전 JSON v1 및 v2/schema3~6 원문 보존을 확인했습니다. Rust168·UI단위37·브라우저43·화면6종·키보드를 검증했으며 실제 판매 참조와 최종 시연은 후속 티켓에 남습니다.

[T-008 생산](docs/tickets/T-008-verification.md)은 실제 여러 투입·결과와 원가 배분을 한 번 확정하고 보유 기준에 반영합니다. 같은 재료의 투입은 입력 전 수량/가치에서 합쳐 계산하며 전량 사용 뒤 마지막 유효 단가를 보존합니다. 실제량이 기록과 충돌하면 입력을 유지하고 누락 입고 등 근거 확인을 안내합니다. 당시 스키마 v8·JSON v2와 이전 schema6/7의 입고 전용 보유 형식 및 원문을 확인했습니다. Rust218·UI단위43·브라우저50·화면6종·키보드를 검증했으며 실제 실사·일반 정정은 T-010/T-012에서 연결합니다.

[T-009 판매](docs/tickets/T-009-verification.md)는 개수·자동 입력 시각과 당시 품목/레시피·판매가·단가 출처·원가를 고정하고 개수 정정 이력을 남깁니다. 판매 자체로 재고를 차감하지 않으며 0개·0원·가격 없음과 실사 소모 미확정을 구분합니다. 당시 writer는 스키마 v9·JSON v2였으며 이전 schema8 원요청·원응답·JSON을 보존했습니다. 전체 Rust258·UI단위51·브라우저57·상세6화면·키보드와 타입/정적 검사를 통과했습니다. 실사 배분 표시는 T-010에 연결하며 이미 배분된 판매의 정정은 T-012에서 이어갑니다.

[T-010 실사·폐기](docs/tickets/T-010-verification.md)는 확인한 품목만 실제 수량으로 정산하고 소모 수량·원가를 직접 참조 메뉴의 판매 개수로 배분합니다. 빈 수량·명시한0·처음 확인한 시작 가치를 구별하며, 판매 없음/총개수0은 미배분으로 남깁니다. 부분 폐기는 총가치를 유지하고 전량 폐기는 남은 가치를 손실로 종료합니다. 당시 writer는 스키마 v10·JSON v2이며 이전 schema9 원요청·응답·JSON을 보존합니다. 실제 관측 뒤 생산 재시도와 판매별 배분 표시를 연결하고, 실행 결과와 남은 정정/반품 범위는 검증 기록에 구분합니다.

[T-011 지연 입고](docs/tickets/T-011-verification.md)는 관련 실사와 이미 포함된 수량을 명시적으로 선택하여 미포함 수량만 추가합니다. 실제 구입금액과 당시 확인 가치의 차이를 현재 품목별 가치 변화와 이미 사용된 부분의 별도 보정으로 나누며, 과거 판매·생산·실사 기록은 보존합니다. 포함 몫은 생산·소모 이후에도 원천별로 추적해 재사용을 차단합니다. 당시 writer는 스키마 v11·JSON v2이며 정상 API로 생성한 schema10의 원응답·JSON을 보존합니다. 실제 관측 정정은 T-012, 반품 연결은 T-013, 지정 실제 자료 시연과 배포 준비 판정은 T-021에서 검증합니다.

[T-012 업무 정정](docs/tickets/T-012-verification.md)은 입고·생산·판매·폐기·실사의 취소/대체와 영향 미리보기를 추가합니다. 원기록과 당시 레시피·가격을 보존하고 유효 개정·현재 결과를 따로 표시합니다. 판매 개수 정정은 확정 총소모와 현재 재고를 유지하며 배분만 바꿉니다. 수량 사건 정정은 후속 실사·포함 입고의 영향을 계산하고 필요한 확인을 안내합니다. 당시 writer는 스키마 v12·JSON v2이며 schema11 원문과 참조를 보존합니다. Rust 전체443건과 최종 영향112건·UI80건·브라우저80건 각각·키보드/화면 검증을 통과했습니다. 반품은 아래 T-013에 연결하며 지정 실제 시연은 T-021에서 진행합니다.

[T-013 반품](docs/tickets/T-013-verification.md)은 원입고와 구입 당시 참고 금액·단위를 보존하고 현재 평균 단가로 수량·가치를 차감합니다. 실제 원입고의 미반환 한도와 현재 보유 수량을 각각 검사하며 전량 반품은 남은 가치를 모두 종료합니다. 반품 정정·취소·복원, 지연 입고 가치 보정과 다음 실사 중복 제외를 연결했습니다. 당시 writer는 스키마 v13·JSON v2이며 정상 API로 만든 schema12 원문을 보존합니다. Rust 전체488·UI90·브라우저87개 각각·키보드/화면8장과 타입/정적 검사를 통과했습니다.

[T-014 모아 입력](docs/tickets/T-014-verification.md)은 판매·생산·폐기·실사를 한 작업 목록에서 열고 기록별로 임시 저장·미리보기·확정합니다. 저장한 초안은 재시작 후 이어서 입력하며, 미저장 입력과 처리 결과 미확인 요청은 각 항목에 구분해서 표시합니다. 다른 저장 뒤에는 실사를 다시 미리보기하고 끊긴 요청은 같은 식별자·본문으로 확인합니다. 기존 저장·계산 경로와 스키마 v13을 사용합니다. 영향 Rust21·UI102·브라우저42건과 키보드·화면8장·타입/정적 검사를 확인했습니다.

[T-015 사진·구입처](docs/tickets/T-015-verification.md)는 재료와 레시피 상세에서 여러 사진·대표 한 장·구입처 링크/설명을 저장합니다. JPEG/PNG를 한 번에 한 장씩 추가하고 원본을 db/에 보관합니다. 연결 해제·교체·독립 복제 뒤에도 과거 파일을 유지하며, 응답 유실 시 같은 요청과 원본 파일로 확인합니다. 스키마 v14·JSON v2와 이전 v13 자료 보존을 검증했습니다. Rust531·UI114·기존 브라우저18건, 신규7흐름과 실패 수정 후 영향2건·키보드·6화면을 확인했습니다. 통계와 현재 연결 조회는 아래 T-016에 이어집니다.

[T-016 통계·이력](docs/tickets/T-016-verification.md)은 원입력 시각의 기간과 현재 유효 정정을 기준으로 판매·실사 소모·종류별 업무를 조회합니다. 당시 레시피 원가와 실사 배분 원가, 미계산·0·취소·기간 밖 근거를 구분하고 실제 상세로 연결합니다. 현재 직접 구성·역참조·간접 경로도 별도로 제공합니다. 스키마 v14·JSON v2를 유지하며 Rust562·UI124·기존 브라우저28건, 신규 첫6건 통과와 시험 대기 수정 후 마지막1건·키보드·6화면을 확인했습니다. 운영 개요는 아래 T-017에 이어집니다.

[T-017 운영 개요](docs/tickets/T-017-verification.md)는 마지막으로 실제 확인한 수량·시각과 그 뒤의 입고·생산·반품·폐기를 구분합니다. 보관 포함 품목·주문 종료 차이·미배분/미확정·DB 초안을 정확한 건수와 전체 목록으로 확인하고 원기록이나 입력 화면으로 이동합니다. 예상 현재고는 만들지 않습니다. 관련 Rust45개·UI133·기존 브라우저19개, 신규 첫6개와 보완 뒤2개·실제 키보드·6화면을 검증했습니다. 최초 실패와 재검증 근거를 구분합니다.

[T-018 전체 복원](docs/tickets/T-018-verification.md)은 선택 JSON의 품목·업무·버전·정정·배분·초안·사진 연결을 전체 교체하고 기존 원문·사진·요청 근거를 보존합니다. 원문 파일 검증·영향 미리보기·직전 상태 보존·새 세대 기록과 같은 요청의 복구를 구현했습니다. 현재 writer는 스키마 v15·JSON v2입니다. Rust 629개·UI144개·기존 브라우저115개와 신규7개를 최초 실패/영향 재검증으로 확인했고 키보드·여섯 화면과540px 비교표도 검증했습니다. T-019 호환·이동은 [현재 Mac 검증](docs/refs/T-019-compatibility-verification.md)을 완료했습니다. T-021 실제 시연·배포 준비 판정은 별도입니다.

[T-031~T-033 일괄 입력](docs/refs/T-031-T-033-verification.md)은 CSV 양식/업로드·시트 직접 입력·업로드 값 편집을 공통 표에 통합했습니다. 기존 정상 API로 등록하며 오류 수정·부분 성공·원요청 재시도·복원 경계와 UI165·입고 HTTP12·최종 새 브라우저13·6화면/키보드/양식3종을 검증했습니다. 전체 회귀·release 성능과 T-001의 외부 실환경 조건은 T-021에서 별도로 판정합니다.

[T-021 통합·규모 측정](docs/refs/T-021-integration-verification.md)은 현재 Mac의 Rust631·기존 브라우저119와 관측 보완 재검증3개·최종 새13개, 지정 격리 시연90개와 최종 통합48개를 구분합니다. 가상 판매100건에서100번째 초안/확정 포함 저장은 약3.50초, JSON 누적은 약126MB였습니다. 전체 상태 이력 검사 비용을 확인했으며 단일 개발 장비 관측을 운영 성능 보장으로 확대하지 않습니다. T-001의 별도 깨끗한 장비·실제 절전·지원 환경·다운로드 실행/서명 조건이 남아 T-021·배포 준비는 미완료입니다.

운영 예외 네 가지와 Rust 백엔드·Nuxt 프론트엔드를 확정했습니다. 바이너리가 로컬 서버와 웹브라우저를 열며 WebSocket heartbeat 연결이 일정 시간 끊기면 종료합니다. 앱 내부 업데이트는 제외하고 새 앱이 이전 DB를 계속 지원합니다. Electron은 현재 고려하지 않습니다. [기술 결정 기록](docs/decisions/ADR-005-rust-nuxt-local-server.md)과 [첫 구현 티켓](docs/tickets/T-001-portable-local-app.md)에 구현 결과·미검증 항목을 정리했습니다. 기존 화면 초안은 레이아웃 참고안입니다.

## 개발·실행

개발 환경은 Rust 1.98 이상과 C 컴파일러/OS SDK, Node `^22.22.3 || ^24.15.0 || >=26.0.0`입니다. 버전은 Cargo.lock·frontend/package-lock.json으로 재현합니다. 빌드 도구는 개발 시 필요하며 배포 실행 시 Node 서버를 사용하지 않습니다.

```sh
npm --prefix frontend ci
node scripts/build.mjs
```

빌드는 UI 생성·내장 검사 뒤 release를 만듭니다. Rust 소스 위치의 개인 경로를 치환하고 최종 실행파일의 홈/프로젝트 경로 잔존을 검사합니다. 별도 `RUSTFLAGS` 등으로 이 설정을 덮어쓰거나 C/링커 입력을 추가했다면 산출물 검사를 다시 확인해야 합니다. 최소 OS·서명·공증의 지원 범위는 아직 확정하지 않았습니다.

macOS 실행파일은 `target/release/sunchang-hansang`, Windows는 `target/release/sunchang-hansang.exe`입니다. 자신이 쓰기 가능한 폴더로 해당 OS의 실행파일을 복사한 뒤 실행하세요. 기본 브라우저가 열리고 실행파일 옆 `db/`에 데이터가 생성됩니다. 브라우저 자동 열기에 실패하면 터미널에 출력된 주소를 직접 엽니다. `--no-browser`로 자동 열기를 생략할 수 있습니다.

모든 화면의 연결이 끊기면 120초 유예 후 종료하며 진행 중인 저장을 기다립니다. 초기 접속 대기도 120초입니다. 같은 `db/`를 중복 실행하면 두 번째 앱은 오류로 종료합니다. 앱을 수동 교체하거나 데이터를 옮길 때는 먼저 정상 종료한 뒤 `db/` 전체를 보존하세요. 이전 앱이 새 DB를 읽는 역방향 호환은 보장하지 않습니다.

JSON 기록 오류가 표시되면 같은 화면의 **같은 요청 재시도**를 사용하세요. DB에는 이미 저장됐을 수 있습니다. 앱 재실행으로 포트가 바뀐 경우 목록을 먼저 확인하세요. [T-018 전체 복원](docs/tickets/T-018-verification.md)의 구현·검증을 완료했습니다. 복원 화면에서 기존 변경 기록이나 JSON 파일을 선택하고 전체 상태·사진 검사 결과를 확인합니다. 복원 뒤 이전 화면의 요청은 처리 여부를 확인하고 현재 자료를 다시 조회해야 합니다. 운영 데이터의 영속 저장소는 `db/`이며 Git에 넣지 않습니다.

### 수동 앱 교체·데이터 이동과 실패 복구

1. 모든 앱 탭을 닫거나 빈 페이지로 이동하고, 기본 120초 유예 뒤 **안전하게 종료했습니다** 문구와 프로세스 종료를 확인합니다.
2. 실행파일과 `db/` 전체를 별도 사본으로 보존합니다. 실행 중인 DB 파일만 복사하지 않습니다.
3. 같은 OS의 호환 실행파일로 교체하거나 실행파일과 `db/` 전체를 새 폴더로 옮깁니다. 재실행 후 목록·사진·이력·복원 미리보기를 확인합니다.
4. 열기나 변환에 실패하면 실패한 폴더를 보존합니다. 이전의 호환 실행파일과 **그 시점의 온전한 `db/` 사본**을 함께 사용합니다. 새 DB에 옛 실행파일만 넣는 역방향 호환은 보장하지 않습니다.

DB만 옮기면 outbox의 JSON 변경 기록은 재발행할 수 있지만 사진·가져온 JSON 원문·복원 직전 상태 파일은 재구성하지 못합니다. 보존 사진이 없으면 시작을 거절하고, 수입/직전 상태 원문이 없으면 해당 복원 검토가 실패합니다. JSON 단독 가져오기는 구조화 상태 복원이며 사진까지 포함하는 전체 폴더 이동을 대신하지 않습니다. [T-019 검증 기록](docs/refs/T-019-compatibility-verification.md)은 이전 자료의 출처와 같은 OS 이동 근거를 구분합니다. OS 간 왕복 검증은 T-027 백로그입니다.

### CSV·시트 일괄 입력

탐색의 **일괄 입력**에서 재료·메뉴·입고를 선택하세요. CSV 양식을 내려받아 작성하거나 표에 직접 입력하고, 시트에서 복사한 여러 행을 붙여넣을 수 있습니다. 파일은 UTF-8 CSV로 저장하며 `.xlsx`는 지원하지 않습니다. 파일·붙여넣기는 1MiB, 표는 200행까지입니다. 화면의 양식 도움말에서 열과 참조 선택 방법을 확인할 수 있습니다.

업로드한 값도 표에서 고친 뒤 **등록 내용 확인**을 누르세요. 오류가 있으면 새 등록을 시작하지 않습니다. 입고는 실제 수량·금액·입고일과 현재 재고 효과를 보여줍니다. 빈 금액은 미입력이고 `0`은 실제 0원입니다. 실사에 이미 포함된 지연 입고는 해당 행의 **실사 포함 근거**를 선택해야 하며 날짜로 자동 추정하지 않습니다.

**확인한 내용 일괄 등록**은 기존 저장 API로 항목을 순서대로 등록합니다. 중간에 멈추면 성공한 행과 조회 링크는 유지됩니다. 입고 효과가 바뀌면 새 미리보기를 확인한 뒤 이어가세요. 통신 결과가 불명확하면 보존한 같은 요청으로 확인하며 성공 행은 다시 전송하지 않습니다. 같은 내용의 재업로드는 이 탭의 이전 결과를 먼저 보여줍니다. 새 앱 주소나 다른 탭에서는 실제 목록을 확인하세요. 복원 뒤에는 보존 입력·요청을 확인하고 **원입력 보존 후 빈 새 입력**으로 시작합니다. 세부 계약은 [ADR-010](docs/decisions/ADR-010-unified-bulk-entry.md)을 따릅니다.

## 검증

UI를 변경했다면 먼저 `node scripts/build.mjs`를 실행합니다. Cargo 빌드는 누락되거나 오래된 UI 자산을 거절합니다.

```sh
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
npm --prefix frontend test
npm --prefix frontend run typecheck
node --test scripts/ui-manifest.test.mjs
node scripts/ui-manifest.mjs --check
node --test scripts/release-artifact.test.mjs
cd frontend
npm exec -- playwright install chromium
npm run test:e2e
```

실행 결과와 수용 기준별 상태는 [T-001 검증 기록](docs/tickets/T-001-verification.md)과 각 기능 티켓에 있습니다. 브라우저 검증은 가상 데이터를 격리한 임시 경로에 만들고 release 실행파일을 사용하며 한글·공백 경로도 검사합니다. 정상 종료는 모든 테스트 페이지를 빈 페이지로 이동한 뒤 기본 120초 유예·종료 코드·메시지를 확인합니다. Windows의 `kill('SIGINT')`를 정상 종료 증거로 사용하지 않습니다. T-001의 초기 6개 시나리오만 직렬 실행해도 약 14분이 걸리며, 후속 기능의 재시작 검증이 추가됩니다.

현재 macOS에서 가상 전체 업무와 규모 측정을 재현하려면 UI/release 빌드·Chromium 준비 뒤 아래 명령을 사용합니다. 실행마다 별도 시험 DB·기록을 제외 경로에 보존합니다. 성능은 다른 빌드·시험이 끝난 뒤 실행하세요.

```sh
node scripts/verify-integration.mjs
node scripts/verify-performance.mjs
```

Windows에서 설치된 Chrome·Edge를 별도 프로필로 30분 동안 검증하려면 저장소 루트에서 `node scripts/verify-windows.mjs`를 실행합니다. 일반 설치 위치의 두 브라우저가 필요합니다. 테스트 창을 최소화하고 실제 `hidden` 상태·서버 생존을 매분 확인한 뒤 복귀·브라우저 프로세스 강제 종료·앱의 기본 종료 유예를 확인하므로 약 32분 이상 걸립니다. 실행별 증거는 제외된 `tmp/verification/windows-runtime/run-*/`에 남습니다. 테스트 창을 조작하거나 실제 절전이 발생하면 실패할 수 있습니다. 이는 실제 절전 시험을 대신하지 않습니다.

같은 개발 PC에서 PATH를 비운 실행과 DLL/라이브러리 검사는 **개발 도구가 없는 별도 Windows/Mac 검증을 대신하지 않습니다. 실제 절전과 다운로드 서명·공증도 미검증**입니다. Windows↔macOS 데이터 왕복 검증은 백로그이며 현재 완료 필수 기준에서 제외합니다. OS 간 데이터 사용 목표와 같은 OS의 경로 이동 검증은 유지합니다. 현재 Windows 실행파일은 서명하지 않았으며 소스 push는 배포 준비 완료를 뜻하지 않습니다.
